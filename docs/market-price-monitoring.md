# 거래소 시세 기능 기획서

> 상태: 현재 구현 정리 및 개선 기획  
> 기준일: 2026-09-29  
> 진행: 1·4단계 구현(#15), 2·3단계(변화 문구) 구현, 5단계(알림 안정화) 구현  
> 데이터 출처: 모비라이프 OpenAPI `GET market/prices`

## 1. 목적

몰리가 게임 밖에서 거래소를 대신 관찰하고, 사용자가 접속하지 않은 동안에도 가격 변화를 파악할 수 있게 한다.

이 기능은 두 가지 가치를 제공한다.

1. **시세 알림**: 등록한 Discord 채널에서 의미 있는 가격 변화와 신규·사라진 매물을 알려준다.
2. **구매·판매 참고 정보**: 현재 가격이 오르는 중인지 내리는 중인지, 같은 방향이 이어질 가능성이 상대적으로 높은지 간단한 문구로 보여준다.

예측은 정확한 미래 가격이나 투자 조언이 아니다. OpenAPI가 제공하는 최신 변화량을 사람이 빠르게 읽을 수 있는 표현으로 바꾸는 수준으로 한정한다.

## 2. 기본 원칙

- 모비라이프의 최신 시세 응답을 가공해 사용한다.
- `market/prices/history`는 사용하지 않는다.
- OpenAPI가 이미 보유한 시세 이력을 몰리 DB에 장기간 중복 저장하지 않는다.
- 기존 정각 수집에 포함된 값으로 판정하며, 변화 문구를 위해 API 호출을 추가하지 않는다.
- 확신하기 어려운 경우에는 억지로 판정하지 않고 변화 문구를 표시하지 않는다.
- 매진, 비정상 가격, 매물 부족 데이터는 판정에서 제외한다.
- 모든 사용자 응답에 `모비라이프 제공` 출처를 표시한다.
- 외부 API 장애가 다른 봇 기능의 실행을 막지 않게 한다.

## 3. 현재 구현

### 3.1 공통 수집 구조

- `Market/IMarketPriceSource`가 시세 기능과 외부 API 구현을 분리한다.
- `MobiLife/MobiLifeMarketPriceSource`가 `GET market/prices`를 호출한다.
- 한 페이지에 최대 100건을 받고, 검색 결과는 최대 5페이지까지 조회한다.
- 봇 전체가 하나의 `MobiLifeApiClient`를 공유해 호출 제한과 장애 차단을 함께 관리한다.
- 수집 작업은 KST 매 정각 실행한다.
- 마지막 정각 자료가 없거나 오래된 상태로 봇이 시작되면 보충 수집을 시도한다.
- 수집 실패는 해당 시세 기능 안에서 처리하고 다른 기능은 계속 동작한다.
- 회차 수집이 실패하면(API 오류, 응답 검증 실패, 상자·패키지의 비정상 0건 등) 10분 간격으로 최대 3번 다시 시도한다. 다음 재시도 시각이 다음 정각에 닿으면 재시도하지 않고 정각 수집에 맡긴다. 규칙은 `Market/MarketSchedule`에서 공용으로 관리한다.

도메인 모델(`Market/MarketPrice`)에는 다음 값이 전달된다.

- 아이템 ID
- 이름
- 대분류
- 최저가
- 등록 수량
- 매진 여부
- 시세 기준 시각
- 1시간·24시간·7일 가격 등락(퍼센트, nullable)
- 24시간 매물 증감(퍼센트, nullable)

변화량 필드는 모두 퍼센트다(`5.2 = +5.2%`). 2026-09-29 실제 응답으로 확인했고, `count_change_24h`도 개수가 아니라 매물 수의 증감률이다.

값이 말이 안 되는 아이템(최저가·매물 수 음수, 가격 등락 `-100` 미만)은 원본 쪽 일시적 데이터 오류로 보고 통신 오류와 똑같이 해당 검색을 실패 처리한다(회차 재시도 대상). 실패 로그에는 아이템 이름과 문제 필드·값을 남긴다. 2026-09-29에 `야생의 영혼석`이 `total_count: -1`, `count_change_24h: -100.02`로 온 사례가 있으며, 같은 시각 모비라이프 사이트에는 매물이 정상으로 표시되었다. 급등은 실제로 일어날 수 있어 상한은 두지 않고, 매물 증감률은 원본이 -1로 계산해 -100 아래가 나올 수 있어 따로 검사하지 않는다. 필드가 없거나 null이면 null로 두고 기존 기능은 그대로 동작한다.

### 3.2 해연 시세

관련 모듈은 `HaeyeonMarket/`이다.

수집 검색어:

- `해연의`
- `마력석`
- `영혼석`
- `특급`
- `백금강괴`

제작 시트의 해연 완제품과 재료 이름에 정확히 일치하는 결과만 사용한다. 매진이 아니고 가격이 0보다 크며 매물이 3개 이상인 경우를 신뢰 가능한 시세로 본다.

| 명령어 | 현재 동작 |
| --- | --- |
| `/해연시세모니터링` | 실행 채널을 알림 채널로 등록한다. 서버당 한 채널이며 장비·재료 등락률을 설정할 수 있다. |
| `/해연시세모니터링해제` | 해당 서버의 알림 등록을 해제한다. |
| `/해연시세모니터링테스트` | 마지막 저장 시세로 가상의 변동 알림 예시를 보여준다. |
| `/해연시세` | 해연 무기·방어구·장신구·재료 또는 완제품과 재료비 합계를 조회한다. |

현재 알림 기준:

- 완제품 기본 등락률: 10%
- 재료 기본 등락률: 20%
- 완제품 구매와 재료 구매 후 제작의 유불리 전환 기준 여유: 3%
- 서버별 기준가와 현재가를 비교해 설정 등락률을 넘으면 알림
- 완제품 가격과 재료 총액 중 저렴한 쪽이 바뀌면 알림

### 3.3 상자·패키지 시세

관련 모듈은 `KeywordMarket/`이다.

| 종류 | 검색 조건 |
| --- | --- |
| 상자 | 검색어 `상자`, 대분류 `아이템` |
| 패키지 | 검색어 `패키지`, 대분류 제한 없음 |

| 명령어 | 현재 동작 |
| --- | --- |
| `/상자시세모니터링`, `/패키지시세모니터링` | 실행 채널을 등록하고 서버별 등락률을 설정한다. |
| 각 `모니터링해제` | 해당 서버의 알림 등록을 해제한다. |
| 각 `모니터링테스트` | 마지막 저장 시세로 신규·사라짐·등락 예시를 보여준다. |
| `/상자시세`, `/패키지시세` | 마지막 정각 수집 결과를 이름순으로 보여준다. |

현재 알림 기준:

- 기본 등락률: 10%
- 처음 발견한 아이템은 기준가만 만들고 가격 변동 알림은 보내지 않음
- 새 아이템을 알림
- 검색에서 2회 연속 사라진 아이템을 사라진 매물로 알림
- 서버별 기준가 대비 설정 등락률 이상 변하면 알림
- 검색 결과가 최대 페이지 수를 넘어 잘렸을 때는 사라짐 판정을 하지 않음
- 매진이 아니고 가격이 0보다 크며 매물이 3개 이상인 경우만 가격 판정에 사용

### 3.4 현재 저장 구조

현재 구현은 다음 상태를 SQLite에 보관한다.

- 서버별 알림 채널과 등락률 설정
- 마지막 성공 회차의 시세(`haeyeon_latest_prices`, `keyword_market_latest_prices`), 변화량 포함
- 서버별 아이템 기준가와 현재가
- 신규·사라짐 판정을 위한 공통 아이템 상태
- 해연 완제품 구매와 제작의 유불리 상태

정각별 원시 시세 이력은 저장하지 않는다(#15). 조회 명령은 마지막 시세를 사용하고, 가격 변동 알림은 서버별 기준가 상태를 사용한다.

## 4. 확인된 문제 (해결됨)

> #15에서 90일 원시 이력 적재를 없애고 마지막 시세 저장 구조로 바꿨다. 아래는 전환 당시의 판단 근거다.

기존의 90일 원시 시세 보관은 OpenAPI가 이미 관리하는 시세 정보와 역할이 겹쳤다.

- 같은 성격의 데이터를 OpenAPI와 몰리 DB 양쪽에 장기간 보관한다.
- 추적 품목이 늘어날수록 저장량과 관리 비용이 계속 증가한다.
- 새 변화 문구에는 OpenAPI가 이미 계산한 변화율이 있으므로 몰리가 별도 장기 이력을 만들 이유가 적다.
- 장기 시세 분석이 목적이 아닌데도 원시 데이터가 분석용 이력처럼 누적된다.

따라서 장기 원시 이력은 제거하는 방향으로 전환한다. 단, 마지막 시세 조회와 기존 알림 상태 복구에 필요한 최소 상태는 유지한다.

## 5. 신규 변화 문구

### 5.1 사용하는 값

`GET market/prices`의 한 응답에서 다음 값을 사용한다.

| 값 | 용도 |
| --- | --- |
| `pct_change_1h` | 아주 최근 가격 방향 확인 |
| `pct_change_24h` | 하루 가격 방향 확인 |
| `count_change_24h` | 매물이 늘었는지 줄었는지 확인(퍼센트) |
| `pct_change_7d` | 모델에는 수용하되 1차 단순 판정에는 사용하지 않음 |

OpenAPI 필드가 누락될 수 있으므로 변화량은 nullable 값으로 다룬다.

### 5.2 사용자에게 보여줄 표현

허용하는 표현은 아래 다섯 종류뿐이다.

- `하락 중`
- `상승 중`
- `하락 가능성 높음` 또는 `하락 가능성 낮음`
- `상승 가능성 높음` 또는 `상승 가능성 낮음`
- 판단하기 어려운 경우 아무것도 표시하지 않음

표시 예시:

> 📉 하락 중 · 하락 가능성 높음  
> 가격은 내리고 매물은 늘고 있어요.

> 📈 상승 중 · 상승 가능성 낮음  
> 가격은 오르고 있지만 매물도 늘고 있어요.

### 5.3 1차 판정 규칙

가격 방향은 1시간과 24시간 등락이 같은 방향일 때만 확정한다.

| 1시간 가격 | 24시간 가격 | 판정 |
| --- | --- | --- |
| 유의미한 하락 | 유의미한 하락 | `하락 중` |
| 유의미한 상승 | 유의미한 상승 | `상승 중` |
| 서로 반대 또는 변화 미미 | 모든 경우 | 표시하지 않음 |

방향이 확정된 경우 24시간 매물 증감의 부호로 가능성을 덧붙인다.

| 현재 방향 | 24시간 매물 | 최종 표시 |
| --- | --- | --- |
| 하락 | 증가 | `하락 중 · 하락 가능성 높음` |
| 하락 | 감소 | `하락 중 · 하락 가능성 낮음` |
| 상승 | 감소 | `상승 중 · 상승 가능성 높음` |
| 상승 | 증가 | `상승 중 · 상승 가능성 낮음` |
| 상승 또는 하락 | 변화 없음·값 없음 | `상승 중` 또는 `하락 중`만 표시 |

초기 제안 임계값은 가격 등락 절댓값 1%이다. 실제 적용 전 샘플 응답을 확인해 노이즈가 많으면 조정한다. 이 숫자는 코드 곳곳에 흩어 두지 않고 시세 규칙 한 곳에서 관리한다.

### 5.4 판정하지 않는 조건

다음 중 하나라도 해당하면 변화 문구를 표시하지 않는다.

- 매진
- 최저가가 0 이하
- 등록 수량 3개 미만
- 1시간 또는 24시간 가격 등락 값 없음
- 1시간과 24시간 방향이 반대
- 두 가격 등락 중 하나라도 미세 변화 구간 안에 있음
- 비정상적으로 큰 값 등 응답 검증 실패

이 문구는 수요·공급 전체를 증명하지 않는다. 매물 감소는 구매뿐 아니라 등록 취소나 만료로도 발생할 수 있으므로 반드시 `가능성`으로 표현한다.

## 6. 화면 적용 범위

1차 적용은 조회 결과에만 한다.

- `/해연시세`
- `/상자시세`
- `/패키지시세`

2026-09-29에 변화 문구를 정각 알림에도 적용했으나 한 시간마다 판정 변화가 자주 발생했다. 2026-09-30 최종 결정으로 조회 화면의 즉시 판정과 알림용 확정 판정을 분리한다(6.1절).

목록이 길어지는 경우 모든 아이템에 설명 문장을 붙이지 않고 아이콘과 짧은 판정만 표시한다. 상세 이유는 한 항목을 자세히 보여주는 화면이나 도움말에서 사용한다.

### 6.1 알림 적용 최종안 (2026-09-30 결정)

#### 조회와 알림의 역할 분리

- `/해연시세`·`/상자시세`·`/패키지시세` 조회 화면은 이번 성공 회차의 즉시 판정을 그대로 표시한다.
- 조회 목록에는 기존 이모지(`📈`·`📉`·`⏫`·`🔼`·`⏬`·`🔽`)와 범례를 유지한다.
- 정각 알림은 매 회차의 즉시 판정 변화가 아니라 **같은 상승·하락 방향이 3회 연속 확인되어 확정될 때만** 보낸다.
- 가능성 높음·낮음의 변화는 조회 정보로만 사용하고 알림 발생 조건으로 사용하지 않는다.
- 판정 있음과 표시 없음(`➖`) 사이의 변화도 알리지 않는다.
- 이미 알린 확정 방향이 계속 유지되는 동안에는 같은 방향을 반복해서 알리지 않는다.
- 기존 서버별 기준가 등락 알림, 신규·사라짐 알림, 해연 제작 유불리 알림은 이 규칙과 별개로 유지한다.

#### 연속 확인 규칙

연속 횟수는 가능성 단계가 아니라 방향만 비교한다. 예를 들어 `📉⏬`와 `📉🔽`은 둘 다 하락 1회로 센다.

| 정각 판정 | 내부 상태 |
| --- | --- |
| 첫 상승 | 상승 후보 1회 |
| 다음 성공 회차도 상승 | 상승 후보 2회 |
| 다음 성공 회차도 상승 | 상승 3회, 상승 확정 및 최초 알림 |
| 후보와 반대 방향 | 새 방향 후보 1회로 교체 |
| 표시 없음(`➖`) | 표시 없음 후보 1회로 교체 |
| API 수집 실패 | 후보·확정 상태를 변경하지 않음 |

상승·하락 확정 상태에서 반대 방향이 3회 연속 확인되면 새 방향으로 확정하고 방향 전환 알림을 보낸다.

표시 없음이 3회 연속 확인되면 내부 확정 방향을 해제하지만 해제 알림은 보내지 않는다. 이후 상승 또는 하락이 다시 3회 연속 확인되면 새로운 흐름으로 보고 알린다. 표시 없음 1~2회만으로 확정 방향을 해제하지 않아 한 번의 미세 변화 때문에 같은 방향 알림이 반복되는 것을 막는다.

#### 회차 연속성

- 10분 간격 재시도는 원래 정각 수집과 같은 회차이므로 성공하더라도 연속 횟수를 한 번만 올린다.
- 수집 실패 자체는 후보 상태를 바꾸지 않지만, 다음 정각까지 정상 회차가 하나 빠졌다면 연속 확인으로 보지 않는다. 다음 성공 회차에서 후보 횟수를 1회부터 다시 시작한다.
- 마지막으로 평가한 정각 회차를 저장해 재시작이나 지연 후에도 같은 회차를 중복 계산하지 않는다.
- 실패한 회차는 마지막 정상 시세를 교체하지 않는 기존 규칙을 유지한다.

#### 저장 상태

최근 3시간의 가격·변화율·원시 시세를 별도 이력으로 저장하지 않는다. 아이템별로 아래 최소 상태만 저장한다.

| 값 | 용도 |
| --- | --- |
| 모니터링 종류와 아이템 키 | 상태 식별. 상자·패키지는 거래소 `kind_id`, 해연은 제작 시트 이름(2026-09-30 결정) |
| 후보 방향(`상승`·`하락`·`없음`) | 현재 연속 확인 중인 방향 |
| 후보 연속 횟수(0~3) | 3회 확인 여부 |
| 마지막 평가 정각 | 회차 연속성·중복 계산 확인 |
| 확정 방향(`상승`·`하락`·`없음`) | 현재 알림 기준 상태 |
| 마지막 알림 방향 | 같은 방향의 중복 알림 방지 |

이 상태는 봇 재시작 후에도 연속 확인과 중복 알림 방지가 이어지도록 SQLite에 보관한다. 최근 세 회차 원본을 보관하지 않아도 후보 방향과 연속 횟수만으로 같은 결과를 얻을 수 있다.

해연 시세는 마지막 시세·기준가·유불리 상태가 모두 제작 시트 이름을 키로 쓰고, 추적 대상도 제작 시트 이름과 정확히 같은 검색 결과로 정한다. 그래서 추세 알림 상태도 해연은 이름을 키로 쓴다. 제작 시트에서 이름이 바뀌면 새 아이템으로 보고 1회부터 다시 센다.

#### 알림 예시

```text
10시  📉⏬  → 하락 후보 1회
11시  📉🔽  → 하락 후보 2회
12시  📉⏬  → 하락 3회 확정, 알림
13시  📉🔽  → 이미 확정된 하락, 알림 없음
```

```text
10시  📉     → 하락 후보 1회
11시  ➖     → 없음 후보 1회
12시  📉     → 하락 후보 1회
```

판정기의 이유 문장(`MarketTrend.Reason`)과 가능성 이모지는 조회 화면에 유지한다. 정각 알림에서는 확정된 방향만 `📈 상승 흐름` 또는 `📉 하락 흐름`으로 간단히 안내한다.

#### 구현 세부 결정 (2026-09-30)

- 정각 알림의 기준가 등락 줄과 상자·패키지 신규 아이템 줄에도 즉시 판정 이모지와 범례를 붙이지 않는다. 알림에서 가능성 이모지는 보이지 않는다.
- 표시 없음 3회로 확정 방향을 해제할 때 마지막 알림 방향도 함께 비운다. 그래야 해제 뒤 같은 방향이 다시 3회 확인될 때 새 흐름으로 알릴 수 있다.
- 이번 응답에 없는 아이템(해연 검색 누락, 상자·패키지의 일시 누락)은 상태를 바꾸지 않는다. 다시 나타나면 정각 연속이 끊긴 것으로 보고 1회부터 센다. 상자·패키지에서 사라짐이 확정되었거나 해연 제작 시트에서 빠진 아이템의 상태는 지운다.
- 배포 직후 상태가 비어 있어도 마지막 시세로 초기 상태를 채우지 않는다. 처음 3시간은 추세 알림이 나가지 않는다.
- 알림 테스트 명령은 저장 시세 중 하나로 만든 확정 흐름 예시 한 줄을 보여준다(실제 확정 아님, DB 변경 없음).

구현 상태:

- 확정 판정은 `Market/MarketTrendAlert.cs`(`MarketTrendAlertEvaluator`, 연속 횟수 `MarketTrendAlertRules.ConfirmRuns`)에 있다. 수집 시각은 `MarketSchedule.HourOf`로 정각 회차로 바꿔 비교한다.
- 상태는 SQLite `market_trend_alert_state`에 모니터링별(`haeyeon`·`box`·`package`)로 저장하고, 각 모니터링의 회차 저장과 같은 트랜잭션에서 통째로 교체한다.
- 알림 구역은 `🔀 상승·하락 흐름`이다. 새 흐름은 `📉 이름 · 가격 · 하락 흐름`, 방향 전환은 `📈 이름 · 가격 · 하락 → 상승 흐름`으로 쓰고, 구역 끝에 3회 연속 확인 안내를 작은 글씨로 붙인다.

## 7. 목표 저장 구조

장기 원시 시세 이력은 없애고 다음 최소 상태만 유지한다(#15에서 적용).

| 데이터 | 보관 여부 | 이유 |
| --- | --- | --- |
| 마지막 정상 시세 | 유지 | 조회 명령, API 장애 시 마지막 정상값, 재시작 복구 |
| 서버별 알림 채널·등락률 | 유지 | 기존 시세 알림 설정 |
| 서버별 기준가·현재가 | 유지 | 기존 임계값 알림을 계속 제공하는 동안 필요 |
| 신규·사라짐 판정 상태 | 유지 | 상자·패키지 알림에 필요 |
| 해연 제작 유불리 상태 | 유지 | 유불리 전환 알림에 필요 |
| 추세 알림 확인 상태 | 유지 | 3회 연속 확인·재시작 복구·중복 알림 방지에 필요한 최소 상태 |
| 정각별 90일 원시 스냅샷 | 제거 대상 | OpenAPI 데이터와 중복되고 현재 기능에 불필요 |
| 변화 문구 이력 | 저장하지 않음 | 매번 최신 OpenAPI 값으로 계산 가능 |
| 7일·90일 자체 차트 데이터 | 저장하지 않음 | 현재 범위 밖이며 OpenAPI 이력과 중복 |

마지막 정상 시세는 아이템별 한 행이지만, 행 단위 upsert가 아니라 **성공한 회차마다 그 모니터링의 행을 통째로 교체**한다. 행 단위로 갱신만 하면 이번 회차 검색에서 빠진 아이템의 옛 가격이 조회 결과와 해연 재료비 계산에 현재 시세처럼 남기 때문이다. 실패한 회차는 교체하지 않아 마지막 정상값이 유지된다.

신규·사라짐 판정 상태(`keyword_market_item_state`)도 현재가를 갖지만, 판정 상태와 조회용 시세는 성격이 달라 합치지 않는다.

개발 단계이므로 기존 이력 표는 별도 검증 기간 없이 정리한다. 봇이 시작할 때 이전 이력 표에서 모니터링마다 마지막 회차만 새 표로 옮기고 이력 표를 삭제한다.

## 8. API 호출량

신규 변화 문구는 기존 `market/prices` 응답의 필드를 사용하므로 호출량을 늘리지 않는다.

현재 예상 자동 호출량:

- 해연: 검색어 5개 × 하루 24회 = 기본 약 120회/일
- 상자·패키지: 각각 검색어 1개 × 하루 24회 = 기본 합계 약 48회/일
- 결과가 100건을 넘으면 페이지당 호출이 추가되며 모니터링 하나당 최대 5페이지

회차가 실패하면 10분 간격으로 최대 3번 재시도하므로, 실패한 회차의 호출량은 최악의 경우 4배가 된다(해연 한 회차 5회 → 최대 20회). 재시도는 실패한 모니터링만 하며 다음 정각을 넘기지 않는다. 모비라이프 클라이언트의 연속 실패 차단이 열려 있으면 재시도해도 실제 요청은 나가지 않는다.

사용자가 조회 명령을 실행할 때 API를 새로 호출하지 않고 마지막 정각 수집 결과를 보여주는 현재 방식을 유지한다.

## 9. 구현 계획

### 1단계: 변화량 수용 (#15와 함께 완료)

- `MobiLifeMarketPrice` DTO에 1시간·24시간·7일 가격 등락과 24시간 매물 증감을 추가
- `MarketPrice` 도메인 모델에 nullable 변화량 추가
- 누락 값과 숫자 범위를 검증
- 기존 테스트 스텁에 새 필드가 있는 응답과 없는 응답을 모두 추가

### 2단계: 순수 판정기 (완료)

- API나 DB를 직접 참조하지 않는 변화 문구 판정기 추가
- 입력: 현재 시세와 임계값
- 출력: 방향, 가능성, 사용자 표시 문구 또는 무표시
- 경계값·반대 방향·매물 부족·매진 테스트 작성

### 3단계: 조회 명령 표시 (완료, `총해연재료` 제외)

- 해연·상자·패키지 조회 결과에 같은 판정기를 적용
- 긴 목록에서는 짧은 아이콘·문구만 사용
- 기존 가격, 매물 수, 매진·적음 표시는 유지
- 모든 결과에 `모비라이프 제공` 유지

### 4단계: 저장 구조 축소 (#15에서 완료)

- 마지막 시세 전용 저장 구조 추가(회차 단위 교체)
- 조회와 모니터링의 읽기 경로를 새 구조로 전환
- 기존 기준가·신규·사라짐·제작 유불리 상태가 정상 복구되는지 확인
- 전환 확인 후 90일 원시 이력 적재 중단 및 기존 테이블 정리

### 5단계: 추세 알림 안정화 (구현)

- 즉시 판정과 알림용 확정 판정을 분리
- 아이템별 후보 방향·연속 횟수·마지막 평가 정각·확정 방향·마지막 알림 방향 저장
- 같은 상승·하락 방향이 3회 연속 확인될 때만 확정 알림
- 가능성 높음·낮음 변화와 표시 없음 변화는 알림에서 제외
- 표시 없음 3회 연속이면 내부 확정 방향만 해제
- 재시도·실패·정각 누락·봇 재시작 시 연속성 검증
- 최근 3시간 원시 시세나 별도 추세 이력은 저장하지 않음

## 10. 검증 시나리오

- 1시간·24시간 가격이 모두 하락하고 매물이 증가하면 `하락 중 · 하락 가능성 높음`
- 1시간·24시간 가격이 모두 하락하고 매물이 감소하면 `하락 중 · 하락 가능성 낮음`
- 1시간·24시간 가격이 모두 상승하고 매물이 감소하면 `상승 중 · 상승 가능성 높음`
- 1시간·24시간 가격이 모두 상승하고 매물이 증가하면 `상승 중 · 상승 가능성 낮음`
- 가격 방향은 같고 매물 변화가 0이면 방향만 표시
- 1시간과 24시간 방향이 다르면 표시하지 않음
- 등락이 임계값 미만이면 표시하지 않음
- 매진·매물 3개 미만·필드 누락이면 표시하지 않음
- 새 문구를 추가해도 정각 API 호출 횟수가 증가하지 않음
- 봇 재시작 후 마지막 정상 시세와 기존 알림 설정이 복구됨
- 외부 API 장애 시 마지막 정상 시세의 수집 시각을 숨기지 않음
- 상승 또는 하락이 3회 연속 확인되기 전에는 추세 알림을 보내지 않음
- 가능성 높음·낮음만 바뀌면 알림을 보내지 않음
- 표시 없음이 생기거나 사라져도 알림을 보내지 않음
- 표시 없음 3회 연속이면 내부 확정 방향만 해제
- 같은 확정 방향을 반복해서 알리지 않음
- 반대 방향 3회 연속이면 방향 전환 알림을 보냄
- 같은 정각 회차의 재시도 성공은 연속 횟수를 한 번만 올림
- 정각 성공 회차가 누락되면 다음 성공 회차는 후보 1회부터 다시 시작
- 봇 재시작 후 후보·확정·마지막 알림 상태가 복구됨
- 알림 안정화를 위해 최근 3시간 원시 시세가 새로 적재되지 않음

## 11. 완료 기준

- 사용자가 가격 숫자를 해석하지 않아도 현재 방향을 한눈에 이해할 수 있다.
- 불확실한 데이터에는 아무 판정도 붙지 않는다.

- 추세 알림은 3회 연속 확인된 방향 전환만 안내하고 가능성 단계 변화로 반복되지 않는다.
- 알림 안정화 상태는 최소 필드만 저장하며 최근 3시간 원시 이력을 만들지 않는다.
- 모든 관련 문서와 도움말이 실제 동작과 일치한다.
