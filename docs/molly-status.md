# 몰리 상태 점검(`/몰리상태`) 기획서

> 문서 상태: 구현 완료(1차)  
> 최종 갱신: 2026-10-29

## 기능명

`/몰리상태` — 운영자용 알림 수집·전송 상태 점검

## 분류

편의(운영 보조)

## 해결하려는 문제

알림이 오지 않을 때 운영자는 다음 중 무엇인지 구분하기 어렵다.

- 새 글·시세 변화가 없어 보낼 알림이 없음
- 몰리의 수집이 실패했거나 늦어짐
- 이 서버에 알림이 등록되지 않음
- 등록 채널이 지워졌거나 몰리가 볼 수 없거나 권한이 부족함
- 수집은 정상인데 이 서버로 전송만 실패함

## Discord에서 제공하는 이점

봇 로그나 DB에 접근하지 않고도, 서버 운영자가 Discord 안에서 수집 상태(봇 공통)와 이 서버의 설정·전송 상태를 나눠 확인한다.

## 핵심 사용자 흐름

1. 서버 관리 권한이 있는 운영자가 `/몰리상태`를 실행한다(옵션 없음).
2. 몰리는 응답을 미루고(본인 전용) 저장된 상태와 이 서버의 설정만 읽는다.
3. 전체 요약(정상·일부 확인 필요·준비 중)과 원인, 이번 실행 시작 시각을 본다.
4. 공홈·시세 수집 상태, 이 서버의 알림 설정(채널·권한·마감 시간·등락률), 전송 상태를 본다.
5. `[확인할 내용]`의 안내에 따라 채널 권한을 고치거나 다시 등록한다(이 명령은 설정을 바꾸지 않는다).

## 사용하는 기존 데이터

| 대상 | 수집 상태 | 서버 설정 | 전송 상태 |
| --- | --- | --- | --- |
| 공지·업데이트·이벤트·에린 노트 | `molly_job_status`(`news:{board}`) + `official_news_board_states.last_success_at_utc`(병합) | `official_news_subscriptions` | `official_news_deliveries`에서 도출(새로 저장하지 않음) |
| 이벤트 마감 | `molly_job_status`(`event_list`) + 메모리의 마지막 목록(`MobiEventService.LastSnapshot`) | `event_expire_alert_settings`(채널·몇 시간 전) | `molly_alert_delivery_status`(`event_expire`) |
| 해연·상자·패키지 시세 | `molly_job_status`(`market:{id}`) + 각 시세 저장소의 마지막 수집 시각(병합) | 각 시세 채널 표(채널·등락률) | `molly_alert_delivery_status`(`market:{id}`) |

- 이벤트 게시판 새 글 감지(`OfficialNewsCollector`, `/News/Events` 목록 첫 페이지)와 이벤트 마감 판정용 진행 중 이벤트 목록(`MobiEventService`, `headlineId=2501` 전체 페이지)은 다른 작업이라 따로 추적한다.
- 기존 저장소가 남기는 마지막 성공 시각은 조회할 때 병합해, 이 기능 배포 전 기록이나 상태 기록이 실패한 회차도 반영한다.

## 새로 필요한 데이터

| 표 | 키 | 내용 | 보존 |
| --- | --- | --- | --- |
| `molly_job_status` | 작업 ID | 마지막 시도 시각, 마지막 성공 시각, 최근 결과, 오류 분류, 연속 실패 횟수 | 작업당 1행 덮어쓰기 |
| `molly_alert_delivery_status` | (서버, 알림 종류) | 마지막 전송 성공 시각·채널, 마지막 전송 실패 시각·채널·오류 분류 | 서버·종류당 1행 덮어쓰기 |

- 이번 실행 시작 시각과 진행 중 작업(시작 시각)은 메모리에만 둬 재시작하면 초기화된다.
- 시각은 모두 그 시도를 **시작한** 시각이며, 더 늦게 시작한 시도의 결과만 반영한다(재시도·중첩 시 오래된 결과가 최신을 덮지 않음).
- 오류는 분류 코드만 저장한다. 원문 메시지·URL·키·스택은 저장·표시하지 않고 기존 로그에만 남긴다.
- 상태 기록 실패는 수집·알림 작업을 실패시키지 않는다. 로그를 남기고 이번 실행의 실패 횟수를 세어 `/몰리상태`에 `상태 기록 실패`로 드러낸다.
- 새 표만 만들고 기존 표·데이터는 바꾸지 않는다(`CREATE TABLE IF NOT EXISTS`).

## API 사용량

- 갱신당·하루 추가 호출: 0회. 조회는 DB·메모리·Discord 캐시만 읽는다.
- 채널 확인은 Discord 게이트웨이 캐시를 먼저 쓰고, 캐시에 없는 채널만 한 번 REST로 확인한다(명령 1회당 최대 알림 종류 수, 8회).
- 길드·사용자 수가 늘어도 수집 호출은 늘지 않는다.

## 수집 상태 판정

| 상태 | 조건 |
| --- | --- |
| 🟢 정상 | 마지막 시도 성공, 다음 확인 기한 이내. 새 글·시세 변화가 없어도 정상 |
| ⏳ 준비 중 | 이번 실행에서 아직 완료된 시도가 없고(대기·진행 중), 첫 시도 허용 시간 이내. 과거 성공 시각이 있으면 함께 표시 |
| 🟡 최근 확인 실패 | 마지막 시도 실패, 사용할 이전 정상 데이터 있음 |
| 🟠 확인 지연 | 진행 중인 시도 없이 다음 확인 기한을 넘김, 진행 중인 시도가 최대 진행 시간을 넘김, 또는 첫 시도 허용 시간이 지났는데 기록이 없음 |
| 🔴 수집 불가 | 마지막 시도 실패, 사용할 정상 데이터 없음 |
| ⚪ 사용 안 함 | 설정으로 끔(의도적) 또는 필수 설정 누락 |

겹칠 때 우선순위: 사용 안 함 → 진행 시간 초과(확인 지연) → 준비 중 → 수집 불가 → 확인 지연 → 최근 확인 실패 → 정상.

마지막 시도가 성공하면 연속 실패 횟수가 0이 되고 이전 오류는 표시하지 않는다.

### 작업별 기한(기존 주기 값을 그대로 사용)

| 작업 | 다음 확인 예정 | 허용 지연 | 최대 진행 | 첫 시도 허용 |
| --- | --- | --- | --- | --- |
| 공식 소식 게시판 | 마지막 시도 + `OfficialNewsCollector.Interval`(10분) | Interval(10분) → 마지막 시도 후 20분 | Interval | Interval |
| 이벤트 마감용 목록 | 마지막 시도 + `MobiEventExpireAlert.UpdateInterval`(10분) | UpdateInterval → 20분 | UpdateInterval | UpdateInterval |
| 해연·상자·패키지 시세 | 마지막 시도 다음 정각(`MarketSchedule.NextHourUtc`) | `MarketSchedule.RetryDelay`(10분) → 정각 뒤 10분 | RetryDelay | RetryDelay |

### 사용 안 함

| 대상 | 의도적 비활성화 | 필수 설정 누락 |
| --- | --- | --- |
| 공식 소식 | `OfficialNews:Enabled=false` | — |
| 이벤트 마감용 목록 | 마감 알림을 켠 서버가 하나도 없음(주기 갱신 안 함) | — |
| 시세 | `MobiLife:Enabled=false` | 모비라이프 API 키 없음 |

필수 설정 누락은 이 서버에 관련 알림이 등록돼 있을 때만 전체 요약의 원인으로 올린다.

## 서버별 채널·권한 확인

- 미등록 / `#채널 · 설정 정상` / `등록 채널을 확인할 수 없음` / `#채널 · 메시지를 보낼 수 없는 채널` / `#채널 · ○○ 권한 필요`.
- 실제 전송 방식 기준 필요 권한: 공식 소식은 채널 보기·메시지 보내기·링크 첨부·파일 첨부(썸네일 없는 글의 기본 이미지), 이벤트 마감·시세는 채널 보기·메시지 보내기·링크 첨부. 스레드는 부모 채널 권한으로 보고 메시지 보내기 대신 스레드에서 메시지 보내기를 본다.
- `설정 정상`은 채널·권한 확인 결과이며 실제 전송 성공이 아니다. 같은 문구의 알림은 한 줄로 묶고(예: `공지·업데이트 → #공식소식 · 설정 정상`), 마감 시간·등락률은 각 줄에 그대로 보여준다.
- 미등록은 오류로 보지 않는다.

## 전송 상태

- 현재 등록 채널로 보낸 기록만 본다. 채널을 바꾸거나 해제하면 이전 채널의 실패는 현재 설정의 문제로 표시하지 않는다.
- 공식 소식·시세는 현재 설정을 등록(재등록 포함)한 시각보다 앞선 실패도 이전 설정의 결과로 보고 표시하지 않는다. 이벤트 마감 설정에는 등록 시각이 없어 채널로만 비교한다.
- 마지막 실패가 마지막 성공보다 늦으면 `해결되지 않은 전송 실패`다. 같은 작업의 재시도 성공이나 이후 같은 채널로의 정상 전송으로 해제된다. `/몰리상태`의 채널·권한 확인 성공만으로는 해제하지 않는다.
- 보낼 소식이 없어 기록이 없으면 `전송 기록 없음`(오류 아님).
- 공식 소식: 영구 실패(`failed`)와 재시도 대기 중인 실패(시도 1회 이상, Discord 연결 대기 제외)를 실패로 본다.
- 이벤트 마감·시세: 전송 지점에서 성공·실패(채널 없음·메시지 채널 아님·Discord 403/404 등)를 기록한다. `/…알림 작업:테스트`로 실행 채널에 보내는 예시는 기록하지 않는다(이벤트 마감 테스트는 실제 알림 경로라 기록됨).

## 응답

- 본인 전용, 서버 관리 권한 필요(`DefaultMemberPermissions(ManageGuild)` + 실행 시 재확인), DM 불가.
- 시각은 KST. 확인 시각과 날짜가 다르면 날짜도 붙이고, 기록이 없으면 `기록 없음`.
- 한 항목을 읽지 못해도 나머지는 표시한다(`상태를 불러오지 못함`). Embed 설명 3,800자 단위로 나눠 여러 본인 전용 메시지로 보낸다.

## 최소 구현 범위

위 대상의 수집·설정·전송 상태 표시, 상태 영속화, 자동 테스트.

## 제외 범위

자동 장애 알림, 외부 생존 감시, 강제 재수집·재시작 버튼, 테스트 메시지 전송, 알림 설정 변경, 장기 상태 이력·통계, 점검 종료 알림·랭킹·배틀·퀴즈·출석의 상태 계측.

## 한계

- 봇 자체가 꺼져 있거나 Discord 연결이 끊기면 이 명령도 응답할 수 없다(도움말에 안내).
- 공식 소식 실패 시각은 발송 작업을 마지막으로 갱신한 시각이라, 재시도 대기 중인 작업은 다시 가져갈 때 시각이 바뀐다.
- 이벤트 마감 알림은 채널을 찾지 못하면 기존처럼 그 회차를 건너뛴다(재시도 없음). 상태에는 실패로 남는다.

## 수동 검증 절차(테스트 서버 `Discord__GuildId`)

1. 배포 후 바로 `/몰리상태`: 전체 요약이 `준비 중` 또는 `정상`, 이번 실행 시작 시각 표시, 공홈 네 게시판이 수 분 안에 🟢로 바뀌는지 본다.
2. 관리 권한 없는 계정으로 실행: 권한 안내만 본인에게 보이는지(명령 목록에 기본으로 보이지 않음).
3. 테스트 채널에 `/공지알림 작업:등록` 후 실행: `공지 → #채널 · 설정 정상`, 전송 상태 `전송 기록 없음`.
4. 테스트 채널에서 몰리의 `링크 첨부` 권한을 끄고 실행: `링크 첨부 권한 필요`와 원인 표시. 권한을 되돌린다.
5. 테스트 채널에 시세 알림을 등록한 뒤 채널을 지우고 실행: `등록 채널을 확인할 수 없음`.
6. 로컬에서 `MobiLife__ApiKey` 없이 실행: 시세가 `사용 안 함 — 모비라이프 API 키가 설정되지 않음 (필수 설정 누락)`.

## 성공 기준

- 알림 문의 때 운영자가 원인(수집·설정·전송)을 스스로 구분한 비율
- 상태 표시와 실제 로그의 불일치 0건
- 상태 조회로 인한 외부 API 호출 0회
