# 새 클래스 배틀 데이터 반영 절차

> 전제: 사용자가 구글 시트의 `클래스`·`스킬`(그리고 있다면 `패시브스킬`) 탭에 새 클래스의 원본 데이터(클래스 설명, 스킬1~5·궁극기, 패시브1~6, 각 스킬·패시브의 설명과 `기타` 필드에 적힌 인게임 캡처 수치)를 이미 입력해둔 상태에서 시작한다. `클래스`·`스킬`·`패시브스킬`은 원본 보존 영역이므로 이 절차에서 건드리지 않는다.

패시브(클래스가 상시로 갖는 능력, 행동으로 선택되지 않음)를 반영할 때는 이 문서의 스킬 절차와 같은 흐름을 따르되, `배틀패시브`·`배틀패시브효과`에 입력하고 8.20(패시브 스킬)의 발동시점 어휘(`전투시작`·`자원획득시`·`자원최대치도달시`·`자원소진시`·`브레이크발생시`·`스킬사용완료시`·`치명타적중시`·`치명타미적중시`·`피격시`·`회복적용시`)와 신규 상태효과유형(`회복량증가`·`멀티히트피해증가`·`치명타피해증가`·`받는기본공격피해감소`·`받는치명타확률감소`·`추가타확률증가`)을 우선 재사용한다. "중첩당 +N%"는 `배틀상태효과.중첩자원ID`로 자원 보유량에 비례시키고, "다음 X 시 강화"는 표식 자원 + `스킬사용완료시` 조건 행 + 소모 행 조합(검술사 질풍태세, 석궁사수 엑스트라 액션)으로 표현한다. 패시브가 요구하는 반응이 이 어휘로 표현되지 않으면(예: 주기적 발동, 대상 수 스케일링) 8.20.4의 음유시인·댄서·검술사·석궁사수 사례처럼 근사하고 `비고`에 원본과의 차이를 남긴다.

Codex와 Claude Code는 대화가 끝나면 이번 세션의 판단 과정을 기억하지 못한다. 다음에 새 클래스를 반영할 때도 이 문서의 순서를 그대로 따르면, 매번 처음부터 설계를 다시 고민하지 않아도 된다.

## 1. 원본 데이터 읽기

- 공개 CSV export로 `클래스`, `스킬` 시트를 읽는다. 인증이 필요 없다.
  ```
  https://docs.google.com/spreadsheets/d/{spreadsheetId}/gviz/tq?tqx=out:csv&sheet={시트이름}
  ```
- 새 클래스의 `스킬1~스킬5`, `궁극기` ID를 확인하고, `스킬.부모스킬ID`로 연결된 파생 스킬도 함께 모은다.
- 각 스킬의 `설명`과 `기타`(대미지, 재사용 대기 시간, 확률, 사거리·범위 등 화면 표시 수치)를 빠짐없이 옮겨 적는다. 브라우저로 직접 열 필요는 없다.

## 2. 기존 배틀 데이터 관례 파악

- `배틀스킬`, `배틀스킬효과`, `배틀스킬파생`, `배틀자원`, `배틀상태효과`, `배틀규칙`도 같은 방식으로 CSV를 읽어, 이미 구현된 클래스(음유시인·댄서·검술사)가 유사한 메커니즘을 어떻게 표현했는지 대조한다.
- `Battle/BattleEngine.cs`와 `Battle/BattleCatalog.cs`를 읽고 어떤 효과유형·조건유형·발동방식이 **실제로 동작하는지** 확인한다. 시트 헤더나 문서에는 있어도 엔진이 처리하지 않는 조합이 있을 수 있다. 알려진 예:
  - `배틀스킬효과`의 `조건유형=상태효과보유`는 문서와 시트에는 있지만 `CanApplyEffect`가 처리하지 않는다(`자원보유`, `분류자원미보유`만 동작). `배틀스킬파생`의 `상태효과보유`는 동작한다.
  - `배틀스킬.자원유형="궁극기 게이지"`는 대응하는 `배틀자원` 정의가 없어 비용 검사가 항상 통과된다(모든 궁극기 공통 문제).
  - `배틀스킬효과.계수기준`/`계수` 컬럼은 더 이상 계산에 쓰이지 않는다. 캡처에 기준 공격력이 없으면 `고정값`에 화면 표시 수치를 그대로 넣고 `배틀규칙.fixed_damage_scale`로 환산한다(댄서·검술사 패턴). 기준 공격력이 있으면 음유시인처럼 계수를 역산해 `고정값=0`으로 두고 `배틀규칙.skill_damage_min/max_multiplier`에 맡길 수도 있다.

## 3. 메커니즘 설계

- 새 자원(`배틀자원`)·상태(`배틀상태효과`) ID는 `snake_case`로 짓고, 클래스 약어 접두사를 붙여 다른 클래스와 충돌하지 않게 한다(`sw_`, `bard_`, `dance_` 등).
- "마지막 사용 기술" 같은 선택형 분기는 상호배타 자원 + `배틀스킬파생`의 `발동방식=대체` 조합으로 표현한다(바즈 테일, 비검 패턴).
- 원본 게임 화면 캡처는 클래스마다 서로 다른 기준 공격력의 캐릭터에서 얻었을 수 있다. 절대값을 그대로 옮기지 말고, **같은 클래스 안에서 스킬 간 배율**을 먼저 맞춘 뒤 다른 클래스의 기본기 배율과도 비슷한 범위(대략 1~3배)에 들어오는지 확인한다. 궁극기라고 해서 기본기보다 5배 이상 세게 잡지 않는다 — 기존 클래스의 궁극기 배율(`ultimate_damage_multiplier` 기준 2.7배 수준)을 참고한다.
- 원본 설명에 상대방 상태를 조건으로 거는 효과(예: "상대가 브레이크 상태일 때")가 있으면, 2단계에서 확인한 엔진 한계 때문에 지금은 확률로 단순화해야 할 수 있다. 이런 단순화는 반드시 `비고`에 원본 조건을 남긴다.

## 4. 구글 시트 입력

- 셀을 Tab으로 이동하며 하나씩 `type`하는 방식은 드문드문 키 입력이 누락되는 경쟁 상태가 있어 신뢰할 수 없다(관찰된 사례: 첫 단어가 사라지거나 셀 전체가 비는 현상).
- 안정적인 방법: `javascript_tool`로 `navigator.clipboard.writeText(tsv)`를 실행해 탭·줄바꿈으로 구분한 표를 클립보드에 쓴 다음, **Name Box가 아니라 시작 셀을 화면에서 직접 클릭**하고 `cmd+v`로 붙여넣는다.
- 개별 셀 하나만 고칠 때는 Name Box로 정확한 주소(`G95`)를 입력해 이동한 뒤 바로 타이핑해도 안정적이다. 다만 연속으로 여러 셀을 고칠 때 `Return` 이후 화면이 스크롤되면서 다음 클릭 좌표가 어긋날 수 있으므로, 좌표를 재사용하지 말고 매번 Name Box로 다시 이동한다.
- 입력 직후에는 스크린샷만 믿지 말고 공개 CSV export를 다시 읽어 실제로 저장된 값을 확인한다.
- 조건연산자 `=`처럼 `=`로 시작하는 셀은 붙여넣을 때 수식으로 해석될 수 있다. 자원은 음수가 되지 않으므로 "0과 같음"은 `<=`·`0`으로 쓴다. 셀 첫 글자가 큰따옴표인 값도 TSV 붙여넣기에서 따옴표가 사라지므로 피한다.
- 한글을 `type`으로 직접 입력하면 IME 조합 때문에 앞 글자가 빠질 수 있다(관찰 사례: "중첩자원ID"가 "ID"로 저장). 한 셀이라도 한글은 클립보드 붙여넣기를 쓴다.
- gviz CSV의 줄 번호는 시트 행 번호와 다를 수 있다(여러 줄 셀 등). 기존 행을 고칠 때는 Name Box로 근처로 이동해 화면에서 ID를 확인한 뒤 수정한다.

## 5. 오프라인 검증

- `tests/Molly.DataTests`는 CI에 포함되지 않는 두 인자를 지원한다.
  - `dotnet run --project tests/Molly.DataTests/Molly.DataTests.csproj -- --battle-live` : 실시간 시트를 읽어 `BattleCatalog.Parse` 검증만 수행.
  - `dotnet run --project tests/Molly.DataTests/Molly.DataTests.csproj -- --battle-balance [반복횟수]` : 배틀 준비된 모든 클래스를 동일 전투력으로 맞대결시켜 승률·스킬 사용 빈도·스킬을 사용한 전투의 승률을 뽑는다.
  - `... -- --battle-balance [반복횟수] [CSV폴더]` : 폴더를 주면 실시간 시트 대신 `{시트이름}.csv` 13개로 시뮬레이션한다. 시트에 입력하기 전에 공개 CSV를 내려받아 새 행을 붙인 로컬 사본으로 수치를 먼저 조정할 때 쓴다.
- 새 클래스가 위 검증을 통과하는지, 그리고 도입한 모든 기본 스킬·파생이 시뮬레이션에서 최소 1회 이상 실제로 발동하는지 확인한다.
- 한쪽으로 크게(대략 70% 이상) 치우친 승률이 나오면 원본 배율이 다른 클래스보다 과도하게 큰 스킬(대개 궁극기나 강화 파생)의 `고정값`을 조정한다. 완벽한 50:50을 요구하지 않는다 — 정밀한 밸런스는 이후 대규모(10,000회 단위) 시뮬레이션으로 조정한다는 것이 문서의 방침이다(`docs/battle/README.md` 10.3, 17장 P1 참고).

## 6. 문서·테스트 갱신

- `docs/battle/README.md`의 "8.x `{클래스}` 배틀 데이터 기준" 절 패턴을 따라 새 섹션을 추가하고, 뒤따르는 하위 절 번호를 한 칸씩 민다. 상호 참조(예: "8.12 검증을 통과한")도 함께 갱신한다.
- 새 클래스가 도입한 고유 메커니즘(조건부 대체 파생, 자원 게이팅 등)을 검증하는 합성 테스트를 `tests/Molly.DataTests/Program.cs`에 추가한다. 기존 코드의 `battleRules`, `Check`, `FixedBattleRandom` 패턴을 그대로 재사용한다.
- `bash scripts/verify.sh`로 빌드·오프라인 테스트·publish·필수 에셋을 모두 확인한다.

## 7. 원본 대비 gap 정리

새 클래스 반영이 끝나면, 입력한 배틀 데이터를 원본 설명·`기타` 필드와 다시 한 줄씩 대조해 다음 세 가지로 분류해 사용자에게 보고한다. 구현에 들어가기 전에 먼저 정리해서 공유한다.

- **단순화한 부분**: 원본에 있었지만 배틀 밸런스·연출을 위해 의도적으로 줄이거나 생략한 수치·효과.
- **엔진이 지원하지 않아 못 넣은 부분**: 2단계에서 확인한 엔진 한계 때문에 원본 그대로 구현하지 못한 항목. 다른 클래스에도 영향을 주는지(공통 버그·공통 미구현) 함께 확인한다.
- **원본 자체가 모호해서 확인이 필요한 부분**: 캡처 수치가 누락되었거나 설명과 수치가 맞지 않아 추측해야 하는 항목.
