# 새 클래스 배틀 데이터 반영 절차

> 전제: 사용자가 구글 시트의 `클래스`·`스킬`(그리고 있다면 `패시브스킬`) 탭에 새 클래스의 원본 데이터(클래스 설명, 스킬1~5·궁극기, 패시브1~6, 각 스킬·패시브의 설명과 `기타` 필드에 적힌 인게임 캡처 수치)를 이미 입력해둔 상태에서 시작한다. `클래스`·`스킬`·`패시브스킬`은 원본 보존 영역이므로 이 절차에서 건드리지 않는다.

패시브(클래스가 상시로 갖는 능력, 행동으로 선택되지 않음)는 스킬과 같은 1~7단계 흐름으로 함께 반영한다. 패시브에만 해당하는 번역 규칙·입력 패턴·검증은 8장을 따른다.

Codex와 Claude Code는 대화가 끝나면 이번 세션의 판단 과정을 기억하지 못한다. 다음에 새 클래스를 반영할 때도 이 문서의 순서를 그대로 따르면, 매번 처음부터 설계를 다시 고민하지 않아도 된다.

## 1. 원본 데이터 읽기

- 공개 CSV export로 `클래스`, `스킬` 시트를 읽는다. 인증이 필요 없다.
  ```
  https://docs.google.com/spreadsheets/d/{spreadsheetId}/gviz/tq?tqx=out:csv&sheet={시트이름}
  ```
- 새 클래스의 `스킬1~스킬5`, `궁극기` ID를 확인하고, `스킬.부모스킬ID`로 연결된 파생 스킬도 함께 모은다.
- 궁극기 `설명`의 『』 대사는 `배틀스킬.궁극기문구`에 그대로 옮긴다(궁극기 사용 시 큰 글씨 제목 아래 작은 글씨로 출력).
- 각 스킬의 `설명`과 `기타`(대미지, 재사용 대기 시간, 확률, 사거리·범위 등 화면 표시 수치)를 빠짐없이 옮겨 적는다. 브라우저로 직접 열 필요는 없다.

## 2. 기존 배틀 데이터 관례 파악

- `배틀스킬`, `배틀스킬효과`, `배틀스킬파생`, `배틀자원`, `배틀상태효과`, `배틀규칙`도 같은 방식으로 CSV를 읽어, 이미 구현된 클래스(음유시인·댄서·검술사·석궁사수·힐러·도적·빙결술사·화염술사·전사)가 유사한 메커니즘을 어떻게 표현했는지 대조한다.
- `Battle/BattleEngine.cs`와 `Battle/BattleCatalog.cs`를 읽고 어떤 효과유형·조건유형·발동방식이 **실제로 동작하는지** 확인한다. 시트 헤더나 문서에는 있어도 엔진이 처리하지 않는 조합이 있을 수 있다. 알려진 예:
  - `배틀스킬효과`의 `조건유형=상태효과보유`는 문서와 시트에는 있지만 `CanApplyEffect`가 처리하지 않는다(`자원보유`, `분류자원미보유`만 동작). `배틀스킬파생`의 `상태효과보유`는 동작한다.
  - `배틀스킬.자원유형="궁극기 게이지"`는 대응하는 `배틀자원` 정의가 없어 비용 검사가 항상 통과된다(모든 궁극기 공통 문제).
  - `배틀스킬효과.계수기준`/`계수` 컬럼은 더 이상 계산에 쓰이지 않는다. 캡처에 기준 공격력이 없으면 `고정값`에 화면 표시 수치를 그대로 넣고 `배틀규칙.fixed_damage_scale`로 환산한다(댄서·검술사 패턴). 기준 공격력이 있으면 음유시인처럼 계수를 역산해 `고정값=0`으로 두고 `배틀규칙.skill_damage_min/max_multiplier`에 맡길 수도 있다.

## 3. 메커니즘 설계

- 새 자원(`배틀자원`)·상태(`배틀상태효과`) ID는 `snake_case`로 짓고, 클래스 약어 접두사를 붙여 다른 클래스와 충돌하지 않게 한다(`sw_`, `bard_`, `dance_` 등).
- "마지막 사용 기술" 같은 선택형 분기는 상호배타 자원 + `배틀스킬파생`의 `발동방식=대체` 조합으로 표현한다(바즈 테일, 비검 패턴).
- 원본 게임 화면 캡처는 클래스마다 서로 다른 기준 공격력의 캐릭터에서 얻었을 수 있다. 절대값을 그대로 옮기지 말고, **같은 클래스 안에서 스킬 간 배율**을 먼저 맞춘 뒤 다른 클래스의 기본기 배율과도 비슷한 범위(대략 1~3배)에 들어오는지 확인한다. 궁극기라고 해서 기본기보다 5배 이상 세게 잡지 않는다 — 기존 클래스의 궁극기 배율(`ultimate_damage_multiplier` 기준 2.7배 수준)을 참고한다.
- 원본 스킬 설명의 "이럴 때 쓰면 좋다"(체력이 낮을 때, 상대가 브레이크일 때, 자원이 모였을 때 등)나 연계 스킬의 발산 시점은 `배틀스킬AI` 행으로 표현한다. 가산 크기는 `docs/battle/README.md` 8.8.1의 가중치 가이드라인(주 조건 +4~5, 대부분 참인 조건 +1~2, 억제 -1~-2)을 따르고, `--battle-balance`의 "배틀스킬AI 조건 충족 시 선택률"이 목표(약 50%) 근처인지 확인한다. `재사용 시` 파생은 더 이상 자동으로 먼저 나가지 않으므로, 바로 이어 써야 하는 재사용(예: 나이트메어)에는 부모 스킬에 AI 가산을 둔다.
- 받는 피해 감소·보호막이 많은 탱커 클래스(빙결술사)는 원본 수치 그대로면 딜이 비슷해도 승률이 크게 치우친다(빙결술사 원본 그대로 82%). 요소를 하나씩 빼 보는 로컬 실험(`--battle-balance`에 CSV 폴더)으로 가장 큰 요인을 찾고, 탱커 성격이 남도록 "피해 보정 배율 + 상시 감소 완화"를 함께 조정한다(빙결술사: 피해 ×0.6, 상시 감소 절반). 행 비고와 README 클래스 절에 원본 수치와 조정 근거를 남긴다.
- 스킬 비용이 "최소 N 이상, 사용 시 전부 소모"이고 소모량에 비례해 강해지면(화염술사 익스플로전) `배틀스킬.자원소모=N`으로 후보를 거르고, 효과 행에서 남은 양을 `조건부피해증가` 수치참조로 곱한 뒤 `자원소모 전부`한다. 비용을 먼저 내므로 피해 고정값에 N의 몫을 미리 곱해 둔다(열기 1당 2%면 고정값 ×2, 남은 열기 1당 +1%).
- 보정 배율은 결과에 매우 민감하다(화염술사 0.5배 44% → 0.55배 54% → 0.6배 61%). 로컬 사본으로 0.05 단위를 비교한 뒤 3,000회로 확정한다. 다단 스킬은 타격마다 방어력(100)이 빠지므로 배율을 너무 낮추면 급격히 약해진다.
- 원본 설명에 상대방 상태를 조건으로 거는 효과(예: "상대가 브레이크 상태일 때")가 있으면, 2단계에서 확인한 엔진 한계 때문에 지금은 확률로 단순화해야 할 수 있다. 이런 단순화는 반드시 `비고`에 원본 조건을 남긴다.

## 4. 구글 시트 입력

- 셀을 Tab으로 이동하며 하나씩 `type`하는 방식은 드문드문 키 입력이 누락되는 경쟁 상태가 있어 신뢰할 수 없다(관찰된 사례: 첫 단어가 사라지거나 셀 전체가 비는 현상).
- 안정적인 방법: `javascript_tool`로 `navigator.clipboard.writeText(tsv)`를 실행해 탭·줄바꿈으로 구분한 표를 클립보드에 쓴 다음, **Name Box가 아니라 시작 셀을 화면에서 직접 클릭**하고 `cmd+v`로 붙여넣는다.
- 개별 셀 하나만 고칠 때는 Name Box로 정확한 주소(`G95`)를 입력해 이동한 뒤 바로 타이핑해도 안정적이다. 다만 연속으로 여러 셀을 고칠 때 `Return` 이후 화면이 스크롤되면서 다음 클릭 좌표가 어긋날 수 있으므로, 좌표를 재사용하지 말고 매번 Name Box로 다시 이동한다.
- 입력 직후에는 스크린샷만 믿지 말고 공개 CSV export를 다시 읽어 실제로 저장된 값을 확인한다. 봇은 gviz CSV(`gviz/tq?tqx=out:csv&sheet=`)로 읽는데, gviz는 열 타입을 추론해 숫자 열에 섞인 문자열 셀(`전부`, `1|0.1` 등)을 빈 값으로 내보낸다. 새 값을 넣은 뒤에는 `--battle-live`로 gviz 경로 파싱도 확인한다.
- 조건연산자 `=`처럼 `=`로 시작하는 셀은 붙여넣을 때 수식으로 해석될 수 있다. 자원은 음수가 되지 않으므로 "0과 같음"은 `<=`·`0`으로 쓴다. 셀 첫 글자가 큰따옴표인 값도 TSV 붙여넣기에서 따옴표가 사라지므로 피한다.
- 셀 하나에 값을 붙여넣을 때 클립보드 끝에 탭을 붙이면 옆 열까지 붙여넣어지고, 시트 마지막 열 오른쪽이면 빈 열이 새로 생긴다. gviz CSV는 이 빈 열을 헤더가 빈 열로 내보내 로더가 "헤더가 비어 있거나 중복" 오류로 배틀 데이터 전체를 거부한다(2026-09-26 배틀상태효과 `대상자원ID` 열 추가 때 발생). 새 열 헤더는 데이터 행의 새 열 값과 함께 붙여넣고, 입력 후 반드시 `--battle-live`로 확인한다. 빈 열이 생기면 Name Box로 `L:L`처럼 열을 선택해 `cmd+alt+-`로 삭제한다.
- 탭을 바꾼(navigate) 직후에는 그리드 클릭이 선택되지 않고 `cmd+j`도 Name Box로 가지 않는 경우가 잦다. 이때 이어서 셀 주소를 `type`하면 선택된 셀에 그 주소가 입력될 수 있으므로, `cmd+j` 뒤 `document.activeElement.id === 't-name-box'`를 확인하고 아니면 배치를 멈춘다. 이동 뒤에는 `#t-name-box` 값이 목표 셀인지 확인한 다음 붙여넣는다(2026-09-27 도적 입력에서 정착).
- 한글을 `type`으로 직접 입력하면 IME 조합 때문에 앞 글자가 빠질 수 있다(관찰 사례: "중첩자원ID"가 "ID"로 저장). 한 셀이라도 한글은 클립보드 붙여넣기를 쓴다.
- gviz CSV의 줄 번호는 시트 행 번호와 다를 수 있다(여러 줄 셀 등). 기존 행을 고칠 때는 Name Box로 근처로 이동해 화면에서 ID를 확인한 뒤 수정한다.

- **여러 셀 붙여넣기는 macOS 시스템 클립보드(`pbcopy`)가 가장 확실하다**(2026-09-27 빙결술사 반영에서 정착). 로컬에서 TSV 파일을 만들어 `pbcopy < 파일.tsv`로 클립보드에 넣은 뒤, 브라우저에서 Name Box로 시작 셀로 이동하고 `cmd+v`만 누른다. 한글 페이로드를 도구 호출에 옮겨 적지 않으므로 글자 변형이 없고, 8개 시트 170여 행이 export 대조에서 차이 0건으로 들어갔다. 탭 이동은 `.docs-sheet-tab` 요소에 JS로 `mousedown`·`mouseup` 이벤트를 보내면 된다(이동 뒤 `location.hash`에 gid가 나온다).

- 붙여넣을 행 수가 시트의 격자 크기(행 수)를 넘으면 Name Box 이동이 "잘못된 범위입니다" 모달로 막힌다(2026-09-27 화염술사, 배틀상태효과가 98행뿐이었음). 이때 Name Box에 입력한 주소 문자열이 이어 붙어(`B6A98`) **이름이 지정된 범위가 새로 생길 수 있다**. 붙여넣기 전 Name Box로 마지막 행+행 수 주소로 먼저 이동해 격자가 충분한지 확인하고, 모자라면 Name Box에 `A84:A98`처럼 끝의 N행 범위를 선택한 뒤 삽입 → 행 → "아래에 행 N개 삽입"으로 늘린다. Name Box는 클릭한 뒤 `cmd+a`로 기존 값을 지우고 입력한다. 실수로 생긴 이름 범위는 데이터 → 이름이 지정된 범위에서 삭제한다.

## 5. 오프라인 검증

- `tests/Molly.DataTests`는 CI에 포함되지 않는 두 인자를 지원한다.
  - `dotnet run --project tests/Molly.DataTests/Molly.DataTests.csproj -- --battle-live` : 실시간 시트를 읽어 `BattleCatalog.Parse` 검증만 수행.
  - `dotnet run --project tests/Molly.DataTests/Molly.DataTests.csproj -- --battle-balance [반복횟수]` : 배틀 준비된 모든 클래스를 동일 전투력으로 맞대결시켜 승률·스킬 사용 빈도·스킬을 사용한 전투의 승률을 뽑는다.
  - `... -- --battle-balance [반복횟수] [CSV폴더]` : 폴더를 주면 실시간 시트 대신 `{시트이름}.csv`(`GoogleSheetsBattleSource.SheetNames`의 모든 시트)로 시뮬레이션한다. 시트에 입력하기 전에 공개 CSV를 내려받아 새 행을 붙인 로컬 사본으로 수치를 먼저 조정할 때 쓴다.
  - `... -- --battle-log {클래스ID} {클래스ID} [CSV폴더]` : 두 클래스의 한 판을 Discord 중계 문구 그대로 출력한다. 패시브가 실제로 발동하는지 로그 문구·자원 변화로 확인할 때 쓴다(`피해` 효과의 `효과문구`는 로그에 나오지 않으므로 자원 변화나 피해 줄로 센다).
- 새 클래스가 위 검증을 통과하는지, 그리고 도입한 모든 기본 스킬·파생이 시뮬레이션에서 최소 1회 이상 실제로 발동하는지 확인한다.
- 한쪽으로 크게(대략 70% 이상) 치우친 승률이 나오면 원본 배율이 다른 클래스보다 과도하게 큰 스킬(대개 궁극기나 강화 파생)의 `고정값`을 조정한다. 완벽한 50:50을 요구하지 않는다 — 정밀한 밸런스는 이후 대규모(10,000회 단위) 시뮬레이션으로 조정한다는 것이 문서의 방침이다(`docs/battle/README.md` 10.3, 17장 P1 참고).

## 6. 문서·테스트 갱신

- `docs/battle/README.md`의 "8.x `{클래스}` 배틀 데이터 기준" 절 패턴을 따라 새 섹션을 추가하고, 뒤따르는 하위 절 번호를 한 칸씩 민다. 상호 참조(예: "8.12 검증을 통과한")도 함께 갱신한다.
- 클래스별 시트 사본 테스트(`HealerBattleTests.cs`, `ThiefBattleTests.cs`, `IceMageBattleTests.cs`, `FireMageBattleTests.cs`, `WarriorBattleTests.cs`)는 시트 행을 그대로 옮긴 사본이다. `배틀스킬AI` 사본은 헤더만 두어도 된다(AI 가산 동작은 `SkillAiBattleTests.cs`가 따로 검사한다). 파생이 없는 클래스는 `배틀스킬파생` 사본에 행이 하나도 없으면 헤더를 읽지 못해 로드가 실패하므로, 절대 성립하지 않는 조건의 자리표시 행을 하나 둔다(석궁사수·도적).
- 새 클래스가 도입한 고유 메커니즘(조건부 대체 파생, 자원 게이팅 등)을 검증하는 합성 테스트를 `tests/Molly.DataTests/Program.cs`에 추가한다. 기존 코드의 `battleRules`, `Check`, `FixedBattleRandom` 패턴을 그대로 재사용한다.
- 게임에 아예 새로 추가된 클래스라면 클래스 아이콘을 `assets/class_icons/{클래스 ID}.png`로 넣고, `Commons/ClassIcons.cs`의 `ClassIds`와 `scripts/verify.sh`, `ClassIconTests`의 개수를 함께 갱신한다. 원본은 나무위키 `마비노기 모바일/클래스` 문서의 `{계열}{번호} icon` 이미지(클래스 상세 문서 제목 옆 아이콘과 동일)다. 이어서 `python3 scripts/make_class_emojis.py`(Pillow 필요)로 텍스트 중간에 넣을 이모지용 회색 원형 배지 `assets/class_emojis/{클래스 ID}.png`를 다시 만든다. 봇이 시작(Ready)할 때 `class_{클래스 ID}` 이름의 봇 이모지로 없는 것만 자동 등록하며(`Commons/ClassEmojis.cs`), 배틀의 클래스 표기에 쓰인다.
- `bash scripts/verify.sh`로 빌드·오프라인 테스트·publish·필수 에셋을 모두 확인한다.

## 7. 원본 대비 gap 정리

새 클래스 반영이 끝나면, 입력한 배틀 데이터를 원본 설명·`기타` 필드와 다시 한 줄씩 대조해 다음 세 가지로 분류해 사용자에게 보고한다. 구현에 들어가기 전에 먼저 정리해서 공유한다.

- **단순화한 부분**: 원본에 있었지만 배틀 밸런스·연출을 위해 의도적으로 줄이거나 생략한 수치·효과.
- **엔진이 지원하지 않아 못 넣은 부분**: 2단계에서 확인한 엔진 한계 때문에 원본 그대로 구현하지 못한 항목. 다른 클래스에도 영향을 주는지(공통 버그·공통 미구현) 함께 확인한다.
- **원본 자체가 모호해서 확인이 필요한 부분**: 캡처 수치가 누락되었거나 설명과 수치가 맞지 않아 추측해야 하는 항목.

### 8.1 원본 읽기와 준비

- `패시브스킬`(`ID`·`이름`·`설명`·`기타`)을 1단계와 같은 CSV export로 읽고, 새 클래스의 `클래스.패시브1~6`이 가리키는 ID를 모은다. `배틀패시브`가 없거나 `활성화=FALSE`인 패시브는 로드 시 조용히 무시되므로, 빠진 패시브가 있어도 오류가 나지 않는다. 빠뜨리지 않도록 6개 모두 표로 정리해 둔다.
- 스킬 설명의 "~상태일 때 추가로" 같은 문장은 이미 그 상태일 때 받는 보너스 조건일 뿐, 그 스킬이 상태를 부여한다는 근거가 아니다. 상태·자원을 **누가 부여하는지는 원본 설명에 명시된 문장으로만** 정한다. 정황(스킬 그룹핑 등)만으로 부여 효과를 추가했다가 되돌린 사례가 있다(Issue #4, 댄서 우아·정열은 `inspiration` 패시브만 부여).
- 패시브와 스킬이 같은 현상을 서로 다른 규칙으로 설명하면(예: `ad_lib.기타`의 "영감 획득 시 20% 화합"과 `skilled_dance`의 "템포 2중첩 시 다음 애드리브가 화합") 한쪽을 덮어쓰지 않는다. 둘 다 살리고 `배틀스킬파생.우선순위`로 상위 규칙을 먼저 판정하게 한다(`ad_lib_harmony_guaranteed`).
- 패시브가 어느 클래스 소속인지, 인게임 표시값이 무엇인지 원본만으로 확정할 수 없으면 추측하지 말고 사용자에게 묻는다(Issue #3 엑스트라 액션·탄창 최대값 사례).

### 8.3 효과 조합 패턴

| 원문 패턴 | 행 구성 | 사례 |
| --- | --- | --- |
| 상시 N% 증가 | `발동시점=전투시작` + `효과유형`에 상태효과유형(`주는피해증가`·`치명타피해증가` 등)을 적고 `상태효과ID`로 `배틀상태효과` 행을 가리킨다. 영구 상태로 취급되어 `지속턴`은 읽지 않는다 | `combat_mastery_*`, `ecstatic_performance` |
| 중첩당 +N% | 중첩 수를 자원(`최대값`=최대 중첩)으로 쌓고, `배틀상태효과.중첩자원ID`에 그 자원을 적은 영구 상태를 전투시작에 부여. 값 × 현재 보유량으로 계산되고 자원이 0이면 효과도 0이다. 특정 스킬만 강화하면 `스킬피해증가`+`대상스킬ID` | `sharp_eye`, `driving_force`, `linked_swordsmanship` |
| 상태 X 동안 여러 효과 | 표식 자원(`최대값=1`, `지속턴`, `중첩방식=교체`) 하나로 지속을 관리하고, 효과 상태들은 `중첩자원ID`=그 표식인 영구 상태로 둔다. 효과마다 지속턴을 따로 주면 재진입 때 어긋난다 | `concentration`(`sw_focus`) |
| 다음 X 시 강화 | 표식 자원 설정 → `스킬사용완료시`("다음 공격"이면 피해를 준 스킬만 세는 `스킬적중완료시`) 행들에 `조건유형=자원보유`·`>=`·`1` → 마지막 실행순서에 같은 조건의 `자원소모`(`수치참조방식=전부`) | `sword_stance`, `first_strike`, `extra_action` |

### 8.4 패시브 전용 주의사항

- **실행 순서**: 한 트리거에서 패시브는 `클래스.패시브1~6` 순서로, 각 패시브 안에서는 `실행순서` 순으로 실행된다. 앞 행이 자원을 바꾸면 뒤 행의 조건 판정이 달라진다. 조건 행 → 소모 행 → 재설정 행 순서를 지킨다.
- **패시브의 피해·회복은 `고정값`으로만 준다**: 패시브 효과는 스킬이 없는 상태(`skill=null`)로 실행되므로, `고정값=0`으로 공격력 배율을 쓰는 방식은 안전하지 않다. `지속피해`·`지속회복`도 `고정값`(보유자 턴마다의 1회량)을 넣으면 쓸 수 있다(`vitality` 10920×2턴). `고정값`은 타격당 수치이며, 전체 피해는 `고정값 × 횟수 × fixed_damage_scale`이다(`encore` 19749×6).
- 패시브 피해에는 상대의 `받는기본공격피해감소`가 적용되지 않는다. 패시브 피해도 `치명타적중시`·`피격시` 트리거를 일으키므로 서로 반응하는 패시브가 있으면 연쇄를 확인한다.
- `대상스킬ID`를 지정한 `치명타적중시`·`치명타미적중시`는 그 스킬의 타격에만 반응하고, 일반 공격·패시브 피해에는 반응하지 않는다. 다단 공격은 타격마다 판정한다.
- `자원획득시`는 값이 늘어날 때마다 발동하지만, 상호배타·최대 1인 자원은 이미 보유 중이면 재설정이 무시되어 사실상 첫 획득 때만 발동한다. `대상자원ID`에는 자원 ID 대신 자원 분류를 적어 분류 전체에 반응하게 할 수 있다.
- 새 자원·상태 ID는 3단계와 같이 클래스 접두사를 붙인다. 같은 이름의 패시브라도 클래스마다 효과가 다르면 ID를 따로 만든다(`combat_mastery_risk` / `combat_mastery_risk_crossbow`).
- 새 발동시점·상태효과유형·조건유형이 꼭 필요할 때만 엔진을 확장한다. 확장하면 `BattleCatalog.cs`의 `passiveTriggers` 허용 목록, README 8.25.2·8.25.3의 어휘 목록, 이 장 첫머리의 어휘 목록을 함께 고친다. 새 기능마다 `tests/Molly.DataTests/Program.cs`의 패시브 회귀 테스트(`BattlePassive`, `Trigger:` 지정 `BattleEffect`) 패턴으로 합성 테스트를 추가한다.

### 8.5 입력과 검증

- 입력 순서: `배틀자원` → `배틀상태효과` → `배틀패시브` → `배틀패시브효과`. `BattleCatalog.Parse`는 존재하지 않는 자원·조건·대상스킬·대상자원 ID와 발동시점 오타를 오류로 처리하므로, 참조되는 행을 먼저 넣는다. 단 `전투시작` 영구 상태는 `지속턴=0`이라 상태 ID 존재 여부를 검사하지 않는다. 오타가 나도 오류 없이 효과만 사라지므로 이벤트 로그의 `PassiveApplied`로 확인한다. 한 패시브의 효과 행을 한 번에 TSV로 붙여넣으면 빠르다(4단계 방법).
- 시트에 넣기 전에 5단계의 `--battle-balance [반복횟수] [CSV폴더]`로 로컬 사본에서 먼저 돌려본다. 입력 후에는 `--battle-live`로 파싱을 확인한다.
- 확률이 걸린 효과는 발동 비율이 원문 확률과 비슷한지 이벤트 로그로 확인한다. 자원·상태·다음행동지정 효과가 발동확률을 무시하고 항상 100% 발동하던 버그가 있었다(526dd03에서 수정).
- `--battle-balance`의 스킬별 "사용 전투 승률"로 패시브 반영 전후를 비교한다. 패시브 하나가 특정 스킬 사용을 지나치게 늘리면(예: `improvised_performance`의 바즈 테일 강제) 그 스킬의 빈도와 클래스 승률이 함께 튄다.
- 전투가 짧아(현재 평균 7턴 수준) 연계형 패시브는 거의 발동하지 않을 수 있다. 발동이 드물면 그 사실을 README 8.25.4·8.25.5에 기록하고, 수치를 억지로 키우지 않는다(석궁사수 사례).
- 문서: README 8.25.4에 "현재 {클래스} 6종(날짜 반영)" 목록을 추가하고, 패시브마다 원문 대비 단순화·미구현 내용을 한 줄씩 적는다. 8.25.5의 시뮬레이션 결과도 갱신한다. 7단계 gap 보고에도 패시브를 포함한다.
