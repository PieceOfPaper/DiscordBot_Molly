# 몰리 놀이터: 배틀 기획서

> 문서 상태: 초안  
> 최종 갱신: 2026-09-25
> 장르: Discord 기반 무조작 텍스트 전투 시뮬레이터

## 1. 개요

몰리 놀이터의 배틀은 Discord 사용자가 자신의 마비노기 모바일 캐릭터를 등록하고, 다른 사용자의 캐릭터에게 도전하여 자동으로 전투하는 텍스트 기반 게임이다.

사용자가 하는 조작은 `/배틀` 명령으로 상대를 지정하는 것뿐이다. 전투가 시작된 뒤에는 공격·스킬·방어 등의 명령이나 버튼을 제공하지 않는다. 몰리가 두 캐릭터의 클래스, 능력치, 스킬을 바탕으로 모든 행동을 결정하고 전투 상황을 Discord 텍스트 메시지로만 중계한다.

```text
종잇장이 ZEL에게 일반 공격!
치명타! 456의 피해를 입혔습니다!
ZEL는 아직 끄떡없습니다!
```

### 1.1 핵심 한 줄

> 마비노기 모바일의 실제 캐릭터 정보와 클래스 스킬을 이용해 몰리가 진행하는 Discord용 텍스트 자동전투 게임.

### 1.2 용어

| 용어 | 의미 |
| --- | --- |
| 캐릭터 | Discord 사용자가 등록한 마비노기 모바일 캐릭터 |
| 도전자 | `/배틀` 명령을 실행한 사용자 |
| 상대 | 배틀 대상으로 지정된 Discord 사용자 |
| 게임 스레드 | `/배틀`을 실행한 일반 텍스트 채널에 만드는 전투 로그용 공개 스레드 |
| 전투 스냅샷 | 전투 시작 시 고정한 캐릭터 클래스와 능력치 |
| 전투 이벤트 | 공격, 피해, 치명타, 회복, 상태 이상 등 전투 중 발생한 사건 |

## 2. 기획 목표

- 기존 랭킹 조회 기능을 놀이 콘텐츠로 확장한다.
- 실제 캐릭터의 클래스와 능력치를 전투에 반영한다.
- Google Sheets에서 관리하는 클래스·스킬 데이터를 활용한다.
- 플레이어의 지속적인 조작 없이도 짧고 재미있는 전투를 제공한다.
- 일반 채팅을 방해하지 않는 독립적인 전투 공간을 사용한다.
- 전투 결과가 능력치만으로 완전히 고정되지 않도록 클래스와 스킬, 돌발 이벤트와 적절한 무작위성을 반영한다.
- 전적 경쟁이나 성장 기록이 아니라 한 판의 구경거리와 대화 소재를 만드는 데 집중한다.
- 이후 전적, 토너먼트, 관전자 기능 등으로 확장할 수 있는 구조를 만든다.

## 3. 초기 범위에서 제외할 것

다음 기능은 초기 버전에 포함하지 않는다.

- 전투 중 플레이어의 실시간 스킬 선택
- 관전자의 전투 개입
- 장비 등록 및 장비 강화
- 별도의 캐릭터 레벨업과 성장 재화
- 포인트 상점과 유료성 재화
- 시즌 보상
- 전적·승률·연승·전투 로그 영구 저장
- 과거 전투 조회와 다시보기
- 토너먼트
- AI를 이용한 실시간 전투 문장 생성
- 생활력과 매력의 복잡한 전투 시스템

## 4. 사용자 흐름

### 4.1 캐릭터 등록

구현된 등록 명령:

```text
/캐릭터등록 서버:칼릭스 캐릭터이름:종잇장
```

명령어 이름과 옵션 계약은 현재 구현된 `/캐릭터등록`을 기준으로 한다. 아래 과정은 배틀 기능에서 기대하는 등록 데이터의 의미를 설명하며, 이미 구현된 명령 처리 흐름을 불필요하게 다시 만들지 않는다.

진행 과정:

1. 사용자가 서버와 캐릭터 이름을 입력한다.
2. 몰리가 마비노기 모바일 랭킹에서 캐릭터를 검색한다.
3. 검색 결과가 없거나 여러 결과를 구분할 수 없으면 등록하지 않는다.
4. 검색 결과를 사용자에게 보여주고 등록 여부를 확인한다.
5. 확인하면 Discord 사용자와 캐릭터를 연결하여 DB에 저장한다.
6. 기존에 등록한 캐릭터가 있다면 변경 여부를 확인한다.

등록 정책:

- Discord 사용자 한 명은 캐릭터를 하나만 등록할 수 있다.
- 캐릭터 등록 정보는 길드별로 나누지 않고 봇 전체에서 공통으로 사용한다.
- 동일한 게임 캐릭터를 여러 Discord 사용자가 등록하는 것은 최종적으로 금지한다.
- 다만 캐릭터 소유권을 봇이 검증할 수 없으므로 중복 등록 방지 기능은 후순위로 구현한다.
- 봇은 서버 이전이나 캐릭터명 변경을 자동으로 추적하지 않는다.
- 동일한 서버와 캐릭터명으로 조회되는 클래스와 능력치 변경은 랭킹 갱신 시 반영한다.

등록 시 확보할 후보 데이터:

- Discord 사용자 ID
- 마비노기 모바일 서버
- 캐릭터 이름
- 현재 클래스
- 전투력
- 생활력
- 매력
- 각 랭킹 및 순위
- 마지막 조회 시각

### 4.2 캐릭터 조회 및 갱신

필요할 가능성이 높은 보조 명령:

```text
/내캐릭터
/캐릭터갱신
/캐릭터변경
/캐릭터해제
```

랭킹 데이터의 유효 시간은 **1시간**으로 한다.

- 마지막 정상 갱신 후 1시간 이내이면 DB에 저장된 정보를 사용한다.
- 1시간이 지났다면 배틀 시작 직전에 랭킹을 다시 검색한다.
- 검색에 성공하면 클래스와 능력치를 갱신한 뒤 배틀을 시작한다.
- 도전자와 상대 중 한 명이라도 랭킹에서 검색되지 않으면 배틀을 시작하지 않는다.
- 검색 실패 시 등록 정보는 즉시 삭제하지 않는다. 일시적인 외부 서비스 장애일 수 있기 때문이다.
- 외부 서비스 장애와 실제 검색 결과 없음 모두 배틀 시작을 중단하지만 안내 문구는 구분한다.
  - 외부 서비스 장애: 잠시 후 다시 시도하도록 안내한다.
  - 검색 결과 없음: 등록 정보는 유지하되 현재 캐릭터로 배틀할 수 없으며 `/캐릭터등록`으로 정보를 다시 확인하도록 안내한다.

### 4.3 배틀 신청

예상 명령 형식:

```text
/배틀 상대:@ZEL
```

기본 흐름:

1. 명령을 실행한 채널이 배틀을 허용한 채널인지 확인한다.
2. 현재 길드에서 다른 게임이 진행 중인지 확인한다.
3. 상대가 현재 같은 Discord 길드에 속해 있는지 확인한다.
4. 도전자와 상대가 모두 캐릭터를 등록했는지 확인한다.
5. 마지막 갱신 시각이 1시간을 넘긴 캐릭터는 랭킹에서 다시 검색한다.
6. 두 캐릭터가 모두 유효하면 상대방의 수락 없이 명령 실행 채널에 게임 스레드를 생성한다.
7. 두 캐릭터의 전투 시작 시점 능력치를 스냅샷으로 저장한다.
8. 몰리가 자동전투를 진행한다.
9. 전투 결과와 주요 이벤트를 메모리의 전투 컨텍스트에만 반영한다.
10. 결과 요약을 출력한다.
11. 출력이 끝나면 전투 컨텍스트를 폐기하고 게임 스레드는 다른 게임과 같이 종료 후 보관한다.

예외 처리 후보:

- 자기 자신에게 도전
- 등록하지 않은 사용자에게 도전
- 같은 길드에 속하지 않은 사용자에게 도전
- 길드에서 이미 다른 게임이 진행 중
- 외부 랭킹 조회 실패
- 클래스 또는 스킬 데이터가 없음
- 배틀 도중 봇 재시작

## 5. 전투 공간

전투는 명령을 실행한 채널의 게임 스레드에서 진행한다.

- `/배틀`은 서버의 일반 텍스트 채널에서 실행한다. 기존 스레드 안에서는 시작하지 않는다.
- 전투 공간은 명령 실행 채널에 공개 스레드로 만든다.
- 스레드 이름은 다른 퀴즈·놀이와 같이 `배틀-yyyyMMddHHmm` 형식으로 사용한다. 날짜와 시간 숫자 사이에 구분 기호를 넣지 않는다.
- 정상 종료와 `/배틀종료` 강제 종료 모두 10초의 결과 확인 시간을 둔 뒤 스레드를 읽기 전용으로 잠그고 보관한다.
- 스레드를 만들 수 없으면 대체 채널을 사용하지 않고 실패 사실을 알린다.
- 한 길드에서는 게임 하나만 동시에 진행할 수 있다. 배틀과 다른 게임도 같은 길드 단위 잠금을 공유한다.
- 전투가 정상 종료되거나 오류로 중단되면 길드의 게임 잠금을 반드시 해제한다.

## 6. 전투 기본 구조

### 6.1 기본 원칙

- 전투 시작 후 플레이어와 관전자의 입력을 받지 않고 완전히 자동으로 진행한다.
- 이미지나 전투 화면 없이 Discord 텍스트 메시지만 출력한다.
- 참가자를 멘션(캐릭터명)한 뒤 30초 준비 시간을 기다리고 전투를 시뮬레이션한다.
- 확정된 각 턴 이벤트를 5초 간격으로 전송해 실시간 전투처럼 중계한다.
- 행동 선택은 조건식 AI, 스킬 쿨다운, 자원과 상태를 기반으로 한다.
- 선공을 결정한 뒤 두 캐릭터가 교대로 행동한다.
- 기본 공격은 항상 명중하며 회피·빗나감은 스킬, 상태 또는 돌발 이벤트로만 발생한다.
- 최대 주요 행동을 넘기면 남은 HP 비율로 판정한다.
- 전투 상태와 이벤트 목록은 출력이 끝나면 폐기하며 DB에 결과를 남기지 않는다.

### 6.2 목표 플레이 시간

| 항목 | 초기 목표 |
| --- | --- |
| 전투 시간 | 준비 30초 + 주요 행동 수에 따른 중계 시간 |
| 평균 주요 행동 | 12~20회 |
| 턴 로그 출력 간격 | 5초 |
| 최대 주요 행동 | 20회 |
| 캐릭터당 돌발 이벤트 | 최대 2회 |
| 길드당 동시 놀이터 | 1개 |

반격, 지속 피해, 상태 변화와 돌발 이벤트는 주요 행동에 딸린 부가 이벤트로 취급한다.

### 6.3 메모리 전투 상태

전투 중에만 다음 상태를 유지한다. DB 모델이 아니라 런타임 모델이다.

```text
BattleContext
- Random
- MajorActionIndex
- CurrentActor
- GlobalSurpriseEventCooldown
- FighterA / FighterB
- PendingEvents

FighterState
- DiscordUserId / CharacterName / ClassId
- CombatPower / LifePower / CharmPower
- MaxHp / CurrentHp / Attack / Defense
- CriticalChance / CriticalMultiplier
- SkillCooldowns
- Resources
- StatusEffects
- SurpriseEventCounts
- TotalSurpriseEventCount
```

쿨다운, 자원, 상태와 이벤트 횟수는 전투 시작 시 초기화한다. 캐릭터 등록 DB의 값을 직접 변경하지 않는다.

### 6.4 전투용 능력치 계산 초안

두 참가자의 전투력 격차는 기하평균과 제곱근으로 압축한다.

```text
기준전투력 = sqrt(A전투력 × B전투력)
전투력배율 = clamp((내전투력 ÷ 기준전투력) ^ power_scale_exponent,
                    power_scale_min,
                    power_scale_max)

최대HP = base_max_hp × 전투력배율
공격력 = base_attack × 전투력배율
방어력 = base_defense × 전투력배율
```

초기 상수는 `배틀규칙` 시트에서 관리한다.

| 항목 | 초기값 |
| --- | ---: |
| 기본 최대 HP | 20,000 |
| 기본 공격력 | 1,000 |
| 기본 방어력 | 200 |
| 전투력 압축 지수 | 0.5 |
| 전투력배율 하한 | 0.75 |
| 전투력배율 상한 | 1.25 |

전투력이 같은 두 캐릭터는 배율 1.0으로 시작한다. 격차는 우위를 만들지만 상·하한 때문에 승패를 단독으로 확정하지 않는다.

> 2026-09-22 조정: 실제 시뮬레이션 결과 평균 주요 행동이 약 5.9회로 여전히 짧았다. 원인은 `max_major_actions`(최대 행동 상한)가 아니라 대부분의 전투가 그 상한에 도달하기 훨씬 전에 HP 0으로 종료된다는 점이었다 — 즉 전투 길이는 상한이 아니라 피해량 대비 HP 총량(TTK)이 결정한다. 실제 3개 클래스 전체 조합으로 4,000회씩 재시뮬레이션한 결과: 원래 값(HP 10,000) 평균 5.9회·KO종료 100%, HP 20,000(×2) 평균 11.7회·KO종료 94.9%, HP 30,000(×3) 평균 16.1회·KO종료 83.5%(최대행동 종료 16.5%), HP 40,000(×4) 평균 18.8회·KO종료 52.5%(최대행동·무승부 급증). 평균을 목표 범위(12~20회)에 들이면서도 "대부분 KO로 끝난다"는 원래 설계 의도를 유지하는 지점은 ×2였으므로 `base_max_hp`를 10,000→20,000으로 조정했다. 공격력·방어력·스킬 배율·고정 피해값은 그대로 두어도 HP만 늘리면 모든 피해원(계수 기반·고정값 기반)의 TTK 기여가 비례해서 늘어난다.

### 6.5 피해·회복 계산 초안

```text
스킬기본값 = 공격력 × 스킬등급별피해배율
방어적용값 = max(1, 스킬기본값 - 방어력 × defense_coefficient)
편차적용값 = 방어적용값 × random(0.90, 1.10)
최종피해 = 치명타이면 편차적용값 × 1.50, 아니면 편차적용값
추가타피해 = round(최종피해 × additional_hit_damage_ratio)
```

- 일반 스킬은 `skill_damage_min_multiplier`와 `skill_damage_max_multiplier` 사이의 고유한 전투 배율을 사용하고, 궁극기는 `ultimate_damage_multiplier`를 사용한다.
- 치명타는 매 타격마다 `base_critical_chance`로 판정하며, 성공하면 `CriticalHit` 이벤트와 강조 메시지를 남긴다.
- 추가타는 일반 피해가 확정된 뒤 `additional_hit_chance`로 한 번 판정한다. 확정 피해의 `additional_hit_damage_ratio`만큼 추가 피해를 주되, 추가 피해에는 별도의 치명타 판정을 하지 않는다.
- 화면의 피해량·계수·고정값은 밸런스 계산에 사용하지 않는다. 피해 효과의 `횟수=N`은 스킬의 총 기본 피해를 `N`등분한다. 각 타격은 따로 치명타·추가타를 판정하므로 다단 스킬이 단일 스킬보다 일방적으로 높은 총피해를 갖지 않는다.
- 최종 피해와 회복은 반올림한 정수이며 최소 피해는 1이다.

### 6.6 한 행동의 처리 순서

`주요 행동`은 한 캐릭터가 일반 공격 또는 독립 행동 스킬 하나를 선택해 실행하는 단위다. 반격, 파생 스킬, 지속 효과와 돌발 이벤트는 별도 주요 행동을 소비하지 않는다.

1. 행동자에게 걸린 행동 시작 효과와 지속 피해·회복을 실행한다.
2. 각 효과 행 적용 직후 사망을 판정한다. 사망했다면 남은 행동을 취소하고 6.9 규칙으로 종료한다.
3. 행동자의 쿨다운을 1 감소시키고 만료된 상태를 정리한다.
4. 기절 등 행동 불가 상태를 검사한다. 행동 불가이면 스킬을 선택하지 않고 행동 종료 단계로 이동한다.
5. 클래스의 기본 스킬 5개와 궁극기 중 활성화되고 사용 가능한 후보를 만든다.
6. 조건·쿨다운을 통과한 스킬을 고르고, 직전 사용 스킬은 다른 후보가 있으면 제외한다. 우선순위는 선택 확률에 완만하게만 반영한다.
7. 자원 비용을 먼저 지불하고 선택한 스킬의 쿨다운을 설정한다.
8. `배틀스킬효과`를 실행순서대로 적용한다. 각 반복 타격은 방어·편차·치명타·추가타와 사망을 따로 판정한다.
9. 살아 있다면 `배틀스킬파생`을 우선순위 순서로 판정한다.
10. 피해 직전·직후, 상태 적용 직후, 스킬 사용 직후에 해당하는 돌발 이벤트를 판정한다.
11. 행동 종료 효과와 상태 지속 턴을 갱신하고 주요 행동 수를 1 증가시킨다.
12. 종료 조건을 검사한 뒤 다음 행동자로 교대한다.

시뮬레이션이 끝나면 `PendingEvents`를 Discord 메시지로 순차 출력한다. 출력 성공 여부와 관계없이 결과를 DB에 기록하지 않는다.

### 6.7 돌발 이벤트 확률

```text
능력치보정 = clamp(능력치 ÷ 능력치기준값, 0, 2) × 능력치보정계수
최종발동확률 = min(최대확률, 기본확률 + 능력치보정)
```

돌발 이벤트는 매력만 사용한다. 생활력은 돌발 이벤트가 아니라 배틀생활스킬(7.2)에 쓴다.

- 발동시점과 조건을 모두 만족할 때만 판정한다.
- 캐릭터당 한 전투 최대 2회와 개별 이벤트의 횟수 제한을 함께 적용한다.
- 이벤트 발생 후 전역 쿨다운 2행동을 적용한다.
- 같은 시점에 여러 이벤트가 성공하면 최종 확률이 높은 하나만 실행하며 동률은 무작위로 정한다.
- 한 번의 이벤트가 즉시 승패를 결정하지 않도록 효과 크기를 제한한다.

### 6.8 쿨다운·상태·자원 시점 규칙

- 스킬의 쿨다운은 사용 직후 시트 값으로 설정한다.
- 쿨다운은 해당 캐릭터의 다음 주요 행동 시작부터 1씩 감소한다. 방금 사용한 행동에서는 감소하지 않는다.
- 쿨다운이 0인 스킬만 후보가 될 수 있다.
- `지속턴=N`인 상태는 적용된 행동을 제외하고 대상의 다음 N회 주요 행동이 끝날 때까지 유지한다. 엔진은 보유자의 턴이 돌아올 때 지속턴을 1 줄이되, 0이 된 상태도 그 턴의 행동까지 적용하고 행동이 끝난 뒤 제거한다. 상대에게 건 디버프는 상대(보유자)의 턴으로 센다. 자원의 `지속턴`도 같은 규칙을 따른다.
- 행동 중 같은 상태를 다시 받으면 `지속방식`에 따라 갱신(남은 턴과 새 지속턴 중 큰 값) 또는 누적(남은 턴에 더함)한다. 이번 행동에 새로 받은 상태는 행동 뒤에 제거되지 않는다.
- 지속 피해와 지속 회복은 대상의 행동 시작에 적용한다.
- `재사용 시` 파생으로 진행 중인 상태를 끝내면(죽은 척 → 라이징 윈드밀) 조건이 된 상태를 즉시 제거하며, 이때 `상태만료 시` 파생은 다시 발동하지 않는다.
- 행동 불가로 행동을 건너뛰어도 주요 행동과 상태 지속 턴은 소비한다.
- 반격과 즉시 파생은 주요 행동, 쿨다운 감소와 상태 지속 턴을 소비하지 않는다.
- 다음 행동 예약 파생은 예약 대상의 다음 주요 행동을 대체하며 주요 행동을 소비한다.
- 초 단위 원본 시간은 **6초 = 1턴, 소수점 올림**을 가이드라인으로 턴에 환산한다(8.11 환산표). 스킬 재사용 대기 시간도 같은 기준이며, 가이드라인일 뿐 밸런스상 필요하면 다르게 정할 수 있다. `minimum_skill_cooldown`은 1이다.
- 자원은 효과 적용 직후 최소 0, 최대값 이하로 제한한다. 상호배타 자원은 새 값을 얻는 즉시 기존 값을 0으로 만든다.
- 전투 종료 시 모든 쿨다운, 상태, 자원과 예약 행동은 폐기한다.

### 6.9 사망·종료 판정

- 피해·회복·반사 등 각 효과 행과 각 반복 타격 직후 HP를 `0..MaxHp`로 제한하고 사망을 판정한다.
- 사망한 대상에게 남아 있는 같은 스킬의 후속 효과와 파생은 실행하지 않는다.
- 지속 피해의 원인 제공자가 살아 있으면 그 캐릭터의 승리로 처리한다.
- 하나의 원자적 효과가 두 캐릭터를 동시에 0 HP로 만들면 무승부다.
- 메시지 전송 실패는 이미 끝난 시뮬레이션의 승패를 바꾸지 않는다.
- 최대 주요 행동 도달 시에는 10.1의 HP 비율 판정을 사용한다.

## 7. 능력치 설계 방향

### 7.1 전투력

전투력은 최대 HP, 공격력과 방어력을 만드는 중심 능력치다. 격차는 제곱근으로 압축하고 상·하한을 적용해 강한 캐릭터가 유리하되 결과가 전투력만으로 고정되지 않게 한다.

### 7.2 생활력

생활력은 생활스킬 레벨을 올리며 축적한 채집·제작·가공·도구 활용 경험의 종합 능력치다. 목표 설계에서는 생활력을 단순한 돌발 이벤트 확률이 아니라, 일반 전투스킬과 같은 주요 행동으로 사용하는 **배틀생활스킬**에 반영한다.

배틀생활스킬은 전투 중 갑자기 도끼를 휘두르거나 낚싯대를 던지는 것처럼 엉뚱해 보이는 행동이 실제로 승패를 가를 수 있는 연출을 목표로 한다. 따라서 주요 행동을 소비하며, 드물게 나오는 대신 한 번 나오면 클래스 스킬에 버금가는 존재감을 갖는다.

배틀생활스킬의 이름은 `생활스킬` 시트의 이름을 그대로 사용한다. 별도의 전투용 별칭을 만들지 않아 플레이어가 자신의 생활스킬과 전투 로그를 바로 연결할 수 있게 한다.

현재 캐릭터 스냅샷에는 생활력 총합만 있고 개별 생활스킬 레벨은 없다. 따라서 어떤 배틀생활스킬이 선택될지는 개별 숙련도가 아니라 공통 후보와 조건으로 정한다. 향후 개별 생활스킬 레벨을 안정적으로 가져올 수 있을 때에만 스킬별 사용 확률이나 효과 차이를 추가한다.

#### 7.2.1 배틀생활스킬 사용 규칙 초안

1. 행동 시작 시 현재 상황에서 효과가 있는 배틀생활스킬 후보를 만든다.
2. 낮은 확률로 배틀생활스킬 사용 여부를 먼저 판정한다.
3. 성공하면 후보 중 하나를 가중치로 선택하고 일반 공격·클래스 스킬 대신 주요 행동으로 사용한다.
4. 실패하거나 후보가 없으면 기존 클래스 행동 선택을 진행한다.
5. 한 캐릭터는 전투당 배틀생활스킬을 최대 1회 사용한다.
6. 회복 대상이 없거나 해로운 상태가 없는 등 효과가 무의미한 스킬은 후보에 넣지 않는다.

생활력 기준값은 실제 분포를 기준으로 30,000으로 정한다. 2026-09-25 기준 적당히 성장한 캐릭터는 약 20,000, 꾸준히 성장한 캐릭터는 약 35,000, 상위권은 45,000 이상이다.

사용 확률은 행동당 기본 6%, 생활력 보정 후 최대 16%다. 실제 전투의 캐릭터당 평균 주요 행동은 약 4.3회이므로(2026-09-25 시뮬레이션) 이를 기준으로 정했다.

| 생활력 | 행동당 사용 확률 | 한 전투에서 사용하는 비율(시뮬레이션) | 생활력효과배율 | 생활력 20,000 상대 승률(시뮬레이션) |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 6.0% | 19% | 0.70 | 50.0% |
| 20,000 | 9.3% | 27% | 0.82 | 49.6% |
| 35,000 | 11.8% | 33% | 1.08 | 52.0% |
| 45,000 | 13.5% | 38% | 1.22 | 53.5% |
| 60,000 이상 | 16.0% | 42% | 1.41~1.50 | 55.0% |

두 참가자를 합치면 대략 두 판에 한 번 배틀생활스킬을 볼 수 있다. 생활력이 높을수록 사용 빈도와 효과가 함께 올라 승률이 완만하게 오르되, 전투력 격차보다 작게 유지한다.

```text
생활력효과배율 = clamp(sqrt(생활력 ÷ 30000), 0.7, 1.5)
최종효과값 = 기본효과값 × 생활력효과배율
```

피해, 회복, 피해 감소율처럼 연속적인 수치는 이 배율을 사용한다. 브레이크 칸 수, 쿨다운 감소 턴, 상태 제거 개수, 확정 치명타, 브레이크 면역처럼 정수·확정 효과는 배율을 적용하지 않는다. 피해 감소·회피·약화처럼 비율로 표현하는 효과는 배율 적용 후 최대 80%로 제한한다.

배틀생활스킬은 주요 행동을 소비하므로 생활력이 높을수록 오히려 약해지는 역전이 생기면 안 된다. 실제 전투는 클래스 스킬이 거의 항상 준비되어 있어 일반 공격이 드물고, 평균 주요 행동 하나의 피해는 약 4,300(클래스 스킬 4,400~6,000)이다. 따라서 생활력효과배율 1.0(생활력 30,000)에서 각 스킬의 가치는 일반 공격이 아니라 **평균 클래스 행동**과 같게 맞춘다.

검증 방법: 실제 시트 데이터로 생활력 30,000인 A가 조건을 만족한 첫 행동에서 해당 스킬을 반드시 쓰고 B는 쓰지 않는 전투를 스킬마다 12,000회 돌려, 생활스킬 없는 전투(승률 50%)와의 차이가 ±3% 안에 들도록 계수를 조정했다(2026-09-25, 모든 스킬 −3.0%~+2.4%). 시트 수치를 바꾸면 같은 방법으로 다시 확인한다. HP 조건이 있는 회복형은 회복이 낭비되지 않도록 HP가 충분히 줄었을 때만 후보가 된다.

#### 7.2.2 생활스킬별 배틀생활스킬 콘셉트

원본 `생활스킬.설명`의 도구와 결과물을 그대로 전투 연출로 옮긴다.

| 배틀생활스킬 이름 | 원본 근거 | 전투 연출 | 후보 조건 | 효과 (배율 1.0 기준) |
| --- | --- | --- | --- | --- |
| 일상 채집 | 맨손으로 달걀·사과·거미줄 등 채집 | 주변을 뒤져 손에 잡히는 것을 쓴다 | HP 80% 미만 | 무작위 1개: 달걀 투척(피해 6.0) / 사과(최대HP 35% 회복) / 거미줄(상대 다음 행동 피해 80% 감소) / 황금 네잎클로버(다음 전투 스킬 치명타 확정, 드묾) |
| 나무 베기 | 벌목 도끼 | 도끼로 크게 내려찍는다 | 상대 생존 | 강한 단타 피해 5.5 |
| 광석 캐기 | 곡괭이 | 곡괭이로 방어를 깨뜨린다 | 상대 생존 | 피해 3.4, 브레이크 2칸 |
| 약초 채집 | 약초 괭이로 약초·버섯 채집 | 약초를 다듬어 해로운 효과를 가라앉힌다 | 해로운 상태 보유 | 해로운 상태 1개 제거, 최대HP 28% 회복 |
| 양털 깎기 | 양털 가위 | 양털을 둘러 충격을 흡수한다 | HP 90% 미만 | 다음에 받는 공격 한 번(다단이면 모든 타격)의 피해 80% 감소, 최대HP 20% 회복 |
| 추수 | 낫 | 낫을 연달아 휘두른다 | 상대 생존 | 총 피해 5.6을 2회로 나눔 |
| 호미질 | 호미로 땅속 작물 채굴 | 발밑을 파헤쳐 자세를 무너뜨린다 | 상대 생존 | 피해 4.5, 브레이크 1칸 |
| 곤충 채집 | 곤충 채집망 | 채집망으로 시야를 가린다 | 상대 생존 | 피해 3.0, 상대 다음 행동 피해 80% 감소 |
| 낚시 | 낚싯대 | 낚싯대를 던져 무엇이 걸릴지 모른다 | 상대 생존 | 무작위 1개: 월척(피해 8.0) / 잔챙이(피해 4.3) / 낡은 장화(피해 3.0) |
| 대장 기술 | 금속으로 근거리 무기 제작 | 무기를 벼려 다음 일격을 준비한다 | 항상 | 다음 전투 스킬 피해 250% 증가 |
| 목공 | 목재로 원거리 무기 제작 | 무기의 균형을 맞춰 급소를 겨눈다 | 항상 | 다음 전투 스킬 치명타 확정, 치명타 피해 200% 증가 |
| 매직 크래프트 | 다양한 재료로 마법 무기 제작 | 무기에 마력을 불어넣는다 | 항상 | 2턴 동안 주는 피해 90% 증가 |
| 중갑 제작 | 금속으로 중갑 방어구 제작 | 갑옷의 약한 부분을 보강한다 | 항상 | 2턴 동안 받는 피해 70% 감소 |
| 경갑 제작 | 가죽으로 활동성 높은 경갑 제작 | 장비를 가볍게 손봐 몸놀림을 올린다 | 항상 | 2턴 동안 회피 확률 75% |
| 천옷 제작 | 옷감과 실크로 몸에 맞는 천옷 제작 | 옷매무새를 고쳐 흐트러지지 않는 자세를 갖춘다 | 항상 | 해로운 상태 1개 제거, 2턴 동안 받는 피해 70% 감소와 브레이크 면역 |
| 물약 조제 | 물약과 붕대 제작 | 물약을 즉석에서 조제해 마시고 붕대를 감는다 | HP 50% 미만 | 최대HP 26% 즉시 회복, 2턴 동안 매 턴 최대HP 5% 회복 |
| 요리 | 먹으면 기운이 나는 음식 제작 | 음식을 먹고 기운을 되찾는다 | HP 80% 미만 | 최대HP 20% 회복, 다음 전투 스킬 피해 60% 증가 |
| 핸디크래프트 | 소모품·도구 제작 | 즉석 도구를 던져 폭발시킨다 | 상대 생존 | 피해 4.6, 브레이크 1칸 |
| 아르바이트 | 아르바이트로 보상 획득 | 익숙한 잡일 솜씨로 전열을 정비한다 | HP 70% 미만 | 모든 전투 스킬 재사용 대기시간 2턴 감소, 최대HP 30% 회복 |

피해 계수는 클래스 스킬과 같은 `공격력 × 계수` 기준이며 방어·편차·치명타·추가타를 동일하게 적용한다. 다단 피해는 총 계수를 횟수로 나눈다.

일상 채집과 낚시는 효과 행 중 하나를 가중치로 뽑는 **무작위 결과형**이다. 낚시의 낡은 장화처럼 평균 클래스 행동보다 약한 결과도 나올 수 있지만, 월척이 나오면 한 번에 흐름을 바꿀 수 있어 전체 기대값은 평균 클래스 행동과 비슷하다.

`연금술`은 `생활스킬` 시트에는 존재하지만 생활력 성장과 무관하므로 배틀생활스킬을 만들지 않는다. 생활력 후보 수, 확률 계산과 관련 데이터 검증에서도 제외한다.

#### 7.2.3 기존 생활력 돌발 이벤트의 처리

배틀생활스킬 도입 전 엔진의 생활력 돌발 이벤트는 `배틀돌발이벤트` 시트가 아니라 `배틀규칙`의 `life_surprise_*` 값으로 하드코딩된 야전 응급처치 하나만 동작했다. `배틀돌발이벤트`의 급조한 방어구와 노련한 몸풀기는 데이터만 있고 엔진에서 실행되지 않았다. 배틀생활스킬 구현(2026-09-25)과 함께 다음처럼 역할을 흡수하고 생활력 돌발 이벤트를 제거했다.

| 기존 이벤트 | 흡수할 배틀생활스킬 |
| --- | --- |
| 야전 응급처치 | 약초 채집, 물약 조제, 요리 |
| 급조한 방어구 | 양털 깎기, 중갑 제작, 천옷 제작 |
| 노련한 몸풀기 | 약초 채집, 천옷 제작 |

엔진의 생활력 돌발 판정 분기, `배틀규칙`의 `life_surprise_*` 6개 행, `배틀돌발이벤트`·`배틀돌발이벤트효과`의 `life_*` 행을 제거했다. `배틀규칙`에는 대신 `life_skill_max_uses_per_actor`(캐릭터당 전투 사용 횟수, 1)와 `life_skill_ratio_cap`(감소·회피·약화 비율 상한, 0.8)을 둔다. 생활력 돌발 이벤트와 배틀생활스킬을 동시에 유지하면 생활력이 발동 확률과 행동 효과 양쪽에서 중복 적용된다.

#### 7.2.4 데이터 구성과 초기값

Google Sheets에 `배틀생활스킬` 19행과 `배틀생활스킬효과` 36행의 초안을 둔다. 배틀생활스킬도 클래스 스킬처럼 정의와 효과를 분리하며, `연금술`은 두 시트 모두에서 제외한다.

`배틀생활스킬` 필드:

| 필드 | 설명 |
| --- | --- |
| `ID`, `생활스킬이름`, `활성화` | 전투용 고유 ID, `생활스킬.이름`과 정확히 일치하는 표시 이름, 사용 여부 |
| `기본사용확률`, `생활력기준값`, `생활력확률보정계수`, `최대사용확률` | 행동 시작 시 사용 판정 값 |
| `전투당최대횟수`, `선택가중치` | 한 캐릭터의 사용 상한과 후보 간 가중치 |
| `조건대상`, `조건유형`, `조건연산자`, `조건값` | 무의미한 행동을 후보에서 제외하는 조건 |
| `행동문구`, `비고` | 전투 로그와 기획·구현 메모 |

초기값은 모든 스킬에 `기본사용확률=0.06`, `생활력기준값=30000`, `생활력확률보정계수=0.05`, `최대사용확률=0.16`, `전투당최대횟수=1`을 사용한다. 확률 값은 퍼센트 서식이 아닌 소수로 입력한다(`gviz` CSV가 `3.0%` 같은 표시 문자열을 내보내면 로더가 읽지 못한다).

```text
최종사용확률 =
  clamp(
    기본사용확률
    + clamp(생활력 ÷ 생활력기준값, 0, 2) × 생활력확률보정계수,
    0,
    최대사용확률
  )
```

생활력 0이면 6%, 기준값(30,000)이면 11%, 60,000 이상이면 최대 16%다. 판정에 성공한 뒤에는 현재 조건을 만족한 후보 중 `선택가중치`로 하나를 선택한다. 사용 판정은 후보를 고르기 전에 한 번만 하므로 모든 행의 사용 판정 값을 같게 유지한다.

`배틀생활스킬효과` 필드:

| 필드 | 설명 |
| --- | --- |
| `ID`, `배틀생활스킬ID`, `실행순서` | 효과 고유 ID, 부모 스킬, 적용 순서 |
| `효과유형`, `대상`, `계수기준`, `계수`, `고정값` | 공통 `BattleEffect`로 변환할 효과와 기본 수치 |
| `생활력비례`, `생활력기준값`, `생활력최소배율`, `생활력최대배율` | 생활력으로 연속 수치를 보정할지와 배율 범위 |
| `횟수`, `지속턴`, `상태효과ID`, `최대중첩` | 다단, 지속, 상태형 효과 정보 |
| `효과문구`, `비고` | 결과 로그와 단순화·엔진 확장 메모 |
| `선택그룹`, `선택가중치` | 무작위 결과형 효과. 같은 `선택그룹`의 행 중 하나만 가중치로 골라 실행하고, 빈 값인 행은 항상 실행 |

`계수기준` 값:

| 값 | 의미 |
| --- | --- |
| `공격력` | `공격력 × 계수`. 클래스 스킬 피해와 같은 방어·편차·치명타·추가타 적용 |
| `최대HP` | `최대HP × 계수` 회복 |
| `비율` | 상태 효과의 비율 값(`0.4`=40%) |
| `개수`, `턴` | `고정값`을 정수로 사용 |

`생활력비례=TRUE`인 효과는 다음 공식을 사용한다.

```text
생활력효과배율 =
  clamp(
    sqrt(생활력 ÷ 생활력기준값),
    생활력최소배율,
    생활력최대배율
  )

최종효과값 = 기본효과값 × 생활력효과배율
```

초기 범위는 `생활력기준값=30000`, `생활력최소배율=0.7`, `생활력최대배율=1.5`다. 피해·회복·피해 감소·강화·약화처럼 연속적인 수치에만 적용하고, 브레이크 칸 수·쿨다운 감소 턴·상태 제거 개수·확정 치명타·브레이크 면역에는 적용하지 않는다.

초안의 효과 배분은 다음과 같다.

| 역할 | 생활스킬 |
| --- | --- |
| 직접 피해 | 나무 베기, 추수, 낚시, 일상 채집(달걀) |
| 피해·브레이크 | 광석 캐기, 호미질, 핸디크래프트 |
| 피해·약화 | 곤충 채집, 일상 채집(거미줄) |
| 회복·해제 | 약초 채집, 물약 조제, 요리, 아르바이트, 일상 채집(사과) |
| 방어·회피 | 양털 깎기, 중갑 제작, 경갑 제작, 천옷 제작 |
| 다음 행동 강화 | 대장 기술, 목공, 매직 크래프트, 요리, 일상 채집(황금 네잎클로버) |
| 재사용 대기시간 보조 | 아르바이트 |

효과유형과 엔진 처리 방식:

| 효과유형 | 처리 |
| --- | --- |
| `피해`, `브레이크피해`, `회복`, `쿨다운감소` | 기존 효과유형 이름을 그대로 쓴다. `피해`와 `회복`은 `계수기준`(공격력·최대HP)을 읽는 생활스킬용 계산 경로를 추가한다. `쿨다운감소`는 기존과 같이 모든 스킬의 쿨다운을 줄인다 |
| `지속회복` | 기존 효과유형. 현재는 `고정값`과 `상태효과ID`가 필요하므로 `최대HP` 계수형을 지원하도록 확장한다 |
| `받는피해감소`, `주는피해증가`, `브레이크면역` | 기존 상태 효과 종류로 매핑한다. 값이 생활력에 따라 달라지므로 시트 행 대신 사용 시점에 파이터별 상태 정의(`life:효과ID`, 이름은 생활스킬 이름)를 만들어 지속턴·만료·합산을 기존 상태 처리로 한다 |
| `다음스킬피해증가`, `다음스킬치명타확률증가`, `다음스킬치명타피해증가` | 클래스 스킬 공격에만 더하는 상태로 구현한다(일반 공격·생활스킬·패시브 피해 제외). 지속턴으로 만료하지 않고, 다음 클래스 스킬 행동(파생 포함)이 끝나면 소모한다 |
| `다음피해감소` | 받는 피해 감소에 "피격 1회 후 소모" 규칙을 더해 구현한다. 다단 공격이면 그 공격 행동의 모든 타격에 적용하고, 피해를 받은 행동이 끝나면 소모한다. 지속턴 안에 피격되지 않으면 만료한다 |
| `다음행동피해감소` | 신규 `주는피해감소` 상태. 대상의 다음 주요 행동이 주는 피해를 감소시키고 그 행동이 끝나면 풀린다 |
| `회피확률증가` | 신규 `회피확률` 상태. 공격 판정마다 비율 확률로 회피한다. 상태가 없으면 회피 난수를 소비하지 않는다 |
| `해로운상태제거` | 신규 효과. 상대가 건 상태(디버프·지속 피해·브레이크)를 해로운 상태로 보고 무작위로 제거한다. 자신이 건 강화 상태는 해로운 상태가 아니다. `배틀상태효과`에 분류 열을 추가하지 않는다 |

알 수 없는 효과유형·계수기준을 조용히 무시해서는 안 되며 데이터 로드 오류로 처리한다.

`생활스킬` 시트는 원본 이름·설명·레벨별 정보를 계속 담당한다. `배틀생활스킬.생활스킬이름`은 원본 이름과 정확히 일치해야 하며, 중복·누락·알 수 없는 이름은 데이터 로드 오류로 처리한다. 전투 로그에도 이 이름을 그대로 표시한다. 현재는 개별 생활스킬 레벨을 가져오지 않으므로 효과 계산에는 캐릭터의 생활력 총합만 사용한다.

### 7.3 매력

매력은 기본 치명타율이나 선공 확률을 상시 높이지 않는다. 관중, 분위기, 행운과 퍼포먼스에 관련된 돌발 이벤트의 발생 확률만 높인다.

| 이벤트 | 시점·조건 | 효과 |
| --- | --- | --- |
| 관중의 환호 | 행동 시작 | 다음 공격 치명타 확률 +30% |
| 눈부신 포즈 | 상대 행동 시작 | 상대의 다음 행동 피해 20% 감소 |
| 행운의 앙코르 | 스킬 사용 직후 | 무작위 일반 스킬 쿨다운 1행동 감소 |

매력 이벤트는 순간적인 흐름과 연출 중심이며 생활력 이벤트와 효과 풀이 겹치지 않게 한다. 매력은 HP 조건 없이 매력만의 기준값·보정계수·확률 상한으로 독립 판정한다.

### 7.4 역할 요약

| 능력치 | 주 역할 | 하지 않는 역할 |
| --- | --- | --- |
| 전투력 | HP·공격력·방어력과 기본 승률 | 돌발 이벤트 종류 결정 |
| 생활력 | 저확률 배틀생활스킬의 사용과 효과 | 상시 HP·방어력 증가 |
| 매력 | 환호·퍼포먼스 이벤트 확률 | 상시 치명타·선공 증가 |

세 능력치는 모두 전투에 쓰이지만 같은 공식에 섞지 않는다.

### 8.2 데이터 분리 원칙

마비노기 모바일의 원본 정보와 몰리 배틀의 규칙을 같은 시트에 섞지 않는다.

| 구분 | 시트 | 책임 |
| --- | --- | --- |
| 원본 데이터 | `클래스` | 클래스 설명과 기본 장착 스킬·패시브 구성 |
| 원본 데이터 | `스킬` | 마비노기 모바일의 스킬명, 공식 설명, 태그와 파생 관계 |
| 원본 데이터 | `패시브스킬` | 마비노기 모바일의 패시브 스킬명, 공식 설명과 `기타` 수치 |
| 배틀 데이터 | `배틀스킬` | 자동전투에서 스킬을 선택하고 사용하는 규칙 |
| 배틀 데이터 | `배틀스킬효과` | 피해, 회복, 강화, 약화 등 스킬 실행 결과 |
| 배틀 데이터 | `배틀스킬파생` | 부모 스킬이 파생 스킬을 선택하거나 예약하는 규칙 |
| 배틀 데이터 | `배틀패시브` | 클래스가 상시로 갖는 패시브의 구현 여부(활성화) |
| 배틀 데이터 | `배틀패시브효과` | 패시브가 발동시점(전투시작·자원획득시 등)마다 실행하는 결과 |
| 배틀 데이터 | `배틀자원` | 클래스 전용 태세·게이지·중첩 자원의 공통 정의 |
| 배틀 데이터 | `배틀규칙` | 전투 공식의 공통 상수와 안전 상한 |
| 배틀 데이터 | `배틀돌발이벤트` | 매력 기반 돌발 이벤트의 조건과 확률 |
| 배틀 데이터 | `배틀돌발이벤트효과` | 돌발 이벤트가 발생했을 때 적용할 결과 |
| 원본 데이터 | `생활스킬` | 생활스킬 이름, 설명과 레벨별 채집·제작·가공 정보 |
| 배틀 데이터 | `배틀생활스킬` | 생활스킬의 사용 확률, 후보 조건, 선택 가중치와 행동 문구 |
| 배틀 데이터 | `배틀생활스킬효과` | 생활력 비례 피해·회복·강화·약화 등 실행 결과 |

`스킬.ID`와 `배틀스킬.ID`는 동일한 값을 사용한다. 원본에 존재하지만 몰리 배틀에서 아직 구현하지 않은 스킬은 `스킬`에만 두거나 `배틀스킬.활성화`를 `FALSE`로 둔다. `패시브스킬.ID`와 `배틀패시브.ID`도 동일한 관계를 따른다.

스킬 시트에는 `클래스ID`를 두지 않는다. 클래스에서 기본 장착 스킬 ID를 참조하고, 파생 스킬은 `스킬.부모스킬ID`를 따라 탐색한다. 패시브 시트도 `클래스ID`를 두지 않고, 클래스의 `패시브1~패시브6`에서 참조한다.

#### 배틀 시트 변경 권한과 관리 원칙

`클래스`와 `스킬`은 마비노기 모바일의 원본 정보를 보존하는 안정 영역으로 취급한다. 반면 이름이 `배틀`로 시작하는 시트는 몰리 배틀 엔진의 구현 데이터이므로, 앞으로의 기획과 개발에 필요하면 GPT와 Codex가 필드를 추가·변경·삭제하고 시트를 분리·통합할 수 있다.

변경할 때는 다음 원칙을 지킨다.

- 변경 전에 최신 시트 구조와 데이터를 읽고 기존 행을 보존한다.
- 기획서의 시트 명세, 로딩 순서, 검증 규칙도 같은 작업에서 함께 갱신한다.
- 필드 삭제·이름 변경·의미 변경은 로더 호환성에 영향을 주므로 마이그레이션 사항을 문서에 남긴다.
- 임시 자유문자열보다 명시적인 ID, 조건, 연산자와 참조 방식을 우선한다.
- 특정 클래스만을 위한 코드 예외보다 데이터로 표현할 수 있는 공통 구조를 우선한다.
- 시트 구조 변경 후 헤더, 참조 무결성, 필수 값과 기존 데이터 보존 여부를 다시 확인한다.

```text
클래스
 ├─ 스킬1~스킬5
 └─ 궁극기
      ↓ ID 참조
스킬 ── 동일 ID ── 배틀스킬
                       ├─ 배틀스킬효과
                       ├─ 배틀스킬파생 ── 파생 스킬
                       └─ 배틀자원 ── 태세·게이지·중첩
```

### 8.3 공통 ID 규칙

- ID는 영문 소문자 `snake_case`를 사용한다.
- 화면에 표시할 한글 이름을 키로 사용하지 않는다.
- 한 번 배포한 ID는 표시 이름이 바뀌어도 변경하지 않는다.
- 클래스 ID와 스킬 ID는 각각의 시트 안에서 유일해야 한다.
- 효과 ID는 `{스킬ID}_{두 자리 순번}` 형식을 기본으로 한다.
- 파생 규칙 ID는 `{부모스킬ID}_{파생 의미}` 형식을 기본으로 한다.
- `클래스.스킬1~궁극기`, `스킬.부모스킬ID`, `배틀스킬효과.스킬ID`, `배틀스킬파생.부모스킬ID`, `배틀스킬파생.파생스킬ID`는 모두 존재하는 ID만 참조해야 한다.

예시:

```text
클래스: bard
기본 스킬: bards_tale
파생 스킬: heroic_hymn
효과: heroic_hymn_01
파생 규칙: bards_tale_heroic
```

### 8.4 `클래스` 시트

클래스의 원본 설명과 기본 장착 스킬 세트를 정의한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `ID` | 문자열 | O | 클래스 고유 ID |
| `이름` | 문자열 | O | 사용자에게 표시할 클래스명 |
| `계열` | 문자열 | O | 전사, 궁수, 마법사, 힐러, 음유시인, 도적 계열 |
| `설명` | 문자열 | O | 마비노기 모바일 공식 클래스 설명 |
| `스킬1` | 스킬 ID | 클래스 구현 시 O | 첫 번째 기본 스킬 |
| `스킬2` | 스킬 ID | 클래스 구현 시 O | 두 번째 기본 스킬 |
| `스킬3` | 스킬 ID | 클래스 구현 시 O | 세 번째 기본 스킬 |
| `스킬4` | 스킬 ID | 클래스 구현 시 O | 네 번째 기본 스킬 |
| `스킬5` | 스킬 ID | 클래스 구현 시 O | 다섯 번째 기본 스킬 |
| `궁극기` | 스킬 ID | 클래스 구현 시 O | 궁극기 스킬 |
| `패시브1`~`패시브6` | 패시브 ID | 선택 | 클래스가 상시로 갖는 패시브. `스킬1~궁극기`와 달리 클래스마다 개수가 달라도 되므로 일부만 채워도 된다 |

`패시브1~6`은 `패시브스킬.ID`를 참조해야 하며 존재하지 않는 ID는 검증 실패로 처리한다. 다만 아직 `배틀패시브`가 구현되지 않은 ID를 참조하는 것은 허용하며(스킬의 `배틀스킬.활성화=FALSE`와 동일한 패턴), 이 경우 전투 시작 시 해당 패시브는 조용히 무시된다.

현재 음유시인 구성:

| 필드 | 스킬 ID | 표시 이름 |
| --- | --- | --- |
| `스킬1` | `string_shot` | 스트링 샷 |
| `스킬2` | `melody_shock` | 멜로디 쇼크 |
| `스킬3` | `triple_stroke` | 트리플 스트로크 |
| `스킬4` | `bards_tale` | 바즈 테일 |
| `스킬5` | `feign_death` | 죽은 척 하기 |
| `궁극기` | `battle_symphony` | 배틀 심포니 |

`클래스`에는 파생 스킬을 직접 나열하지 않는다.

현재 댄서 구성:

| 필드 | 스킬 ID | 표시 이름 |
| --- | --- | --- |
| `스킬1` | `natural_turn` | 내추럴 턴 |
| `스킬2` | `windmill` | 윈드밀 |
| `스킬3` | `front_step` | 프론트 스텝 |
| `스킬4` | `pirouette` | 피루엣 |
| `스킬5` | `ad_lib` | 애드리브 |
| `궁극기` | `finale` | 피날레 |

현재 음유시인 패시브 구성(`fever`, `improvised_performance`, `combat_mastery_support`, `battlefield_song`, `ecstatic_performance`, `vitality`)과 댄서 패시브 구성(`inspiration`, `encore`, `combat_mastery_swift`, `skilled_dance`, `closed_position`, `flower_and_butterfly`), 검술사 패시브 구성(`concentration`, `sword_stance`, `combat_mastery_risk`, `linked_swordsmanship`, `sharp_eye`, `first_strike`), 석궁사수 패시브 구성(`extra_action`, `driving_force`, `combat_mastery_risk_crossbow`, `quick_attack`, `extend_magazine`, `fortune_bolt`)의 구현 세부사항은 8.20을 참고한다.

### 8.5 `스킬` 시트

마비노기 모바일에서 확인한 원본 스킬 정보를 보존한다. 피해 계수, 쿨다운 턴, AI 우선순위 등 몰리 배틀 전용 수치는 기록하지 않는다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `ID` | 문자열 | O | 원본 및 배틀에서 공통으로 사용하는 스킬 ID |
| `이름` | 문자열 | O | 공식 스킬명 |
| `스킬구분` | 문자열 | O | `일반`, `궁극기`, `파생` 중 하나 |
| `부모스킬ID` | 스킬 ID | 파생만 O | 파생 스킬의 부모. 일반·궁극기는 빈 값 |
| `설명` | 문자열 | O | 게임에서 확인한 공식 설명 |
| `태그` | 문자열 | 선택 | 공식 태그를 쉼표로 구분하여 저장 |

음유시인 원본 데이터는 기본 스킬과 궁극기 6개, 파생 스킬 5개로 총 11개다.

```text
bards_tale
├─ heroic_hymn
├─ indomitable_overture
└─ song_of_hope

feign_death
├─ rising_windmill
└─ fine_tuning
```

### 8.6 `배틀스킬` 시트

자동전투에서 스킬을 후보로 만들고 선택하며 실행하기 위한 규칙을 정의한다. `ID`는 반드시 같은 원본 스킬의 `스킬.ID`와 일치해야 한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `ID` | 스킬 ID | `스킬.ID`와 동일한 고유 ID |
| `활성화` | 불리언 | `FALSE`이면 로드하되 행동 후보에서는 제외 |
| `행동분류` | 문자열 | 공격, 회복, 지원, 방해, 생존, 반격, 궁극기 등의 조합 |
| `대상유형` | 문자열 | 자신, 상대, 자신·상대 등 대상 선택 방식 |
| `기본쿨다운` | 정수 | 사용 후 다시 후보가 되기까지 필요한 주요 행동 수 |
| `최초쿨다운` | 정수 | 전투 시작 시 적용할 초기 쿨다운 |
| `사용우선순위` | 정수 | 조건을 만족한 후보끼리 비교할 우선순위 |
| `사용조건` | 문자열 | 로더가 등록된 조건 규칙으로 정규화할 값. 빈 값은 항상 사용 가능 |
| `자원유형` | 문자열 | 악상, 궁극기 게이지 등 사용하는 전용 자원 |
| `자원소모` | 숫자 | 사용 시 소모하는 자원 |
| `자원획득` | 숫자 | 사용 시 얻는 자원 |
| `궁극기여부` | 불리언 | 궁극기 전용 처리 여부 |
| `배틀설명` | 문자열 | 몰리 배틀에서 단순화한 동작 설명 |
| `사용문구` | 문자열 | 기본 전투 출력 템플릿 |
| `비고` | 문자열 | 원본과 다른 단순화 및 임시 결정 기록 |

먼저 쿨다운, 자원, 상태와 사용 조건을 검사한다. 직전 사용 스킬을 제외한 후보 중에서 `사용우선순위`를 완만한 가중치로 반영해 하나를 추첨한다. 모든 스킬은 `minimum_skill_cooldown` 이상의 쿨다운을 적용한다.

파생 전용 스킬은 독립 행동 후보로 선택하지 않는다. 현재 데이터에서는 기본쿨다운과 우선순위를 `0`으로 두고 `배틀스킬파생`을 통해서만 실행한다.

### 8.7 `배틀스킬효과` 시트

스킬 한 번이 발생시키는 결과를 효과 단위의 여러 행으로 정의한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `ID` | 문자열 | 효과 고유 ID |
| `스킬ID` | 스킬 ID | 효과를 소유한 `배틀스킬.ID` |
| `실행순서` | 정수 | 동일 스킬 안에서 효과를 처리할 순서 |
| `효과유형` | 문자열 | 피해, 회복, 지속피해, 상태효과, 브레이크피해, 브레이크면역, 기본공격변경 등 |
| `대상` | 문자열 | 자신 또는 상대 |
| `횟수` | 정수 | 동일 효과 반복 횟수 |
| `발동확률` | 실수 | `0.0~1.0`. `1`은 100% |
| `지속턴` | 정수 | 상태 및 지속 효과가 유지되는 턴 수 |
| `상태효과ID` | 문자열 | 적용하거나 검사할 상태 효과 ID |
| `최대중첩` | 정수 | 같은 상태 효과의 최대 중첩 수 |
| `조건대상` | 문자열 | 조건을 검사할 자신·상대·효과대상 |
| `조건유형` | 문자열 | 자원, 상태, HP비율 등 등록된 조건 종류 |
| `조건ID` | 문자열 | 검사할 자원·상태 ID. 필요 없는 조건은 빈 값 |
| `조건연산자` | 문자열 | `=`, `!=`, `>`, `>=`, `<`, `<=`, `보유`, `미보유` 중 하나 |
| `조건값` | 문자열 | 조건 비교값. 로더가 조건유형에 맞는 타입으로 변환 |
| `수치참조ID` | 문자열 | 효과 수치가 참조할 자원·상태 ID |
| `수치참조방식` | 문자열 | 현재값, 소모값, 중첩당가산 등 등록된 계산 방식 |
| `효과문구` | 문자열 | 효과 발생 시 출력할 문구 템플릿 |
| `비고` | 문자열 | 원본 수치와 단순화 근거 |
| `연속치명타배율` | 실수 | 선택 필드. `피해` 효과가 다단(`횟수>1`)일 때 N번째 타격(0부터 시작)의 치명타 확률에 이 값의 N제곱을 곱한다. 비워두면 `1`(변화 없음)로 처리한다. 거스팅 볼트처럼 "발사할수록 치명타 확률이 감소" 하는 원본을 표현할 때 사용한다(`0.75`면 두 번째 타격부터 0.75, 0.5625, …로 감소) |

효과를 `배틀스킬`과 분리하는 이유는 한 스킬이 서로 다른 대상과 조건을 가진 여러 결과를 순서대로 발생시키기 때문이다.

예를 들어 `희망의 송가`는 한 번의 사용으로 다음 효과들을 만든다.

```text
1. 상대에게 5회 피해
2. 자신 회복
3. 상대에게 현기증
4. 자신의 공격 속도 증가
5. 자신이 주는 피해 증가
6. 자신이 받는 피해 감소
```

이를 `효과1`, `효과2`처럼 가로 열에 넣으면 새 효과가 생길 때마다 스키마와 로더를 변경해야 한다. 별도 행으로 두면 효과 수가 달라도 동일한 로더가 `스킬ID`로 수집한 뒤 `실행순서`대로 처리할 수 있다.

피해와 회복의 기본 계산식:

```text
스킬 총 기본 피해 = 공격력 × 스킬별 전투 배율
다단 1회 기본 피해 = 스킬 총 기본 피해 ÷ 횟수
스킬 총 기본 회복 = 공격력 × 스킬별 회복 배율
다단 1회 기본 회복 = 스킬 총 기본 회복 ÷ 횟수
```

피해·회복·추가피해·브레이크피해는 각 반복마다 발동확률을 판정한다. 피해는 방어, 편차, 치명타와 사망도 개별 판정한다. 그 밖의 효과(`자원설정`·`자원증가`·`자원소모`·상태 부여·`쿨다운감소`·`다음행동지정` 등)는 효과 한 행마다 발동확률을 한 번 판정하고, 실패하면 그 행을 건너뛴다. 발동확률이 `1`이면 난수를 소비하지 않는다.

> 2026-09-23 수정: 이전 엔진은 피해 계열 이외의 효과에서 `발동확률`을 아예 읽지 않았다. 그래서 강철 쐐기의 비검 준비(25%/집중 시 50%)는 항상 100%로, 댄서 `inspiration`의 우아/정열 배정(`insp_01`·`insp_07`, 50%)은 항상 우아로 처리되었다(애드리브: 정열이 한 번도 발동하지 않음). 위 규칙으로 고친 뒤 두 경우 모두 시트 수치대로 동작한다.

`고정값`이 양수인 피해·회복 행은 공격력 계수 대신 해당 값을 **한 타격(또는 한 틱)의 기본 수치**로 사용한다(`고정값 × 횟수 × fixed_damage_scale`을 총량으로 삼아 다시 횟수로 나눈다). 실제 화면의 피해·회복 단위와 배틀 HP 단위 차이는 `배틀규칙.fixed_damage_scale`로 공통 환산한다. 따라서 타수와 고정 수치 구조는 보존하면서 밸런스만 시트에서 조정할 수 있다. `대상=주변적`은 1:1 자동전투에서 대상이 없으므로 처리하지 않는다.

> 2026-09-23 수정: 회복은 원래 `최대 HP × skill_heal_ratio(6%) × 횟수`로 계산했다. 이 공식은 `고정값`을 전혀 참조하지 않고 다단 횟수만큼 총량이 그대로 커지는 구조라, 음유시인의 `heroic_hymn`·`counter_overture`·`song_of_hope`(횟수 5) 는 매번 최대 HP의 30%를, `feign_death`(횟수 8)는 48%를 회복했다. 이 세 노래가 음유시인 행동의 약 20% 이상을 차지해 동일 전투력 기준 승률이 82~86%까지 치우치는 핵심 원인이었다(다른 클래스는 회복 효과가 아예 없다). 피해와 동일하게 "공격력 × 배율" 구조로 바꾸고 다단 총량을 횟수로 나누도록 고쳐, 다단이어도 총 회복량이 커지지 않게 했다. 새 배율은 `skill_heal_min_multiplier`(1.5)·`skill_heal_max_multiplier`(2.0)·`ultimate_heal_multiplier`(2.4, 현재 사용하는 궁극기는 없어 예비값)로 `배틀규칙`에 추가했고, 기존 `skill_heal_ratio`는 제거했다. 수정 후 동일 조건 시뮬레이션(2,000회 × 상대 3클래스)에서 음유시인 승률은 약 59~62%로 낮아져 다른 클래스와 비슷한 범위에 들어왔다.

현재 엔진은 `피해`, `회복`, `추가피해`, `지속피해`, `지속회복`, `조건부피해증가`, `자원설정`, `자원증가`, `자원소모`, 브레이크와 지속 상태 효과를 `실행순서`대로 처리한다. 피해와 회복은 각 반복마다 발동확률을 판정하며, 피해는 치명타·추가타까지 적용한다. 자원 조건은 같은 스킬의 앞선 효과로 자원이 바뀐 뒤에 판정하며, `소모중첩배율`·`현재값`·`최대값` 수치 참조를 지원한다.

`조건유형`은 `자원보유`, `분류자원미보유`, `상태효과보유`, `상태효과미보유`를 지원한다. `상태효과보유`·`상태효과미보유`는 `조건대상=상대`와 함께 쓰면 상대의 현재 상태를 검사할 수 있다(예: 상대가 브레이크 상태일 때만 추가 피해). 같은 스킬 안에서 앞선 효과가 방금 적용한 상태도 즉시 인식한다. `배틀스킬파생`의 `조건유형=상태효과보유`는 자신의 상태만 검사하며 별도로 이미 지원되고 있었다.

### 상태 효과 실행

`배틀상태효과` 시트는 효과 행의 `상태효과ID`를 실제 전투 보정으로 해석한다. 상태를 새로 추가할 때는 먼저 이 시트에 ID를 등록하고, 이후 `배틀스킬효과` 행에서 같은 ID와 지속 턴을 지정한다.

| 필드 | 설명 |
| --- | --- |
| `ID` | `배틀스킬효과.상태효과ID`와 일치하는 고유 ID |
| `이름` | 전투 로그에 표시할 상태명 |
| `효과유형` | `주는피해증가`, `받는피해증가`, `받는피해감소`, `치명타확률증가`, `받는치명타확률증가`, `받는치명타확률감소`, `받는방어무시`, `첫스킬타격소모`, `쿨다운감소`, `쿨다운증가`, `악상피해증가`, `기본공격피해증가`, `스킬피해증가`(`대상스킬ID` 필수), `브레이크`, `브레이크면역`, `없음`. 두 효과 이상을 함께 쓰면 `|`로 연결한다. |
| `값` | 숫자 하나. 비율 효과는 소수(`0.15` = 15%), 쿨다운감소·쿨다운증가는 행동당 가감되는 감소량. 효과유형이 여러 개면 모두 이 값을 공유한다. |
| `설명` | 배틀용 단순화 근거와 실제 적용 내용 |
| `대상스킬ID` | 쿨다운감소·쿨다운증가·스킬피해증가용 선택 필드. 쿨다운감소·쿨다운증가는 비어 있으면 기존처럼 보유자의 모든 스킬 쿨다운에 적용하고, 배틀 스킬 ID를 적으면 그 스킬의 쿨다운에만 추가로 적용한다. `스킬피해증가`는 반드시 적어야 하며, 사용한 스킬의 ID 또는 `스킬.부모스킬ID`가 일치할 때만 그 스킬의 피해에 더한다(연계 검술: `secret_sword`로 비검 파생 3종 지정). 여러 스킬에 걸치려면 스킬마다 상태를 하나씩 둔다(드라이빙 포스: `cb_driving_force_gusting`·`cb_driving_force_spreading`). |
| `시너지` | 선택 필드. [시너지] 옵션인 효과유형을 `|`로 적는다(예: `주는피해증가|받는피해감소`). 같은 효과유형의 시너지 옵션끼리는 보유 중인 것 가운데 **가장 높은 값 하나만** 적용하고, 시너지가 아닌 옵션은 그대로 합산한다. |
| `지속방식` | 선택 필드. `갱신`(기본, 비어 있으면 갱신) 또는 `누적`. `누적`이면 보유 중에 다시 받을 때 남은 턴에 지속턴을 더한다(음유시인 고양). |
| `효과별값` | 선택 필드. 복합 상태의 효과유형마다 값이 다르면 `1|0.1`처럼 효과유형 순서대로 적는다. 비어 있으면 모든 효과유형이 `값`을 쓴다. `값` 칸에 `|`를 섞지 않는 이유는 봇이 읽는 gviz CSV가 숫자 열의 문자열 셀을 빈 값으로 내보내기 때문이다. |
| `중첩자원ID` | 선택 필드. `배틀자원` ID를 적으면 이 상태의 `값`에 보유자가 가진 그 자원의 현재 보유량(중첩 수)을 곱해 적용한다. 자원이 0이면 효과도 0이다. "중첩당 +N%" 패시브(날카로운 눈, 드라이빙 포스, 퀵 어택, 연계 검술)나 "표식 보유 중에만 켜지는 효과"(검술사 집중: `sw_focus` 0/1)를 표현할 때 쓰며, 보통 `발동시점=전투시작`의 영구 상태로 한 번 부여하고 자원 증감으로 세기를 조절한다. |

`쿨다운증가`는 `쿨다운감소`와 대칭인 효과유형으로, 상대의 이동·행동 속도 저하를 단순화할 때 쓴다. 매 행동 시작마다 쿨다운은 기본으로 1씩 감소하는데, `쿨다운증가` 보유자는 그 감소분에서 값을 뺀 만큼만(최소 0까지) 줄어든다. 즉 남은 쿨다운을 늘리지는 않고, 값이 기본 감소분(1)과 같거나 크면 보유 중에는 해당 쿨다운이 전혀 줄지 않는다(석궁사수 `슬라이딩 스텝`의 `cb_slowed` 참고).

현재 적용한 기준은 현기증(지속 피해만, 받는 피해 증가 없음), 약점 노출(첫 스킬 공격 치명타 확률 +50%·방어도 50% 무시 후 소모), 고양(용맹)(쿨다운 추가 감소·연주 스킬 위력 +10%), 고양(희망)(쿨다운 추가 감소·[시너지] 주는 피해 +10%·[시너지] 받는 피해 -10%), 고양(반격)(쿨다운 추가 감소), 죽은 척(받는 피해 -40%)이다. 2026-09-24 이전의 현기증 받는 피해 +15%는 원본 근거가 없는 임시값이라 제거했다(GitHub Issue #5). 공격·이동·스킬 속도 증가는 턴제 자동전투에 맞춰 다음 행동의 스킬 쿨다운을 한 번 추가 감소시키는 방식으로 단순화한다. `정밀 조율`은 활성 악상이 적용된 스킬만 +10%, `원거리 기본 공격`은 좌표 없는 전투에서 다음 일반 공격 +20%로 처리한다. 상태는 적용·해제 시 이름과 남은 턴을 전투 로그에 출력한다.

### 지속피해와 브레이크

`지속피해`는 `상태효과ID`와 `지속턴`을 반드시 지정한다. 적용된 대상의 매 행동 시작 시 한 번 피해를 주며, 지속피해는 치명타·추가타를 일으키지 않는다. `고정값`이 있으면 보유자 턴마다 `고정값 × fixed_damage_scale`을 주고(현기증 5040×2턴, 두려움 5602×2턴), 없으면 공격력 배율 총량을 `횟수`(유지 시간 전체의 총 타격 수)로 나눈다.

`지속회복`은 `상태효과ID`·`지속턴`·`고정값`을 지정한다. 보유자 턴마다 `고정값 × fixed_damage_scale × (1 + 부여 시점 시전자의 회복량증가)`만큼 회복하며, 이 틱은 `회복적용시` 패시브를 발동시키지 않는다(활력이 자기 회복으로 다시 발동하지 않게 한다).

`조건부피해증가`는 스킬이 효과를 실행하기 **전** 상태로 조건을 판정해, 조건이 맞으면 같은 스킬의 모든 `피해` 행에 `1 + 고정값/100`을 곱한다(멜로디 쇼크: 현기증 보유 시 고정값 50 = ×1.5). 행 자체는 다른 효과를 내지 않는다.

`첫스킬타격소모` 효과유형을 가진 상태(약점 노출)는 스킬 피해의 첫 타격이 판정되는 순간 소모된다. 다단 스킬도 첫 타격에만 보정이 붙고, 일반 공격·패시브 피해는 소모하지 않는다. `받는방어무시`는 그 타격에 반영되는 대상 방어력을 값만큼 줄인다.

`브레이크피해`는 대상의 브레이크 게이지를 `고정값`만큼 올린다. `배틀규칙.break_gauge_maximum`에 도달하면 `break_broken` 상태가 적용되고, 대상은 `break_duration_turns` 동안 다음 행동을 잃는다. `브레이크면역` 상태가 있으면 게이지가 오르지 않는다. 브레이크 상태는 받는 피해 +25%도 함께 적용한다.

브레이크 게이지는 `고정값=1`을 한 칸으로 하는 다단 자원이다. `break_gauge_maximum=3`이므로 기본적으로 3칸을 채워야 브레이크가 걸린다. 대부분의 브레이크피해 효과는 한 번에 1칸을 채우지만, 궁극기급으로 설계된 스킬은 `고정값=3`처럼 더 큰 값을 넣어 한 번에 게이지를 모두 채울 수 있다.

> 2026-09-22 조정: 짧은 전투(주요 행동 최대 10회)에서 브레이크 한 번이 승패를 사실상 결정짓는 문제가 보고되어, `break_gauge_maximum`을 1→3, `break_duration_turns`를 2→1, `max_major_actions`를 10→20으로 함께 조정했다. 브레이크가 걸리는 빈도 자체는 유지하되(한 번의 히트만으로 즉시 걸리지 않게 하고) 걸렸을 때의 행동 상실 페널티를 줄여, 전체 판의 스윙 크기를 완화하는 방향이다. 이 값들은 확정이 아니라 시뮬레이션으로 재조정할 실험값이다.

`대상해제` 상태는 `배틀규칙.target_release_evasion_chance` 확률로 다음 상대 공격을 회피한다. 현재 `죽은 척`은 받는 피해 감소와 대상 해제를 함께 적용한다.

### 8.8 `배틀스킬파생` 시트

원본 파생 관계는 `스킬.부모스킬ID`에 보존하고, 이 시트에는 몰리 배틀에서 실제로 어떤 조건과 순서로 파생 스킬을 실행할지 기록한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `ID` | 문자열 | 파생 규칙 고유 ID |
| `부모스킬ID` | 스킬 ID | 파생을 시작하는 스킬 |
| `파생스킬ID` | 스킬 ID | 실행할 파생 스킬 |
| `발동방식` | 문자열 | `무작위`, `조건`, `대체` 등 선택 방식. `대체`는 부모 대신 자식 스킬을 실제 사용으로 기록한다. |
| `가중치` | 숫자 | 무작위 선택 시 상대 가중치 |
| `발동확률` | 실수 | 조건 성립 후 실제 발동 확률 |
| `우선순위` | 정수 | 여러 파생 조건이 동시에 성립할 때의 평가 순서. 큰 값 우선 |
| `조건유형` | 문자열 | 악상, 피격·다운, 생존 등 검사 대상 |
| `조건값` | 문자열 | 조건을 만족시키는 값 |
| `중복허용` | 불리언 | 같은 파생 스킬의 연속 선택 허용 여부 |
| `실행시점` | 문자열 | 즉시, 재사용 시, 상태만료 시 등 |
| `비고` | 문자열 | 임시 규칙과 원본 차이 |

현재 음유시인의 배틀 파생 초안:

- `바즈 테일`: 보유 악상에 따라 용맹의 찬가·반격의 서곡·희망의 송가 중 하나로 **대체**되는 선택 스킬이다. 악상이 없으면 희망 악상을 얻은 뒤 희망의 송가로 대체한다. 바즈 테일에 연결된 기본 범위 피해·현기증·회복·고양은 선택된 실제 연주곡의 효과로 처리하며, 전투 로그에는 바즈 테일을 출력하지 않는다. 2026-09-24 이전에는 부모 행(`bards_tale_02~05`)이 남아 연주곡 효과와 중복 실행되었으므로 삭제하고 악상 선택 행만 남겼다(GitHub Issue #5).
- 연주곡(용맹의 찬가·반격의 서곡·희망의 송가)은 곡마다 다른 버프 `고양(용맹)`·`고양(반격)`·`고양(희망)`을 준다. 원본은 회복 1회마다 고양 3초가 붙어 5회면 15초이므로, 연주곡 사용 시 한 번에 3턴을 부여하고 이미 있으면 남은 턴에 3턴을 더한다(`지속방식=누적`). 각 고양은 공격 속도(쿨다운 1회 추가 감소)와 원본 고양 회복(3초마다 1374, 반격은 3384 → 턴당 2배)을 지속 회복으로 갖는다.
- `죽은 척 하기`: 죽은 척 상태가 끝나면 다음 행동을 라이징 윈드밀로 교체한다.
- `죽은 척 하기`: 상태가 유지되는 중 동일 스킬을 다시 사용하면 쿨다운과 관계없이 즉시 라이징 윈드밀로 전환한다. Discord 자동전투에서는 버튼 입력을 받지 않으므로, 이 경로는 엔진의 재사용 파생 규칙으로 보존한다.

악상은 생성된 뒤 다른 악상으로 교체되기 전까지 유지한다. `바즈 테일`은 보유 악상에 맞는 곡으로 대체되며, `정밀 조율`은 이처럼 악상이 실제로 적용된 연주곡에만 피해 +10%를 적용한다.

현재 엔진은 `무작위`, `조건`, `확률`, `대체` 발동방식과 `즉시`, `재사용 시`, `상태만료 시` 실행시점을 처리한다. 즉시 파생은 부모 효과가 모두 처리된 뒤 판정하므로, 같은 스킬이 자원을 얻어 조건을 만족시키는 구성도 가능하다. `대체` 파생은 부모를 전투 로그에 기록하지 않고 실제 선택된 자식 스킬을 행동 제목으로 기록하며, 부모의 공통 효과도 그 제목 아래에 출력한다. 상태만료 파생은 예약된 다음 주요 행동을 대체한다. 피격 반격과 일반적인 다음 행동 예약은 이후 상태 효과로 확장한다.

### 8.9 `배틀자원` 시트

클래스가 사용하는 태세, 게이지와 중첩을 공통 형식으로 정의한다. 스킬 효과는 자원 ID를 참조하여 생성·소모·조건 검사·수치 계산을 수행한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `ID` | 문자열 | 자원 고유 ID |
| `이름` | 문자열 | 사용자와 기획자에게 표시할 이름 |
| `분류` | 문자열 | 태세, 자원, 중첩 등 처리 방식 |
| `최대값` | 숫자 | 최대 보유량. 미확정 값은 `0`으로 두고 활성화 전에 확정 |
| `초기값` | 숫자 | 전투 시작 시 보유량 |
| `지속턴` | 정수 | 자동 소멸까지의 턴. 전투 동안 유지하면 `0` |
| `중첩방식` | 문자열 | 가산, 교체, 상호배타 등 |
| `전투종료시제거` | 불리언 | 전투 스냅샷 종료 시 제거 여부 |
| `설명` | 문자열 | 동작과 제약 설명 |

현재 댄서 확장용 자원은 `dance_grace`(우아), `dance_passion`(정열), `rhythm`(리듬), `performance_heat`(공연의 열기)다. 우아와 정열은 상호배타 태세이며, 아직 캡처만으로 확정할 수 없는 최대값은 0으로 표시한다. 태세에 맞는 내추럴 턴·윈드밀·프론트 스텝·피루엣과 애드리브 파생은 리듬을 생성한다. 피날레는 공연의 열기와 템포를 최대 중첩으로 설정하고(템포는 2026-09-25 GitHub Issue #6에서 `finale_02`로 추가, 템포 획득·최대치 도달 패시브가 함께 발동) `피날레의 고조` 상태로 5턴 동안 쿨다운을 추가 감소시키며, 재사용 마무리는 열기를 모두 소모한 뒤 소모량 비례 추가 피해를 준다.

> 2026-09-23 검토: 승률 검사 결과 리듬이 어떤 효과에서도 소비·참조되지 않는 죽은 자원이었다. 피날레에 리듬 보유량 비례 추가 피해(1스택당 200, 사용 후 전량 소모)를 추가해 실제 소비처를 만들었다(`finale_rhythm_bonus`/`finale_rhythm_reset`). 같은 검토에서 `tempo`(템포)는 `performance_heat`와 역할이 완전히 겹치는데도 실제로는 최대값이 0인 자원을 참조해 매번 0으로 설정되는 죽은 효과(`finale_02`)만 갖고 있었음을 확인해, 자원과 해당 효과 행을 함께 제거했다. 이 ID는 이후 완전히 다른 용도(댄서 패시브 `inspiration`이 부여하는 템포 중첩 자원, 8.20.4 참고)로 재사용됐으니 혼동하지 않는다.
>
> 또한 `dance_grace`·`dance_passion` 자체를 부여하는 효과 행이 시트 전체에 없다는 것도 함께 확인했다. 즉 내추럴 턴·윈드밀·프론트 스텝·피루엣의 "태세일 때 리듬 추가 생성" 조건은 항상 거짓이라 리듬은 애드리브 파생(무조건 발동)에서만 쌓인다. 어느 스킬이 원본에서 우아·정열 태세를 실제로 부여하는지 원본 설명만으로 확인되지 않아 이번에는 수정하지 않았다(GitHub Issue #4).
>
> 2026-09-23 후속 수정(GitHub Issue #4): 처음에는 Issue #4가 제안한 대로 "내추럴 턴·피루엣 사용 시 우아, 윈드밀·프론트 스텝 사용 시 정열을 자신에게 부여"하는 행을 추가했으나, 이는 `스킬.설명`을 다시 대조하는 과정에서 근거가 없다는 것이 확인되어 되돌렸다. 네 스킬의 원본 설명은 모두 "**우아/정열 상태일 때** 리듬을 추가 생성한다"로, 이미 그 태세일 때의 **보너스 조건**일 뿐 스킬 자신이 태세를 만든다는 문장이 아니다. 반면 댄서 패시브 `inspiration`의 원본 설명은 "**전투 시 영감을 얻어 우아 또는 정열 상태 중 하나가 된다**... 템포를 얻을 때마다 새로운 영감을 획득"이라고 명시하므로, 우아·정열을 실제로 배정하는 것은 이 패시브뿐이라는 확정 근거가 된다(8.20.4 참고). 애초에 "2:2 그룹핑이 우연이 아니다"라는 정황 증거만으로 스킬 쪽에 태세 부여를 추가한 것이 판단 착오였다.
>
> 같은 재검토에서 `ad_lib.기타` 필드에 "정열·우아는 **새로운 영감 획득 시 20% 확률로 화합 동작 발동**"이라는 캡처 수치가 있는 것도 확인했다. `배틀스킬파생`의 `ad_lib_harmony` 행(발동방식=확률, 발동확률=0.2, 조건유형=새로운영감)은 원래부터 이 수치를 정확히 반영한 것이었으므로 그대로 되돌렸다. 댄서 패시브 `skilled_dance`("리듬을 통해서 템포 2중첩을 얻게 될 경우, 다음 애드리브가... 화합 동작을 취한다")는 이 20% 확률과 별개로 템포가 최대 중첩에 도달했을 때만 화합을 확정시키는 상위 규칙으로 이해해, `ad_lib_harmony_guaranteed`라는 별도 행(발동방식=조건, 조건유형=자원보유, 조건값=dance_harmony_ready=1, 우선순위 300으로 20% 확률 행의 200보다 높음)을 새로 추가했다. 즉 템포 2중첩 표식이 없으면 평소처럼 20% 확률로만 화합이 나오고, 표식이 있으면 확정으로 화합이 나온다.

> 2026-09-25 수정(GitHub Issue #6): 위의 `조건유형=새로운영감`은 엔진이 확률 파생이면 무조건 참으로 판정해, 새로운 영감과 무관하게 모든 애드리브에 20%가 적용되고 있었다. 영감 패시브가 템포를 얻을 때 `dance_new_inspiration`(새로운 영감) 표식을 설정하고(`insp_10`), `ad_lib_harmony`는 `조건유형=자원보유`, `조건값=dance_new_inspiration=1`로 이 표식이 있을 때만 20%를 판정한다. 애드리브 파생 세 가지(`ad_lib_passion_03`·`ad_lib_grace_03`·`ad_lib_harmony_04`)는 화합 여부와 관계없이 표식을 소모하므로, 새로운 영감 하나는 다음 애드리브 한 번에만 기회를 준다. 확정 화합 행(`ad_lib_harmony_guaranteed`, 우선순위 300)을 먼저 판정하는 순서는 그대로다. 엔진의 `새로운영감` 예외 처리는 제거했고, `배틀스킬파생`의 조건유형은 이제 `자원보유`·`상태효과보유`·`악상`만 허용한다(그 밖의 값은 로딩 단계에서 거부).

음유시인 악상은 `bard_valor`(용맹), `bard_hope`(희망), `bard_counter`(반격) 3종이다. 모두 `분류=악상`, `최대값=1`, `중첩방식=상호배타`로 정의한다. 악상 생성 효과에는 `조건유형=분류자원미보유`, `조건ID=악상`을 지정한다. 따라서 이미 악상이 있으면 새 악상 생성 효과는 실행되지 않고 기존 악상을 유지한다.

현재 생성 규칙은 멜로디 쇼크 → 용맹, 트리플 스트로크·바즈 테일·배틀 심포니 → 희망, 죽은 척 하기 → 반격이다. `배틀스킬파생.조건값`의 자원 조건은 `bard_hope=1`처럼 비교식을 권장하며, 기존 호환을 위해 `bard_hope`만 적어도 1 이상 보유로 판정한다. 이후 확인되는 실제 조건은 같은 방식으로 효과 행만 추가해 확장한다.

자원 `최대값`이 `0`이면 상한 없는 누적 자원이다. `중첩방식=상호배타`인 같은 `분류`의 자원은 새 값이 생기는 즉시 기존 값이 0이 된다. `지속턴`이 양수이면 보유자의 다음 주요 행동 기준으로 감소하며 0이 되면 제거한다. `중첩방식=교체`인 지속 자원은 보유 중에 같은 값으로 다시 설정되면 지속턴만 새로 채운다(값이 그대로이므로 `자원획득시` 패시브는 다시 발동하지 않는다. 검술사 집중 재진입, 석궁사수 엑스트라 액션, GitHub Issue #1). `가산` 자원은 최대 중첩에서 더 얻어도 값이 그대로라 지속턴을 갱신하지 않는다(댄서 템포 등).

#### 궁극기 게이지

`배틀스킬.자원유형`에 정확히 일치하는 `배틀자원.ID`가 없으면 로더는 같은 `분류`를 가진 자원이 정확히 하나일 때 그 자원으로 대신 연결한다(`ResolveSkillResource`). 모든 클래스의 궁극기는 `자원유형=궁극기 게이지`를 공유하므로, `배틀자원`에 `ID=ultimate_gauge`, `분류=궁극기 게이지`인 자원 하나만 두면 각 궁극기 스킬 행을 따로 고치지 않고도 비용 검사가 연결된다. 기본기 스킬도 같은 `자원유형=궁극기 게이지`와 `자원획득`을 지정해 사용할 때마다 이 자원을 채운다. 궁극기가 한 판에서 아예 나오지 않거나 너무 자주 나오면 기본기들의 `자원획득` 값을 함께 조정한다 — 궁극기의 `자원소모`(보통 300) 하나만 바꿔서는 밸런스가 맞지 않는다.

### 8.10 댄서 스킬 모델링 기준

댄서는 음유시인의 단순 피해·상태 구조에 더해 태세, 조건부 자원 생성, 기본 공격 변경, 브레이크, 다중 파생과 자원 중첩 참조를 사용한다.

- `배틀스킬효과`의 `조건대상`, `조건유형`, `조건ID`, `조건연산자`, `조건값`으로 조건부 효과를 표현한다.
- 다른 자원의 현재값이나 소모량으로 효과 수치를 계산할 때 `수치참조ID`, `수치참조방식`을 사용한다.
- 효과 유형은 필요에 따라 `자원증가`, `자원소모`, `상태전환`, `기본공격변경`, `브레이크피해`, `브레이크면역` 등을 사용한다.
- `배틀스킬파생.우선순위`로 여러 파생 조건이 동시에 성립할 때 선택 순서를 결정한다. 숫자가 클수록 먼저 평가하는 것을 기본 규칙으로 한다.
- 애드리브의 우아·정열·화합 동작은 한 셀에 조건문으로 넣지 않고 부모 스킬과 파생 스킬로 나눈다. 화합 발동은 일반 태세 파생보다 높은 우선순위를 갖는다.
- 피날레의 첫 사용과 재사용 마무리는 부모·파생 스킬로 나누고, 마무리 피해는 소모한 `performance_heat` 중첩을 수치 참조한다.
- 이동 거리와 범위는 공간 좌표가 없는 초기 배틀에서는 원본 `스킬.설명`에 보존하되, 직접적인 배틀 수치로 사용하지 않는다.

현재 입력된 댄서 데이터:

| 구분 | 수량 | 내용 |
| --- | ---: | --- |
| 기본 스킬·궁극기 | 6 | 내추럴 턴, 윈드밀, 프론트 스텝, 피루엣, 애드리브, 피날레 |
| 파생 스킬 | 4 | 애드리브 정열·우아·화합, 피날레 마무리 |
| 배틀 효과 | 26 | 피해, 자원, 태세 조건, 브레이크, 기본 공격 변경, 궁극기 강화, 리듬 소비 |
| 파생 규칙 | 4 | 애드리브 3종 선택과 피날레 재사용 |

댄서 캡처에는 기준 공격력이 표시되지 않았으므로 현재 피해량은 `계수=0`, `고정값=화면 표시 수치`로 저장한다. 기준 공격력을 확인하면 공격력 계수로 변환한다. 재사용 대기 시간은 6초=1턴 가이드라인(8.11)에 따라 내추럴 턴 1턴, 윈드밀·프론트 스텝·애드리브 2턴, 피루엣 3턴으로 변환했다(2026-09-24 이전: 2·4·3·3·5행동).

애드리브는 화합형을 우선순위 200으로 먼저 판정하고, 실패하면 현재 우아·정열 태세에 맞는 파생을 우선순위 100으로 실행한다. 피날레 마무리는 `performance_heat` 보유 중 재사용할 때 실행하며 기본 피해 20,690과 소모 중첩당 추가 피해를 별도 효과로 계산한다. 원본 중첩당 13,793은 배틀용으로 250(최대 1,250)으로 낮춰 저장했다(`finale_finish_02` 비고).

### 8.11 음유시인 배틀 데이터 기준

음유시인 데이터는 공격력 `56,024`인 캐릭터의 스킬 화면 캡처를 기준으로 작성했다. 피해 및 회복 계수는 다음과 같이 역산한 추정값이다.

```text
추정 계수 = 화면 표시 수치 ÷ 56,024
```

예시:

| 스킬 | 표시 수치 | 저장 계수 |
| --- | ---: | ---: |
| 스트링 샷 | 37,536 | `0.670` |
| 트리플 스트로크 | 28,012 × 3 | `0.500`, 3회 |
| 용맹의 찬가 | 16,022 × 5 | `0.286`, 5회 |
| 라이징 윈드밀 | 14,263 × 4 | `0.255`, 4회 |
| 파인 튜닝 마지막 타격 | 67,564 | `1.206` |
| 배틀 심포니 타격 | 50,298 | `0.898` |

이 계수는 원본 게임 공식을 확정한 값이 아니다. 장비, 버프, 반올림, 숨겨진 고정값이 포함되었을 수 있으므로 몰리 배틀의 초기 밸런스 초안으로만 사용한다.

#### 턴 환산 가이드라인 (2026-09-24)

초 단위 원본 시간은 **6초 = 1턴, 소수점 올림**으로 환산한다. 모든 클래스의 상태·자원 지속턴과 스킬 재사용 대기 시간에 같은 기준을 쓴다. 가이드라인일 뿐이며, 원본에 시간이 없거나 밸런스상 필요하면 다르게 정하고 비고에 근거를 남긴다(예: 활력 재발동 45초 → 8턴, 배틀 심포니·피날레처럼 원본 시간이 없는 효과는 기존 값 유지).

| 원본 시간 | 턴 | 적용 예 |
| --- | ---: | --- |
| 1~6초 | 1 | 죽은 척 4초, 피루엣 원거리 5초, 바즈 테일 재사용 6초, 강철 쐐기 재사용 4초 |
| 7~12초 | 2 | 현기증 9초, 슬라이딩 스텝 둔화 8초, 날카로운 눈·퀵 어택 10초, 스트링 샷 재사용 12초 |
| 13~18초 | 3 | 약점 노출 15초, 고양 15초(회복 5회×3초), 템포·선수필승 15초, 멜로디 쇼크 재사용 15초 |
| 19~24초 | 4 | 집중 20초(집중력 100을 초당 5 소모), 연계 검술 20초, 죽은 척 재사용 19초 |
| 25~30초 | 5 | 전장의 노래·파인 튜닝 강화 30초, 간파 재사용 25초 |
| 43~48초 | 8 | 활력 대상별 재발동 45초 |

이전 환산(현기증 9초→3턴, 약점 노출 15초→4턴 등)은 약 3초=1턴이라 쿨다운과 지속 시간이 전반적으로 길었다. 배틀 계수와 함께 확정 규칙이 아니며, 시뮬레이션으로 평균 주요 행동 수와 승률을 측정한 뒤 조정한다.

`heroic_hymn`·`counter_overture`·`song_of_hope`의 회복 효과와 `feign_death`의 회복 효과는 2026-09-23에 최대 HP 비율 기반에서 공격력 배율 기반으로 계산 방식을 바꿨다. 원인과 수정 내용은 8.7(회복 공식과 신규 배틀규칙)을 참고한다.

### 8.12 검술사 배틀 데이터 기준

검술사는 `steel_thrust`(강철 쐐기), `scabbard_strike`(칼집 치기), `gale_slash`(질풍 베기), `secret_sword`(비검), `insight`(간파), `single_flash`(일섬, 궁극기) 6개 배틀 스킬과 `secret_sword`의 파생 3종(`secret_sword_steel_thrust`, `secret_sword_scabbard_strike`, `secret_sword_gale_slash`)으로 구성한다. 원본 스킬 데이터는 `스킬` 시트의 `기타` 필드에 기록된 인게임 표시 수치를 그대로 참고했다.

- `강철 쐐기`는 명중 시 확률적으로 `sw_secret_ready`(비검 준비) 자원을 얻는다. 원본의 "비검 사용 가능 효과 부여 확률 25%(집중 시 50%)"는 `배틀스킬효과`에 `자원증가` 행 두 개로 분리해 반영한다. 하나는 `조건유형=자원보유`로 `sw_focus`(집중) 보유를 검사하고, 다른 하나는 `조건유형=분류자원미보유`로 `sw_focus`가 없을 때만 발동하도록 상호 배타적으로 구성했다.
- `강철 쐐기`, `칼집 치기`, `질풍 베기`는 사용할 때마다 각각 `sw_last_steel`, `sw_last_scabbard`, `sw_last_gale`(분류=최근기술, 상호배타) 표식을 남긴다. `비검`은 `sw_secret_ready`를 소모해야만 후보가 되는 선택형 스킬이며 자체 효과가 없다. `배틀스킬파생`에서 `발동방식=대체`, `조건유형=자원보유`로 세 표식 중 남아 있는 것을 검사해 대응하는 비검 파생 스킬로 대체한다. 이는 음유시인의 `bards_tale` 악상 선택과 동일한 구조다.
- `간파`는 기본 피해에 더해 원본의 "빈틈 포착 조건: 브레이크 및 스킬 사용 완료" 시 추가 피해·쿨다운 감소를 얻는 조건부 구조를 갖는다. `배틀스킬효과`가 `조건대상=상대`, `조건유형=상태효과보유`, `조건ID=break_broken`을 지원하게 된 뒤로는 "상대가 브레이크 상태" 조건을 그대로 반영했고(`insight_break_bonus`), "스킬 사용 완료"처럼 엔진이 아직 판정할 수 없는 나머지 조건은 낮은 확률(`발동확률=0.3`)의 별도 행(`insight_residual_bonus`)으로 근사했다. 사용 중에는 받는 피해 감소(`sw_insight_guard`)와 브레이크 면역(`sw_insight_break_immune`)을 1턴 부여한다.
- `집중`은 `sw_focus_gauge`(집중력 게이지, 최대값 100)와 `sw_focus`(집중 상태 보유 표식, `배틀자원.지속턴=4`, `중첩방식=교체`) 하나로 판정한다. 집중 효과인 `sw_focus_precision`(치명타 확률 +40%)·`sw_focus_crit_damage`(치명타 피해 +30%)·`sw_focus_haste`(질풍 베기 전용 쿨다운 매 행동 1회 추가 감소)·`sw_sharp_eye_evasion`(급소 회피)은 모두 `중첩자원ID=sw_focus`인 영구 상태로 전투 시작에 부여되어, `sw_focus`를 보유한 동안에만 켜지고 `sw_focus`가 사라지면 함께 꺼진다(2026-09-25 GitHub Issue #1 후속. 이전에는 스킬·패시브가 상태를 각각 4턴 부여해, 집중 중 재진입 시 `sw_focus`만 먼저 끝나는 불일치가 있었다). 비검: 강철 쐐기(집중력 30)와 간파(집중력 35)가 원본의 "집중력 회복량"만큼 게이지를 채우고, 게이지가 100에 도달하면 패시브 `concentration`이 `sw_focus`를 얻게 하고 게이지를 초기화한다. 일섬은 사용 직후 `sw_focus`를 게이지 없이 즉시 얻는다(원본의 "즉시 획득 효과: 집중", "사용 후 획득 효과: 집중 태세"는 같은 집중으로 통합). 어느 경로든 이미 집중 중이면 `sw_focus` 지속턴이 4로 다시 채워진다. 집중이 끝나면 강철 쐐기의 비검 준비 확률도 25% 조건으로 돌아간다. `sw_focus_haste`는 `배틀상태효과.대상스킬ID=gale_slash`로 원본의 "집중 상태 시 질풍 베기 재사용 대기 시간 감소(10→5초)"를 질풍 베기에만 적용하고, 간파·칼집 치기·강철 쐐기의 쿨다운은 집중만으로 추가 감소하지 않는다.
- 모든 피해 효과는 댄서와 동일하게 `고정값`에 화면 표시 수치를 그대로 넣고 `배틀규칙.fixed_damage_scale`로 환산한다. 검술사 캡처는 공격력 기준이 표시되지 않았을 뿐 아니라, 다른 클래스 캡처보다 훨씬 높은 전투력의 캐릭터에서 얻은 것으로 보여 원본 수치 간 배율 차이가 매우 컸다. 일섬(원본 68,420), 비검: 칼집 치기 2타(원본 19,060), 비검: 질풍 베기 마무리(원본 17,593), 간파의 추가 피해(원본 15,394)는 다른 검술사 스킬과 5~8배 가까이 벌어져 있어, 다른 클래스의 기본기 대비 배율을 참고해 각각 20,000 / 13,190 / 8,000 / 7,000으로 낮춰 저장했다. 원본 표시 수치는 각 행의 `비고`에 남겨 두었다.
- 칼집 치기와 비검: 칼집 치기는 서로 다른 두 타격 값을 그대로 보존하기 위해 `횟수=1`인 `피해` 행 두 개로 나누어 입력했다. 균등하게 나누어지는 다른 다단 공격과 달리, 이 두 스킬은 타격마다 공식 표시 수치가 다르기 때문이다.
- 비검: 강철 쐐기의 "뒤이어 강한 바람을 일으켜 범위 피해"는 `기타`에 별도 수치가 없어 단일 타격(고정값 17,105)으로만 반영했다. 원본이 실제로 2회 타격인지는 확인되지 않았다.
- 궁극기 일섬은 다른 클래스와 동일하게 `자원유형=궁극기 게이지`, `자원소모=300`을 쓰며, 검술사의 기본기 4종(강철 쐐기·칼집 치기·질풍 베기·간파)이 사용할 때마다 같은 자원에 150씩 채운다. `비검`은 이미 `sw_secret_ready`를 자원으로 쓰고 있어 궁극기 게이지에는 기여하지 않는다.

고정 난수로 검술사·음유시인·댄서 세 클래스를 총당 400회씩 오프라인 시뮬레이션한 결과 예외 없이 완주했고, 검술사의 모든 기본 스킬과 비검 파생 3종이 최소 1회 이상 관측되었으며 궁극기(일섬·배틀 심포니·피날레) 모두 실제로 발동했다. 동일 전투력 기준 검술사 승률이 다른 두 클래스보다 여전히 높게 나타나(음유시인전 약 72%, 댄서전 약 63%) 다른 클래스보다 강한 편이므로, 이후 10,000회 단위 시뮬레이션으로 밸런스를 추가 조정할 대상으로 남겨 둔다.

### 8.13 석궁사수 배틀 데이터 기준

석궁사수는 `buster_shot`(버스터 샷), `shock_explosion`(쇼크 익스플로전), `sliding_step`(슬라이딩 스텝), `gusting_bolt`(거스팅 볼트), `spreading_bolt`(스프레딩 볼트), `hell_fire`(헬 파이어, 궁극기) 6개 배틀 스킬로만 구성한다. 원본 `스킬` 시트에 파생 스킬이 등록되어 있지 않아 `배틀스킬파생`에는 석궁사수 관련 행을 추가하지 않았다.

- 원본 설명은 다섯 기본기 중 세 개(버스터 샷·쇼크 익스플로전·슬라이딩 스텝)가 "강화 볼트 탄창을 장전"하고, 나머지 두 개(거스팅 볼트·스프레딩 볼트)가 그 탄창을 소모한다고 밝힌다. 이를 새 배틀자원 `cb_bolt_magazine`(강화 볼트 탄창, 분류=자원, 최대값=3)으로 표현했다. 최대값 3은 인게임 표시(탄창 3칸)로 확인한 값이다.
- 장전 3종은 각 스킬의 효과 행에서 `자원증가`로 `cb_bolt_magazine`을 1씩 올리고, 궁극기 게이지는 `배틀스킬.자원유형=궁극기 게이지`·`자원획득=150` 필드로 기존 클래스와 동일하게 적립한다. 소모 2종(거스팅 볼트·스프레딩 볼트)은 반대로 `배틀스킬.자원유형=cb_bolt_magazine`·`자원소모=1`로 탄창 보유를 사용 조건으로 걸었기 때문에, 궁극기 게이지 적립은 효과 행의 `자원증가`(`ultimate_gauge`, 150)로 대신했다. 헬 파이어는 사용 시 `자원설정`으로 `cb_bolt_magazine`을 3(최대값)으로 되돌려 "전량 재장전"을 표현한다.
- 원본 재사용 대기 시간이 명시된 버스터 샷(10초)·쇼크 익스플로전(8초)·슬라이딩 스텝(8초)은 기존 클래스와 같은 환산 비율로 4·3·3턴을 부여했다. 반면 거스팅 볼트·스프레딩 볼트는 원본에 재사용 대기 시간이 없고 탄창 소모로만 제한되므로 `기본쿨다운=0`으로 두었다(엔진이 `minimum_skill_cooldown=2`를 항상 적용하므로 실질적으로 최소 2턴은 쉰다).
- 쇼크 익스플로전의 "기절시킨다"는 브레이크 상태 자체가 다음 행동을 잃게 만드는 기존 구조를 그대로 사용해 `브레이크피해` 1칸으로 반영했다(칼집 치기·윈드밀과 동일한 단순화).
- 버스터 샷의 자기 강화 "이동 속도 증가 10%·지속 5초·최대 중첩 2"는 검술사의 속도 계열 변환 관례를 따라 쿨다운 감소 상태(`cb_haste`, 값 1, 2턴)로 단순화했다. 최대 중첩 2는 엔진이 상태 지속 시간에 배수 개념을 지원하지 않아 반영하지 못했다.
- 슬라이딩 스텝의 자기 강화 "받는 대미지 감소 20%·지속 5초"는 `cb_guard`(받는피해감소 0.2, 2턴)로 반영했다. 상대에게 거는 "이동 속도 감소 30%·8초"는 초기에는 대응하는 배틀 효과유형이 없어 반영하지 못했으나, 이후 `쿨다운감소`와 대칭인 `쿨다운증가` 효과유형을 엔진에 추가해 `cb_slowed`(값 1, 3턴)로 반영했다. 매 행동 감소분(기본 1)과 값이 같아 지속 중에는 대상의 쿨다운이 전혀 줄지 않는 형태로 단순화했다(8.7 참고).
- 모든 피해 효과는 검술사·댄서와 동일하게 `고정값`에 화면 표시 수치 계열의 값을 넣고 `배틀규칙.fixed_damage_scale`로 환산한다. 다만 초기 밸런스 시뮬레이션(2,000회 × 상대 3클래스)에서 원본 표시 수치를 그대로 입력했을 때 석궁사수 승률이 94.1%로 크게 치우쳤다. 원인은 원본 캡처가 다른 클래스보다 훨씬 높은 기준 전투력에서 얻은 것으로 보여 절대값이 과도했기 때문으로 판단해, 다른 클래스의 기본기 배율에 맞춰 각 값을 낮췄다. 1차로 대폭 낮춘 값은 반대로 30.0%까지 떨어져 다시 소폭 올렸다. 최종적으로 버스터 샷 18,023→11,000, 슬라이딩 스텝 18,023×2→6,300×2, 거스팅 볼트 3,950×10→2,000×10, 스프레딩 볼트 22,467→20,000, 헬 파이어 화살 3,456×9→1,000×9·폭발 110,091→22,500으로 보정했다(쇼크 익스플로전 8,814는 원본값 그대로 유지). 각 행의 `비고`에 원본 수치와 보정 과정을 남겼다.
- 거스팅 볼트의 "발사할수록 감소하는 치명타 확률(발사마다 0.75배)"은 `배틀스킬효과`에 다단 피해 전용 `연속치명타배율` 필드를 추가해 반영했다(`gusting_bolt_01`에 `0.75` 지정, 8.7 참고). 두 번째 타격부터 치명타 확률이 0.75, 0.5625, …로 누적 감소한다.
- 원본에 언급된 "엑스트라 액션 발동 시 추가 발사"(버스터 샷·쇼크 익스플로전·슬라이딩 스텝)와 "드라이빙 포스 발동 시 위력 강화"(거스팅 볼트·스프레딩 볼트)는 스킬 설명만으로는 발동 조건을 알 수 없었으나(GitHub Issue #3), 이후 `패시브스킬` 시트에 석궁사수 패시브가 추가되면서 둘 다 석궁사수 패시브임이 확인되었다. 엑스트라 액션은 "강화 볼트 소모 스킬 사용 시 다음 장전 스킬의 공격 횟수 2배", 드라이빙 포스는 "동일한 소모 스킬을 4초 안에 연속 사용 시 피해 +30%(최대 2스택)"이며 8.20.4에 반영했다.
- `cb_bolt_magazine` 최대값 3은 인게임에서 탄창이 3개로 표시되는 것을 확인해 확정했다(2026-09-23, GitHub Issue #3). 헬 파이어의 "강화 볼트 장전: 3개 탄창"(=전량 재장전)과도 일치한다. 패시브 `extend_magazine`의 "강화 볼트 장전 스킬 최대 스택 수: 2"는 장전 **스킬의 충전 횟수**이지 탄창 보유량이 아니다. 헬 파이어의 "엠블럼 장착 필요" 조건은 캡처 당시 앰블럼을 장착하지 않아 표시되었을 뿐 실제 사용 조건이 아니므로 반영하지 않는다.

현재 입력된 석궁사수 데이터:

| 구분 | 수량 | 내용 |
| --- | ---: | --- |
| 기본 스킬·궁극기 | 6 | 버스터 샷, 쇼크 익스플로전, 슬라이딩 스텝, 거스팅 볼트, 스프레딩 볼트, 헬 파이어 |
| 파생 스킬 | 0 | 원본 스킬 시트에 파생 관계 없음 |
| 배틀 효과 | 17 | 피해, 브레이크 피해, 자원 증가·설정, 쿨다운증가 |
| 파생 규칙 | 0 | 없음 |
| 신규 배틀자원 | 1 | `cb_bolt_magazine`(강화 볼트 탄창) |
| 신규 배틀상태효과 | 3 | `cb_haste`(가속), `cb_guard`(회피 기동), `cb_slowed`(둔화) |

고정 난수로 4개 클래스를 상대별 2,000회씩(총 12,000전) 오프라인 시뮬레이션한 결과 예외 없이 완주했고, 석궁사수의 모든 기본 스킬과 궁극기가 최소 1회 이상 발동했다. 동일 전투력 기준 석궁사수의 통합 승률은 약 51~61%로 4개 클래스 중 상위권이었다(쿨다운증가·연속치명타배율 반영 전후로 큰 차이는 없었다). 이 시점에는 음유시인이 약 82~86%, 댄서가 약 19~20%로 나타났는데, 이는 석궁사수 추가와 무관하게 기존에도 보고되어 있던(8.12 참고) 음유시인 회복 공식 문제와 댄서 리듬 자원 미사용 문제였다. 이후 별도 검토로 두 문제를 수정했고(8.9, 8.11 참고), 수정 후에는 4개 클래스 승률이 약 26~61% 범위로 모였다(댄서는 자기 회복 수단이 없다는 구조적 차이가 남아 있어 여전히 가장 낮다). 정밀한 클래스 간 밸런스는 10,000회 단위 시뮬레이션으로 추후 조정한다는 기존 방침(10.3, 17장 참고)을 따른다.

### 8.14 데이터 로딩과 검증

Google Sheets 전체를 하나의 버전으로 취급한다. 일부 시트만 성공한 상태로 캐시를 교체하지 않는다.

권장 로딩 순서:

1. `배틀규칙`을 로드하고 필수 키, 값 타입과 허용 범위를 검사한다.
2. `클래스`를 로드하고 클래스 ID의 유일성을 검사한다.
3. `스킬`을 로드하고 스킬 ID와 부모 관계를 검사한다.
4. `배틀자원`을 로드하고 자원 ID, 최대값, 초기값과 중첩 규칙을 검사한다.
5. `배틀스킬`을 로드하고 모든 ID가 `스킬`에 존재하는지 검사한다.
6. `배틀스킬효과`를 `스킬ID`로 그룹화하고 실행순서, 조건과 자원 참조를 검사한다.
7. `배틀스킬파생`의 부모와 파생 ID, 우선순위를 검사한다.
8. `패시브스킬`을 로드하고 패시브 ID의 유일성을 검사한다.
9. `배틀패시브`를 로드하고 모든 ID가 `패시브스킬`에 존재하는지 검사한다.
10. `배틀패시브효과`를 `패시브ID`로 그룹화하고 실행순서·발동시점·조건과 자원·스킬 참조를 검사한다.
11. `배틀돌발이벤트`를 로드하고 능력치 유형, 시점, 조건과 확률 범위를 검사한다.
12. `배틀돌발이벤트효과`를 `이벤트ID`로 그룹화하고 효과 참조와 실행순서를 검사한다.
13. `클래스`의 스킬1~궁극기, 패시브1~6 참조가 모두 유효한지 검사한다.
14. 파생 관계에 순환 참조가 없는지 검사한다.
15. 검증이 모두 성공하면 불변 스냅샷으로 만들어 현재 캐시와 원자적으로 교체한다.
16. 실패하면 오류를 한글 로그로 남기고 마지막 정상 캐시를 계속 사용한다.

필수 검증 항목:

- 필수 셀 누락
- ID 중복 및 존재하지 않는 참조
- `스킬구분=파생`인데 부모스킬ID가 비어 있는 경우
- 일반·궁극기 스킬에 부모스킬ID가 들어간 경우
- 활성화된 배틀 스킬에 효과도 파생 규칙도 없는 경우
- 계수, 확률, 횟수, 지속턴이 허용 범위를 벗어난 경우
- 같은 스킬 안에서 실행순서가 중복된 경우
- 파생 스킬이 일반 행동 후보로 들어가는 경우
- 파생 관계의 순환 참조
- 효과와 파생 규칙이 존재하지 않는 자원·상태 ID를 참조하는 경우
- 조건 연산자와 조건값 타입이 맞지 않는 경우
- 자원의 초기값이 최대값을 초과하거나 상호배타 태세가 동시에 초기화되는 경우
- 같은 부모 스킬의 파생 규칙에서 우선순위가 충돌하는 경우
- 필수 `배틀규칙`이 없거나 값유형·값 범위가 잘못된 경우
- 돌발 이벤트의 능력치 유형이 생활력·매력 이외인 경우
- 기본확률·보정계수·최대확률이 0~1 범위를 벗어나거나 기본확률이 최대확률보다 큰 경우
- 돌발 이벤트 효과가 존재하지 않는 이벤트 ID를 참조하는 경우
- 활성화된 돌발 이벤트에 효과가 하나도 없는 경우
- 클래스의 패시브1~6이 존재하지 않는 패시브 ID를 참조하는 경우
- 활성화된 배틀패시브에 효과가 하나도 없는 경우
- 배틀패시브효과의 발동시점이 정해진 값(전투시작, 자원획득시, 자원최대치도달시, 자원소진시, 브레이크발생시, 스킬사용완료시, 스킬적중완료시, 치명타적중시, 치명타미적중시, 피격시, 회복적용시) 밖인 경우
- 배틀상태효과의 스킬피해증가에 대상스킬ID가 없는 경우
- 배틀상태효과의 중첩자원ID가 존재하지 않는 자원을 참조하는 경우
- 배틀패시브효과의 대상스킬ID·대상자원ID가 존재하지 않는 스킬·자원(또는 자원 분류)을 참조하는 경우

행 순서는 의미를 갖지 않으며 반드시 ID와 실행순서로 처리한다. 열 위치를 숫자로 고정하지 말고 헤더 이름으로 열을 매핑한다. 알 수 없는 헤더는 경고 후 무시할 수 있지만, 필수 헤더가 없으면 로드를 실패시킨다.

### 8.15 자동 행동 선택

스킬은 **조건식 AI와 행동 횟수 기반 쿨다운**으로 사용한다.

```text
클래스의 기본 스킬 ID 확인
→ 활성화된 배틀스킬 조회
→ 쿨다운·자원·HP·상태 조건 검사
→ 독립 행동이 아닌 파생 스킬 제외
→ 사용 가능한 후보 생성
→ 우선순위와 가중치로 행동 결정
→ 후보가 없으면 일반 공격
→ 선택한 스킬 효과를 실행순서대로 적용
→ 파생 규칙이 있으면 조건에 맞는 파생 스킬 실행 또는 예약
```

후보 선택 규칙은 다음과 같다.

1. 조건, 자원 비용, 쿨다운과 행동분류를 검사해 사용할 수 없는 스킬을 제거한다.
2. 직전 사용 스킬을 제외한다. 다른 후보가 없을 때만 직전 스킬을 다시 후보로 둔다.
3. 남은 후보에서 `사용우선순위`를 완만하게 반영해 하나를 추첨한다.
4. 후보가 없으면 일반 공격을 사용한다.
5. 같은 전투 데이터와 주입된 난수 시퀀스에서는 같은 결과가 나와야 한다.

현재 시트의 `사용조건`, `행동분류`, `대상유형`은 기획자가 읽기 쉬운 문자열이다. 개발 시 명시적인 enum과 구조화된 조건 모델로 한 번 변환한 뒤 엔진에는 정규화된 값만 전달한다. 문자열 부분 일치로 조건을 실행하지 않으며 알 수 없는 값은 데이터 전체 검증 실패로 처리한다.

### 8.16 `배틀규칙` 시트

전투 엔진의 공통 상수를 키와 값으로 관리한다.

| 필드 | 설명 |
| --- | --- |
| `ID` | 코드에서 참조하는 규칙 키 |
| `분류` | 전투능력치, 피해, 치명타, 추가타, 종료, 돌발이벤트 |
| `값유형` | number, integer, boolean, string |
| `값` | 실제 설정값 |
| `설명` | 값의 의미와 단위 |

필수 규칙이 없거나 타입·범위를 벗어나면 배틀 데이터 로드를 실패시킨다.

### 8.17 `배틀돌발이벤트` 시트

매력 돌발 이벤트의 조건과 확률을 정의한다. 생활력 이벤트 행은 배틀생활스킬 도입과 함께 제거했다.

| 필드 | 설명 |
| --- | --- |
| `ID`, `이름`, `활성화` | 이벤트 식별과 사용 여부 |
| `능력치유형` | 생활력 또는 매력 |
| `발동시점` | 행동시작, 행동종료, 피격직전, 상태효과적용직후, 스킬사용직후 등 |
| `기본확률` | 능력치 보정 전 확률 |
| `능력치기준값`, `능력치보정계수` | 능력치를 확률로 변환하는 값 |
| `최대확률` | 판정 확률 상한 |
| `전투당최대횟수` | 동일 이벤트의 전투 내 횟수 제한 |
| `조건대상`, `조건유형`, `조건값` | 후보가 되기 위한 조건 |
| `대상유형` | 효과를 받을 대상 |
| `이벤트문구` | 발생 사실을 알리는 문구 |
| `비고` | 밸런스와 구현 메모 |

### 8.18 `배틀돌발이벤트효과` 시트

이벤트가 발생했을 때의 결과를 행 단위로 정의한다.

| 필드 | 설명 |
| --- | --- |
| `ID`, `이벤트ID`, `실행순서` | 효과 식별, 부모 이벤트와 적용 순서 |
| `효과유형`, `대상` | 처리기와 적용 대상 |
| `계수기준`, `계수`, `고정값`, `횟수` | 효과 수치 계산 |
| `지속턴`, `상태효과ID`, `최대중첩` | 상태형 효과 정보 |
| `효과문구`, `비고` | 출력과 구현 메모 |

스킬 효과와 데이터 책임은 분리하지만 구현 시에는 공통 `BattleEffect` 모델로 변환하여 같은 효과 처리기를 재사용한다.

### 8.19 전투 데이터 스냅샷 계약

- 기존 13개 배틀 관련 시트(`배틀상태효과` 포함)에 원본 `생활스킬`과 `배틀생활스킬`·`배틀생활스킬효과`를 더한 16개 시트를 한 묶음으로 로드한다. `생활스킬`은 배틀생활스킬 이름 검증에만 쓴다. 배틀생활스킬 시트에 행이 없으면 생활스킬 판정을 하지 않는다.
- 이후 갱신도 8.14 검증을 모두 통과한 묶음만 원자적으로 교체한다. 갱신 주기는 기존 Sheets 데이터 갱신 경로가 담당하며 전투 엔진이 직접 원격 시트를 읽지 않는다.
- 각 배틀은 시작 순간의 불변 데이터 스냅샷 참조를 끝날 때까지 유지한다. 도중에 캐시가 갱신되어도 진행 중 전투에는 섞이지 않는다.
- 엔진 입력은 `CharacterBattleSnapshot`, `BattleDataSnapshot`, 난수 공급자이며 Discord·DB·Google Sheets 객체를 직접 참조하지 않는다.
- 프로덕션 난수 시드는 저장하지 않는다. 테스트에서는 고정 난수 공급자를 주입해 경계 조건을 재현한다.
- 유효한 마지막 캐시가 하나도 없으면 배틀만 사용할 수 없다고 안내하고 봇의 다른 기능은 계속 동작한다.

### 8.20 패시브 스킬

패시브는 `스킬1~5·궁극기`처럼 행동으로 선택되지 않고, 전투 시작부터 끝까지 클래스가 항상 갖고 있는 능력이다(2026-09-23 도입). 스킬과 동일한 3단 구조(`패시브스킬` 원본 → `배틀패시브` 구현 여부 → `배틀패시브효과` 실제 수치)를 따르되, "발동시점"이라는 개념이 추가된다.

#### 8.20.1 `배틀패시브` 시트

| 필드 | 설명 |
| --- | --- |
| `ID` | `패시브스킬.ID`와 동일 |
| `활성화` | FALSE면 로드하되 전투에 적용하지 않음(스킬과 동일 패턴) |
| `비고` | 원본 대비 단순화 근거 |

#### 8.20.2 `배틀패시브효과` 시트

`배틀스킬효과`와 같은 컬럼(`효과유형`, `대상`, `고정값`, `횟수`, `발동확률`, `지속턴`, `상태효과ID`, `조건대상~수치참조방식` 등)에 아래 컬럼을 더한다.

| 신규 필드 | 설명 |
| --- | --- |
| `발동시점` | `전투시작`, `자원획득시`, `자원최대치도달시`, `자원소진시`, `브레이크발생시`, `스킬사용완료시`, `스킬적중완료시`, `치명타적중시`, `치명타미적중시`, `피격시`, `회복적용시` 중 하나 |
| `대상스킬ID` | `스킬사용완료시`·`스킬적중완료시`·`치명타적중시`·`치명타미적중시`를 특정 스킬로 한정할 때 사용 |
| `대상자원ID` | `자원획득시`·`자원최대치도달시`·`자원소진시`를 특정 자원 ID 또는 자원 분류로 한정할 때 사용 |
| `재발동대기턴` | 선택 필드. 이 효과가 한 번 발동한 뒤 보유자의 N턴 동안 다시 발동하지 않는다(활력 8턴). 비어 있으면 대기 없음 |

`효과유형`은 `배틀스킬효과`와 같은 처리기를 그대로 재사용한다(피해·회복·자원증가·상태효과 등). 패시브 전용으로 `다음행동지정`(대상의 다음 주요 행동을 `상태효과ID`에 적은 스킬로 강제 지정) 효과유형과, `조건유형=HP비율`(조건대상의 HP 비율을 `조건연산자`·`조건값`으로 비교) 조건을 새로 추가했다. `회복적용시`에서 `HP비율`을 쓰면 회복 **전** 체력으로 판정한다. 패시브 전용 `조건유형=효과미발동`(조건ID=같은 패시브·발동시점에서 먼저 실행되는 효과 ID)은 이번 트리거 발동에서 그 효과가 발동확률 판정에 실패했거나 조건이 맞지 않아 실행되지 않았을 때만 참이다. 현재 보유 자원과 무관하게 "A 50%, 실패하면 B"를 고를 때 쓴다(댄서 새로운 영감). 로더는 같은 패시브·발동시점에 더 앞선 실행순서의 효과 ID만 허용한다.

`치명타적중시`·`치명타미적중시`는 스킬·일반 공격·패시브 피해의 **타격마다** 판정 결과에 따라 발동한다(다단 공격은 타격 수만큼). `대상스킬ID`를 지정하면 그 스킬의 타격에만 반응하므로 일반 공격·패시브 피해에는 반응하지 않는다. `피격시`는 상대의 공격(스킬·일반 공격·패시브 피해)으로 실제 피해를 받았을 때 피격자 관점에서 한 번 발동한다(지속 피해·추가피해 효과는 제외). 패시브가 주는 `피해`는 일반 공격이 아니므로 상대의 `받는기본공격피해감소`가 적용되지 않는다.

`스킬적중완료시`는 `스킬사용완료시`와 같은 시점이지만, 방금 사용한 스킬(파생이면 부모 효과 포함)이 상대에게 실제로 피해를 줬을 때만 발동한다. 피해가 없는 스킬, 대상 해제로 회피된 공격, 일반 공격에서는 발동하지 않는다. 같은 스킬 완료에서 `스킬적중완료시`를 먼저, `스킬사용완료시`를 나중에 발동하므로, 스킬 완료 때 새로 얻는 표식(간파 후 질풍태세 준비)을 그 스킬 자신이 바로 소모하지 않는다(질풍태세 "다음 공격", 2026-09-25 GitHub Issue #1).

`자원획득시`는 해당 자원의 값이 **이전보다 늘어날 때마다** 발동한다(상호배타·1개 상한 자원은 이미 보유 중이면 재설정이 무시되므로 실질적으로 최초 획득 때만 발동한다). `자원최대치도달시`는 값이 `배틀자원.최대값`에 새로 도달하는 순간, `자원소진시`는 값이 0으로 내려가는 순간(지속턴 만료로 자연 소진되는 경우 포함) 발동한다.

#### 8.20.3 전투시작 트리거와 영구 상태

`발동시점=전투시작`으로 상태 효과를 부여하면 일반 상태(`지속턴`만큼 매 행동 감소하다 소멸)와 달리 **영구 상태**로 취급되어 전투가 끝날 때까지 유지된다. `지속턴` 값은 이 경우 읽지 않는다. 회복량·최종 피해처럼 여러 패시브가 공유할 수 있는 새 상태효과유형 5종을 추가했다: `회복량증가`, `멀티히트피해증가`(횟수>1인 피해 효과에만 적용), `치명타피해증가`, `받는기본공격피해감소`(일반 공격에만 적용), `추가타확률증가`.

#### 8.20.4 클래스가 상시로 갖는 패시브

클래스의 `패시브1~6`이 참조하는 패시브 중 `배틀패시브`가 없거나 `활성화=FALSE`인 것은 조용히 무시된다(스킬과 동일 패턴). `배틀패시브.활성화=TRUE`인 패시브만 `Fighter.Passives`로 로드되어 전투시작·이벤트 트리거에 반응한다.

현재 음유시인 6종:

- `fever`(피버): 대상 수에 비례한 강화는 1:1 배틀이라 항상 최솟값(타격 피해 +3%, 연주 피해 +2%)으로 고정하고 상시 적용했다. "스트링 샷·멜로디 쇼크 적중 시 궁극기 게이지 추가"는 명중이 아닌 치명타 적중으로 단순화했다.
- `improvised_performance`(즉흥 연주): 브레이크 발생 시, 멜로디 쇼크·연주 스킬(`heroic_hymn`·`counter_overture`·`song_of_hope`) 사용 완료 시 `다음행동지정`으로 바즈 테일 변주곡을 강제한다. 원칙상 파생·돌발 이벤트는 행동을 소비하지 않아야 하나, 엔진에 무행동 삽입 경로가 없어 다음 행동을 대체하는 것으로 단순화했다. 악상 획득 시 쿨다운 감소는 "악상에 따라 변화하는 스킬"의 범위가 불명확해 보유자 전체 쿨다운 1턴 감소로 단순화했다.
- `combat_mastery_support`(전투 숙련: 지원): 회복량 +10%, 멀티히트 피해 +3%(상시). 레벨 30 어시스트 해금 문구는 구현 범위에서 제외했다(항상 만렙 가정).
- `battlefield_song`(전장의 노래): 악상 획득 시 치명타·추가타 확률 +3%(30초→5턴). 원문 최대 3중첩은 엔진이 상태 수치 중첩을 지원하지 않아 단일 값으로 단순화했다.
- `ecstatic_performance`(광란의 연주): 치명타 피해 +20%(상시). "피버 보유 중" 조건은 피버가 상시 패시브라 상시 적용으로 단순화했다.
- `vitality`(활력): 회복 전 체력이 40% 미만일 때 회복을 받으면(`조건유형=HP비율`) `지속회복`으로 2730×8을 2턴에 나눠 회복한다(턴당 10920). 대상별 재발동 대기 45초는 `재발동대기턴=8`로 표현하고, 지속 회복 틱은 활력을 다시 발동시키지 않는다. 2026-09-24 이전에는 즉시 회복한 활력이 `회복적용시`를 다시 일으켜 HP가 40%를 넘을 때까지 스스로 반복 발동했다(GitHub Issue #5). 멜로디 쇼크·파인 튜닝 치명타 적중 시 스트링 샷과 같은 `weak_point_exposure`(첫 스킬 공격 치명타 확률 +50%·방어도 50% 무시, 3턴)를 부여한다. 아군 회복 조건은 1:1이라 자기 회복으로 해석했다.

현재 댄서 6종:

- `inspiration`(영감): 전투시작 시 우아·정열 중 하나를 무작위로 배정한다(발동확률 0.5 + `분류자원미보유` 조합, 음유시인 악상 생성과 동일 패턴). 이것이 README 8.9에서 지적했던 "우아·정열을 실제로 부여하는 효과가 없던" 갭을 메운다. 리듬이 임계값(5, 초기값)에 도달하면 신규 자원 `tempo`(템포, 최대 2중첩)를 얻고 리듬을 모두 소모한다. 템포를 얻을 때마다(리듬·피날레 모두) 쿨다운·최종 피해 보너스(`dance_tempo_haste`/`dance_tempo_power`, 중첩당 배율은 엔진 한계로 단일 고정값 단순화)를 부여하고, 새로운 영감으로 우아/정열을 50:50으로 다시 정하고(`insp_07` 우아 50%, 실패 시 `insp_08`이 `조건유형=효과미발동`으로 정열 확정), 체력을 회복하며(3676), 애드리브 화합 판정용 `dance_new_inspiration` 표식을 남긴다(`insp_10`).
  - 2026-09-25 수정(GitHub Issue #6): `insp_08`의 예전 조건(`분류자원미보유 태세`)은 이미 우아일 때 우아 50%가 실패해도 정열로 바뀌지 못해, 한 번 우아가 되면 전투 끝까지 우아였다. 또 템포 강화 상태(`insp_04`/`insp_05`)는 리듬 획득 시점에 걸려 피날레로 얻은 템포에는 적용되지 않았으므로 템포 획득 시점으로 옮겼다.
- `encore`(앵콜): 템포가 최대 중첩(2)에 도달하면(리듬·피날레 모두) `dance_encore_ready` 표식을 얻고, 이후 템포가 소진될 때(자연 만료 포함) 광역 피해(19749×6)를 낸 뒤 표식을 소모한다. 스킬 레벨 총합은 항상 120(최댓값)으로 고정했다. 광역 피해는 1:1이라 단일 대상에 적용한다. 원본의 "추는 동안 기본 공격·스킬 사용 불가"와 "피날레 중 템포 종료 시 피날레 종료 후 발동"은 생략하고, 템포 소진 시 행동을 쓰지 않는 즉시 피해로 단순화했다(GitHub Issue #6에서 결정, `배틀패시브.비고`에도 기록).
- `combat_mastery_swift`(전투 숙련: 쾌속): 받는 기본 공격 피해 -10%, 연타 피해 +5%(상시). 레벨 30 어시스트 해금 문구는 제외했다.
- `skilled_dance`(숙련된 댄스): 템포가 최대 중첩(2)에 도달하면 `dance_harmony_ready` 표식을 얻는다. 원문은 "리듬을 통해서" 얻은 경우로 한정하지만, GitHub Issue #6의 결정에 따라 피날레로 템포가 최대가 된 경우에도 같은 표식을 얻는다. `배틀스킬파생`에 `ad_lib_harmony_guaranteed`(조건=`자원보유 dance_harmony_ready=1`, 우선순위 300) 행을 추가해, 이 표식이 있으면 원래의 20% 확률 행(`ad_lib_harmony`, 우선순위 200, `ad_lib.기타`의 캡처 수치)보다 먼저 판정되어 다음 애드리브의 화합이 확정된다(표식이 없으면 평소처럼 20% 확률). 화합 스킬 자체의 효과(`ad_lib_harmony_03`)가 표식을 소모하므로 한 번만 확정된다. 표식을 얻는 순간 `ad_lib`의 쿨다운을 사실상 초기화하는 상태(`dance_harmony_haste`, 대상스킬ID=`ad_lib`)도 함께 부여한다. 최대 사용 횟수 증가, 앙콜 중 이동 속도 증가는 대응 매커니즘이 없어 구현하지 못했다.
- `closed_position`(클로즈드 포지션): 최종 피해 +10%, 단일 대상 시 +15% 추가(상시). 1:1 배틀은 항상 단일 대상이므로 둘 다 상시 적용해 합 +25%다.

- `AttackEvaded`
- `CooldownReduced`
- `CounterActivated`
- `CharacterDefeated`
- `BattleEnded`
- `SurpriseEventTriggered`
- `SurpriseEventEffectApplied`

### 9.2 메시지 생성 원칙

- 전투 계산과 메시지 생성을 분리한다.
- 전투 중에는 이미지와 애니메이션을 사용하지 않는다.
- 전투 이벤트 하나에 여러 메시지 템플릿을 둘 수 있다.
- 동일한 행동이 반복되어도 표현이 지나치게 반복되지 않게 한다.
- 공격 피해량, 회복량, 치명타, 추가타, 상태 효과는 표시한다.
- 턴 시작에 발생하는 지속피해·상태 해제·브레이크 행동 불가는 `상태 효과` 묶음으로 먼저 표시한다.
- 전투 중 정확한 현재 HP는 숨기고 HP 비율에 맞는 상태 문장을 표시한다.
- 전투 종료 시에는 남은 HP와 주요 통계를 공개한다.
- 초기 버전에서는 AI 생성 문장을 사용하지 않는다.

예시:

```text
{Actor}가 {Target}에게 일반 공격!
{Actor}의 공격이 {Target}을 향합니다!
{Actor}가 틈을 노려 공격합니다!
```

```text
치명타! {Damage}의 피해를 입혔습니다!
급소를 정확히 노렸습니다! {Damage}의 피해!
⚡ 추가타! {Target}에게 {AdditionalDamage}의 추가 피해!
```

체력 상태 메시지 후보:

```text
{Target}은 아직 끄떡없습니다!
{Target}이 조금씩 밀리기 시작합니다.
{Target}의 상태가 심상치 않습니다.
{Target}은 간신히 버티고 있습니다.
```

체력 구간에 따라 메시지를 선택할 수 있다.

초기 중계는 한 주요 행동을 한 Discord 메시지로 묶는다. 메시지에는 스킬 사용, 피해·회복·치명타·추가타·돌발 이벤트와 마지막으로 영향을 받은 캐릭터의 상태 문장을 함께 넣는다. 상태 문구는 남은 HP 비율 85% 이상(끄떡없음), 60% 이상(조금씩 밀림), 30% 이상(상태 심상치 않음), 그 미만(간신히 버팀)으로 구분한다.

초기 메시지 템플릿 수 목표:

| 이벤트 | 최소 템플릿 수 |
| --- | ---: |
| 일반 공격 시작 | 5개 |
| 일반 피해 | 5개 |
| 치명타 | 5개 |
| 추가타 | 3개 |
| 회피·실패 | 5개 |
| HP 상태 | 구간당 3개 |
| 승리·패배 | 각각 5개 |
| 클래스 스킬 | 스킬별 2~3개 |

## 10. 승패와 밸런스

### 10.1 승리 조건

- 상대 HP를 0 이하로 만들면 승리한다.
- 최대 주요 행동 20회에 도달하면 두 캐릭터의 남은 HP 비율을 비교한다.
- 남은 HP 비율 차이가 5%를 초과하면 비율이 높은 캐릭터가 승리한다.
- 남은 HP 비율 차이가 5% 이하이면 무승부로 처리한다.
- 동시 처치는 6.9 규칙에 따라 무승부로 처리한다.

### 10.2 목표

- 전투력이 높은 캐릭터가 분명히 유리해야 한다.
- 전투력만 보고 결과를 확정적으로 예상할 수 없어야 한다.
- 클래스와 스킬의 차이가 전투 로그와 결과에 나타나야 한다.
- 무작위성 때문에 능력치 의미가 사라지지 않아야 한다.
- 특정 클래스가 모든 상황에서 항상 우세하지 않아야 한다.

### 10.3 밸런스 검증

구현 시 실제 Discord에서 반복 실행하기보다 전투 시뮬레이터 테스트를 제공한다.

예상 검증 항목:

- 동일 조건 10,000회 실행 시 클래스별 승률
- 전투력 격차별 승률
- 평균 전투 턴과 소요 시간
- 스킬별 선택률과 기여도
- 무승부 비율
- 특정 스킬의 무한 반복 또는 교착 여부
- 극단적인 전투력·생활력·매력 입력

## 11. 캐릭터 소유권

랭킹 검색만으로는 해당 Discord 사용자가 실제 캐릭터 소유자인지 증명할 수 없다.

봇이 캐릭터의 실제 소유권을 확인할 방법은 없다. 장기적으로는 `게임 서버 + 캐릭터명`이 같은 캐릭터를 여러 사용자가 등록하지 못하게 할 예정이지만, 소유권 검증과 선점 분쟁 처리가 필요하므로 중복 등록 방지 구현은 후순위로 둔다.

초기 버전에서는 다음 원칙을 적용한다.

- 사용자당 등록 캐릭터는 하나다.
- 등록 정보는 모든 길드에서 공통으로 사용한다.
- 소유권을 인증하지 않는다.
- 서버 이전과 캐릭터명 변경을 자동으로 추적하지 않는다.
- 분쟁 대응과 운영진의 강제 등록 해제 기능은 추후 결정한다.

## 12. 도전 정책

배틀은 상대방의 수락 없이 즉시 시작한다.

- 도전 수락과 거절 기능을 제공하지 않는다.
- 수락 제한 시간과 반복 도전 쿨다운을 두지 않는다.
- 배틀 신청 차단 기능을 제공하지 않는다.
- 재대결 버튼을 제공하지 않는다.
- 도전자와 상대는 현재 같은 Discord 길드에 속해 있어야 한다.
- 길드당 게임 하나만 동작하므로 여러 배틀 또는 다른 놀이와 동시에 진행할 수 없다.
- 자기 자신에게는 배틀을 신청할 수 없다.
- Discord 온라인 상태는 검사하지 않는다. 현재 길드 구성원이고 등록 캐릭터가 유효하면 오프라인 사용자도 상대가 될 수 있다.

## 13. 저장 정책

### 13.1 영구 저장하는 데이터

배틀 기능이 DB에 저장하는 것은 Discord 사용자와 등록 캐릭터의 연결 정보뿐이다.

```text
UserCharacter
- DiscordUserId
- GameServer
- CharacterName
- ClassId
- CombatPower
- LifePower
- CharmPower
- LastSyncedAt
- CreatedAt
- UpdatedAt
```

캐릭터 등록은 봇 전체 공통이므로 `GuildId`는 캐릭터 소유 데이터의 키가 아니다.

### 13.2 영구 저장하지 않는 데이터

- 배틀 ID와 결과
- 승자·패자, 승률과 연승
- 참가자 전투 스냅샷
- 사용한 스킬, 피해량과 돌발 이벤트
- 전투 로그와 난수 시드
- 과거 전투 조회·다시보기 데이터

전투는 한 번 보고 웃고 끝나는 가벼운 놀이이며 결과를 누적해 경쟁하거나 성장시키는 콘텐츠가 아니다.

### 13.3 런타임 데이터

전투 시작 시 등록 캐릭터의 클래스·전투력·생활력·매력을 복사해 `BattleContext`와 `FighterState`를 만든다. 계산과 메시지 출력이 끝나면 참조를 제거한다. 봇이 도중에 재시작되면 복구하지 않고 해당 배틀을 취소한다.

### 13.4 로그 정책

일반 운영 로그에 승패나 전투 내용을 남기지 않는다. 오류 분석에는 오류 코드, 예외 종류와 실패한 데이터 ID만 한글로 기록한다. 상세 디버그 로그가 필요하면 개발 환경에서만 일시적으로 활성화한다.

## 14. 데이터 버전과 비재현성

전투 기록과 난수 시드를 저장하지 않으므로 종료된 전투를 재현하는 기능은 제공하지 않는다. 같은 두 캐릭터가 다시 싸워도 피해 편차, 행동 선택과 돌발 이벤트 때문에 결과가 달라질 수 있으며 이를 의도된 재미로 본다.

버전 관리는 과거 전투 복원이 아니라 현재 기준 데이터의 안전한 로딩을 위해 사용한다.

- 모든 배틀 관련 시트를 한 번에 검증한다.
- 성공한 데이터만 불변 스냅샷으로 교체한다.
- 실패하면 마지막 정상 데이터 스냅샷을 계속 사용한다.
- 이 스냅샷은 기준 데이터 캐시이지 전투 결과 기록이 아니다.

## 15. 오류와 복구

- 1시간이 지난 캐릭터의 랭킹 갱신에 실패하면 과거 값을 대신 사용하지 않고 배틀을 시작하지 않는다.
- 1시간 이내 캐시가 있으면 외부 랭킹 서비스에 접근하지 않고 그 값을 사용한다.
- 스킬 데이터 로딩 실패가 전체 봇 시작을 막지 않게 하며 마지막 정상 배틀 데이터 캐시를 유지한다.
- 마지막 정상 캐시도 없으면 배틀 명령만 실패시키고 다른 명령은 계속 제공한다.
- 전투 로그 한 건 전송 실패 시 한 번 재시도하고, 계속 실패하면 가능한 경우 결과 요약 한 건만 시도한다.
- 봇 재시작 시 진행 중 배틀은 복구하지 않는다.
- 캐릭터 등록·갱신 DB 쓰기가 실패하면 배틀을 시작하지 않는다.
- 배틀 가능 클래스(클래스 시트의 스킬 칸이 모두 채워지고 그 스킬이 모두 `배틀스킬`에 있는 클래스)는 시트 스냅샷을 불러올 때 미리 계산해 둔다. `/배틀`은 두 참가자의 클래스를 확인한 직후, 스레드를 만들기 전에 이 목록으로 판정한다. 지원하지 않는 클래스면 신청자에게만 현재 배틀 가능 클래스 목록과 함께 안내하고 전투를 시작하지 않는다. 엔진도 같은 기준으로 한 번 더 거부한다.
- 스레드 생성 뒤 시뮬레이션이 실패하면 중단 안내를 남기고 스레드를 잠금·보관한다.
- 성공·실패·취소의 모든 경로에서 `finally`로 길드 게임 잠금과 런타임 상태를 해제한다.
- 전투 결과와 전적은 저장하지 않으며 종료 시 런타임 상태를 반드시 폐기한다.

## 16. MVP 제안

### 단계 1: 데이터와 전투 엔진

- 캐릭터 등록·조회·변경
- 랭킹 데이터 스냅샷 저장
- 클래스 데이터 로딩
- 전투력 기반 HP·공격력 계산
- 일반 공격
- 치명타와 스킬·상태·돌발 이벤트에 의한 회피
- HP와 승패
- 실행 중에만 사용하는 난수 생성기
- 전투 시뮬레이션 테스트

### 단계 2: Discord 배틀

- `/배틀 상대:@사용자`
- 명령 채널과 같은 길드 사용자 검증
- 명령 실행 채널에 전투 스레드 생성
- 시간차 전투 로그 출력
- 결과 요약
- 길드 단위 게임 잠금 관리

### 단계 3: 클래스 스킬

- Google Sheets의 배틀 관련 시트를 원자적으로 로드하는 스냅샷 구현
- 전체 시트의 참조 무결성 검증과 마지막 정상 캐시 유지
- 스킬과 효과 타입 파싱
- 파생 스킬의 즉시 실행, 반격 실행, 다음 행동 예약
- 스킬 선택 로직
- 쿨다운과 조건
- 버프·디버프·상태 이상
- 타입별 메시지 템플릿

### 단계 4: 배틀생활스킬·돌발 이벤트와 연출

- 배틀생활스킬의 낮은 사용 확률, 후보 조건, 무작위 결과형 선택과 생활력 비례 효과 처리
- 기존 생활력 돌발 이벤트(`life_surprise_*`) 제거
- 매력 돌발 이벤트의 조건과 확률 처리
- 전투당 횟수 제한과 전역 쿨다운
- 이벤트 효과를 공통 `BattleEffect` 처리기로 실행
- 이벤트별 메시지 다양화
- 전투 종료 후 런타임 상태 폐기 검증

생활력은 전투력·클래스 스킬 기반 MVP가 안정된 뒤 저확률 배틀생활스킬로 추가하고, 매력은 돌발 이벤트로 추가한다.

## 17. 남은 구체화 항목

아래 항목은 구현을 막는 계약이 아니라 시뮬레이션 결과를 보고 조정할 밸런스 값이다. 초기 구현은 본 문서와 `배틀규칙` 시트의 기본값으로 진행한다.

### 확정된 구현 규칙

- 사용자당 캐릭터 하나, 봇 전체 공통 등록
- 등록 명령은 현재 구현된 `/캐릭터등록` 사용
- 랭킹 데이터 유효 시간 1시간, 만료 후 갱신 실패 시 배틀 중단
- 상대방 수락·도전 쿨다운·신청 차단·재대결 버튼 없음
- 같은 길드의 다른 사용자만 상대 가능하며 온라인 상태는 검사하지 않음
- 길드당 모든 놀이터를 합쳐 하나만 동시 실행
- 무조작 텍스트 자동전투, 주요 행동 최대 20회
- 선공은 별도 민첩 능력치가 없으므로 초기 버전에서 50:50 무작위 결정
- 조건식 AI와 행동 횟수 기반 쿨다운 사용
- 다단 공격은 타격마다 방어·편차·치명타·추가타·사망 판정
- 파생·반격·돌발 이벤트는 원칙적으로 주요 행동을 소비하지 않음
- 생활력은 주요 행동을 소비하는 저확률 배틀생활스킬의 사용 확률과 효과에 사용하고(기준값 30,000), 매력은 별도의 돌발 이벤트 확률에만 사용
- 동시 처치는 무승부
- 전투 결과·전적·로그·난수 시드는 저장하지 않음

### P1: 시뮬레이션으로 조정

1. 전투력 압축 지수와 상·하한별 목표 승률
2. 클래스·스킬별 우선순위, 가중치와 쿨다운
3. 일반 공격과 궁극기의 평균 선택 빈도
4. 버프·디버프별 최대 중첩과 수치
5. 상태 이상 저항·해제 효과를 실제로 도입할지 여부
6. 초 단위 원본 효과를 행동 수로 변환하는 기준
7. 돌발 이벤트의 기준값·보정계수·확률 상한
8. 메시지 묶음 크기와 전송 간격

### P2: MVP 이후 검토

1. 관전자 응원 또는 개입
2. 토너먼트
3. 클래스별 기본 공격 연출 확장
4. 운영진의 강제 캐릭터 등록 해제 도구

전적·승률·연승·전투 로그 저장은 현재 기획 범위에서 제외하며 별도 결정 항목으로 남기지 않는다.

## 18. 구현 순서

1. 현재 `/캐릭터등록`이 저장하는 모델을 `UserCharacter` 계약과 대조한다.
2. 배틀 관련 시트를 하나의 `BattleDataSnapshot`으로 로드·검증한다.
3. Discord와 분리된 순수 전투 엔진과 고정 난수 테스트를 만든다.
4. 일반 공격, 종료 판정과 전투력 공식을 먼저 구현한다.
5. 스킬 효과, 쿨다운, 상태, 자원과 파생을 순서대로 추가한다.
6. 배틀생활스킬과 매력 돌발 이벤트를 공통 효과 처리기에 연결한다.
7. `/배틀`, 게임 스레드, 길드 잠금과 출력 큐를 연결한다.
8. 10,000회 시뮬레이션으로 밸런스 값을 조정한다.

### 18.1 구현 완료 기준

- 문서의 입력으로 전투를 끝까지 시뮬레이션할 수 있고 Discord 없이 단위 테스트할 수 있다.
- 동일한 고정 난수 입력은 동일한 이벤트 목록을 만든다.
- 잘못된 시트 참조·enum·범위는 로드 단계에서 한글 오류로 식별된다.
- 데이터 갱신 실패 시 마지막 정상 스냅샷이 유지된다.
- 전투 도중 데이터 캐시가 교체되어도 진행 중 전투 결과는 영향을 받지 않는다.
- 정상 종료, 무승부, 예외, 취소와 메시지 실패 모두 길드 잠금을 해제한다.
- 전투 전후 DB를 비교했을 때 캐릭터 갱신 외에 전투 결과 데이터가 추가되지 않는다.
- 전투 로그와 오류 메시지에 Discord 토큰, Google 인증 정보 등 비밀 값이 포함되지 않는다.
- README의 슬래시 명령 표와 실제 `/배틀` 옵션이 일치한다.
- `bash scripts/verify.sh`가 통과한다.

### 18.2 문서와 데이터의 우선순위

1. 사용자에게 보이는 명령 이름·옵션은 실제 명령 구현과 README를 우선한다.
2. 전투 상수와 활성 데이터는 검증을 통과한 Google Sheets 스냅샷을 우선한다.
3. 처리 순서, 저장 금지와 오류 정책은 이 기획서를 우선한다.
4. 서로 충돌하면 임의로 추정하지 말고 한글 오류와 충돌한 키·ID를 남긴 뒤 배틀 시작을 막는다.

## 19. 기획·시트 갱신 개발 절차

기획서나 배틀 시트가 갱신될 때는 구현이 문자열을 추측하지 않도록 다음 순서로 작업한다.

새 클래스의 스킬 데이터를 `배틀스킬`·`배틀스킬효과` 등 기존 스키마에 채워 넣는 반복 작업은 이 절차가 아니라 `new-class-workflow.md`를 따른다. 이 절은 스키마 자체(새 효과유형·조건유형·상태·규칙 상수)를 바꿀 때만 적용한다.

1. `Battle/BattleModels.cs`의 불변 입력 모델과 `Battle/BattleCatalog.cs`의 헤더·참조 검증을 먼저 함께 갱신한다.
2. 새 규칙 상수는 `배틀규칙.ID`에 영문 `snake_case`로 추가한다. 현재 기본 엔진이 요구하는 ID는 `base_max_hp`, `base_attack`, `base_defense`, `power_scale_exponent`, `power_scale_min`, `power_scale_max`, `defense_coefficient`, `damage_variance_min`, `damage_variance_max`, `base_critical_chance`, `critical_damage_multiplier`, `additional_hit_chance`, `additional_hit_damage_ratio`, `max_major_actions`, `draw_hp_ratio_threshold`, `normal_attack_multiplier`, `skill_damage_min_multiplier`, `skill_damage_max_multiplier`, `ultimate_damage_multiplier`, `minimum_skill_cooldown`, `skill_heal_min_multiplier`, `skill_heal_max_multiplier`, `ultimate_heal_multiplier`, `life_surprise_hp_ratio_threshold`, `life_surprise_base_chance`, `life_surprise_stat_reference`, `life_surprise_stat_coefficient`, `life_surprise_max_chance`, `life_surprise_heal_ratio`, `charm_surprise_base_chance`, `charm_surprise_stat_reference`, `charm_surprise_stat_coefficient`, `charm_surprise_max_chance`, `charm_surprise_damage_multiplier`다.
3. 시트 전체를 검증한 새 `BattleDataSnapshot`을 캐시에 저장할 수 있을 때만 공개한다. 일부 탭만 성공한 데이터나 미검증 자유문자열을 전투 엔진에 전달하지 않는다.
4. 새 효과·조건·상태·자원은 `BattleEffect`와 명시적 enum/처리기로 정규화한 뒤 `BattleEngine`에 추가한다. 알 수 없는 값은 조용히 무시하지 말고 로드 오류로 처리한다.
5. 고정 난수로 재현 가능한 오프라인 회귀 테스트를 `tests/Molly.DataTests`에 추가하고 `bash scripts/verify.sh`를 실행한다.

`배틀스킬효과`의 `계수` 열은 2026-09-20에 삭제했다. 실제 게임 화면의 수치를 역산한 계수는 캐릭터·장비 조건에 따라 일관되지 않아 밸런스 입력으로 사용하지 않는다.

`클래스`의 `스킬1~궁극기`가 모두 비어 있는 행은 아직 배틀 미구현 클래스의 원본 정보로 보고 스냅샷에는 보존한다. 이 클래스의 캐릭터는 배틀을 시작할 수 없다. 반대로 여섯 칸 중 일부만 비어 있거나 존재하지 않는 스킬 ID를 참조하면 반영 중 오류로 보고 전체 스냅샷 갱신을 실패시킨다.

현재 구현은 전투력 압축·일반 공격·스킬 다양화 쿨다운·전투 배율 기반 피해·회복·배틀생활스킬·매력 돌발 이벤트·최대 행동 수 종료와 `/배틀` 스레드 중계를 제공한다. 상태, 자원, 파생은 시트 CSV의 원자적 로드와 기본 참조 검증까지만 연결되어 있으며, 해당 효과 처리기는 이후 기획 갱신에서 위 절차로 확장한다.

## 20. 레퍼런스

### 19.1 Progress Quest

Progress Quest는 캐릭터 생성 이후 전투, 퀘스트, 전리품 판매와 성장까지 시스템이 자동으로 진행하는 제로 플레이어 RPG다. 공식 매뉴얼은 이를 `fire and forget` 방식으로 설명하며 플레이어가 전혀 상호작용할 필요가 없다고 명시한다.

몰리 배틀에서는 다음 원칙을 참고한다.

- 전투가 시작된 뒤 플레이어 입력을 요구하지 않는다.
- 캐릭터의 행동과 결과를 시스템이 모두 결정한다.
- 사용자는 계산을 조작하는 사람이 아니라 진행 상황을 관찰하는 사람이다.
- 내부 처리와 사용자에게 보여주는 진행을 분리한다.

출처:

- <https://progressquest.com/>
- <https://progressquest.com/info.php>

### 19.2 Godville

Godville은 영웅이 스스로 성장하고 모험하며 그 과정을 일기 형식으로 기록하는 텍스트 중심 제로 플레이어 게임이다. 정확한 계산식보다 캐릭터의 행동을 다양하고 유머러스한 문장으로 전달하는 데 집중한다.

몰리 배틀에서는 다음 원칙을 참고한다.

- 수치 계산보다 전투 상황을 설명하는 문장을 중심으로 보여준다.
- 같은 전투 이벤트에 여러 메시지 템플릿을 둔다.
- HP 상태와 위기, 역전, 승패를 이야기 흐름으로 표현한다.
- 사용자가 개입하지 않아도 다음 문장을 기다리게 만드는 중계 속도를 사용한다.

출처:

- <https://godvillegame.com/>
- <https://en.wikipedia.org/wiki/Godville>

### 19.3 Stone Story RPG

Stone Story RPG는 AI가 이동과 전투를 자동으로 처리하고 ASCII로 상황을 표현하는 오토 RPG다. 전투 중 사용자의 장비 교체와 능력 사용 개입이 가능하므로 몰리 배틀의 직접적인 사용자 경험 레퍼런스는 아니다. 다만 HP와 상태에 따라 행동을 선택하는 조건식 AI 구조는 참고한다.

몰리 배틀에서는 다음 원칙만 제한적으로 참고한다.

- 현재 HP와 상태 효과에 따른 행동 조건
- 사용 가능한 스킬 후보 선별
- 상황별 장비 대신 클래스 스킬의 우선순위 결정

출처:

- <https://store.steampowered.com/app/603390/Stone_Story_RPG/>

### 19.4 적용 범위

Progress Quest와 Godville은 무조작·텍스트 표현의 레퍼런스이며, 공정한 단판 PvP 밸런스를 직접 제공하지 않는다. 따라서 피해 공식, 전투력 격차별 승률, 최대 행동 수와 무승부 판정은 몰리 배틀의 목적에 맞게 별도로 설계하고 시뮬레이션으로 검증한다.
