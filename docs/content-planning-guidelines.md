# 몰리 콘텐츠 기획 가이드라인

> 문서 상태: 초안  
> 최종 갱신: 2026-09-29  
> 목적: GPT의 콘텐츠 기획·검토와 Codex·Claude의 구현 판단에 공통 기준을 제공한다.

## 1. 프로젝트 방향

몰리는 마비노기 모바일 이용자를 위한 Discord 기반 보조 서비스이자 가벼운 놀이터다.

게임을 직접 대신 플레이하거나 인게임 기능을 그대로 복제하지 않는다. Discord라는 환경의 장점을 이용해 다음 두 가지 가치를 제공한다.

1. 게임에 접속하지 않은 동안에도 도움이 되는 편의 기능
2. 별다른 준비 없이 가볍게 참여할 수 있는 놀이 기능

### 핵심 한 줄

> 몰리는 사용자가 게임을 보고 있지 않을 때 필요한 정보를 대신 지켜보고, Discord에서 대화하다가 부담 없이 즐길 수 있는 마비노기 모바일 동반자다.

## 2. 콘텐츠의 두 가지 중심축

모든 신규 콘텐츠는 원칙적으로 다음 두 축 중 하나에 속해야 한다.

### 2.1 편의 기능

게임에 접속하지 않은 상태에서도 가치가 있거나, 인게임에서 직접 확인하는 것보다 더 편리해야 한다.

- 사용자를 대신해 주기적으로 정보를 확인한다.
- 중요한 변화가 생겼을 때 먼저 알려준다.
- 여러 정보를 모아 비교하거나 요약한다.
- 기능에 꼭 필요하고 원본 서비스가 제공하지 않는 과거 데이터만 저장해 변화 추이를 보여준다.
- 사용자의 관심 항목만 골라 관리한다.
- 길드원이나 Discord 사용자 사이의 정보를 함께 보여준다.

현재 구현된 이벤트 마감 알림, 거래소 시세 모니터링, 완제품·재료 가격 비교, 랭킹·룬·상점 검색 등이 이 방향에 해당한다.

#### 필수 질문

> 사용자가 게임에 직접 들어가 확인하는 것보다 몰리를 사용하는 편이 왜 좋은가?

다음 중 하나 이상이 명확하게 성립해야 한다.

- 게임에 접속하지 않아도 알림을 받을 수 있다.
- 사용자가 반복해서 확인할 작업을 몰리가 대신한다.
- 인게임에서는 보기 어려운 과거 기록이나 비교 결과를 제공한다.
- 흩어진 정보를 한 번에 정리한다.
- 개인 또는 길드에 맞춘 결과를 제공한다.
- 조회에 필요한 시간이나 조작 횟수를 크게 줄인다.

이 질문에 답하기 어렵다면 단순한 인게임 정보 복제일 가능성이 높다.

### 2.2 놀이 기능

마비노기 모바일을 플레이하던 사람들이 Discord에서 대화하다가 자연스럽게 참여할 수 있는 가벼운 콘텐츠다.

현재 구현된 자동 배틀, 모의배틀, 퀴즈, 눈치게임, 라이어게임, 당첨뽑기, 병 속에 든 쪽지 등이 이 방향에 해당한다.

#### 기본 원칙

- 명령 한 번 또는 버튼 몇 번으로 시작할 수 있어야 한다.
- 규칙을 긴 설명 없이 이해할 수 있어야 한다.
- 중간에 참여하거나 구경만 해도 재미가 있어야 한다.
- 게임을 중단해도 손해가 크지 않아야 한다.
- 별도의 성장 숙제나 매일 접속해야 하는 의무를 만들지 않는다.
- 마비노기 모바일을 아는 사람에게 익숙한 이름과 소재를 사용한다.
- 결과가 Discord 안에서 대화 소재가 되어야 한다.
- 강한 경쟁보다 짧은 구경거리와 가벼운 반응을 우선한다.

몰리의 놀이는 “이거 한 번 해보자”, “내 캐릭터는 어떻게 나오지?”, “결과가 왜 이렇게 됐지?” 같은 반응을 목표로 한다. 매일 하지 않으면 손해를 보거나, 먼저 시작한 사람이 계속 유리하거나, 장시간 집중해야 하는 구조는 피한다.

## 3. Discord에서 제공해야 하는 이유

신규 콘텐츠는 마비노기 모바일을 소재로 사용한다는 이유만으로 충분하지 않다. 다음 가운데 최소 하나를 핵심 가치로 가져야 한다.

| Discord의 장점 | 적용 예시 |
| --- | --- |
| 비접속 알림 | 시세 변동, 이벤트 마감, 관심 아이템 등장 |
| 비동기 이용 | 사용자가 나중에 결과 확인 |
| 자동 관찰 | 정해진 주기로 외부 데이터 확인 |
| 기록 축적 | 가격 이력, 전적, 변화 기록 |
| 커뮤니티 공유 | 길드 단위 현황, 비교, 함께 보는 결과 |
| 짧은 상호작용 | 버튼, 선택, 명령 한 번으로 참가 |
| 대화 소재 생성 | 자동 배틀, 무작위 결과, 퀴즈 |
| 데이터 결합 | 시세·제작법·캐릭터·클래스 정보의 비교 |

단순히 게임 화면의 설명을 다시 보여주는 기능은 우선순위가 낮다. 검색 시간을 크게 줄이거나 다른 데이터와 결합한다면 편의 기능으로 검토할 수 있다.

## 4. 현재 활용 가능한 자산

### 4.1 저장소 기능

- Discord 슬래시 명령과 버튼·스레드 기반 상호작용
- 캐릭터 등록과 랭킹 조회
- 이벤트 수집 및 마감 알림
- 거래소 시세 수집·캐싱·변동 감지
- 서버별 알림 채널과 기준값 저장
- 배틀 엔진과 클래스별 전투 데이터
- 배틀 전적 저장
- 퀴즈와 참가형 미니게임
- SQLite 기반 영구 데이터 저장
- Google Sheets 데이터 로딩 및 검증

신규 기능은 가능하면 이 기반을 재사용한다.

### 4.1.1 외부 데이터 보관 원칙

- 외부 API가 이미 변화율이나 이력을 제공하면 같은 원시 이력을 몰리 DB에 장기간 중복 저장하지 않는다.
- 조회·알림·재시작 복구에 필요한 마지막 정상값과 최소 판정 상태만 보관한다.
- 자체 이력이 정말 필요한 기능은 먼저 사용자 가치, 보존 기간, 예상 저장량과 삭제 정책을 기획서에 적는다.
- 외부 API 응답에 필요한 계산값이 있다면 기존 호출에서 함께 받아 사용하고 별도 호출을 추가하지 않는다.
- 세부 시세 정책은 [거래소 시세 기능 기획서](market-price-monitoring.md)를 따른다.

### 4.2 Google Sheets 데이터

- 클래스, 액티브 스킬, 패시브 스킬
- 배틀 스킬·효과·AI·자원·상태 효과
- 배틀 패시브와 효과
- 배틀 생활스킬과 효과
- 돌발 이벤트
- 룬
- NPC와 지역
- 생활스킬
- 제작법과 가공법
- 상점 및 교환 정보
- 병 속에 든 쪽지

이 데이터는 조회뿐 아니라 검색·필터링·비교·추천·계산·시뮬레이션·퀴즈·무작위 사건·맞춤 결과·외부 시세와의 결합에 활용한다.

## 5. 아이디어 채택 기준

새로운 아이디어는 다음 항목을 각각 0~2점으로 평가한다.

| 평가 항목 | 0점 | 1점 | 2점 |
| --- | --- | --- | --- |
| 사용자 가치 | 없어도 불편하지 않음 | 일부 사용자에게 유용 | 반복적으로 분명한 도움 |
| Discord 이점 | 인게임과 차이 없음 | 접근이 조금 편함 | 알림·자동화·기록 등 명확한 우위 |
| 기존 데이터 활용 | 새 데이터가 대부분 필요 | 일부 재사용 | 기존 시트와 기능을 적극 활용 |
| 이용 장벽 | 설명과 입력이 많음 | 몇 단계가 필요 | 한 명령 또는 몇 번의 버튼 |
| 반복 이용성 | 한 번 사용 후 끝 | 가끔 사용 | 변화·상황에 따라 계속 사용 |
| 운영 비용 | API와 유지보수 부담이 큼 | 관리 가능 | 캐시·내부 데이터 중심 |
| 확장 가능성 | 전용 코드로 고립됨 | 일부 확장 가능 | 공용 구조로 다른 콘텐츠에 재사용 |

- 11점 이상: 적극 검토
- 8~10점: 범위를 줄여 실험
- 7점 이하: 보류하거나 다른 기능에 흡수
- 편의 기능은 `사용자 가치`와 `Discord 이점`에서 각각 1점 이상이어야 한다.
- 놀이 기능은 `이용 장벽`에서 2점을 받아야 한다.

점수는 결정을 돕는 도구이며, 사용자의 명시적인 판단을 대신하지 않는다.

## 6. API 호출과 운영 비용 원칙

- 길드 수에 비례해 같은 데이터를 반복 조회하지 않는다.
- 공통 데이터는 봇 전체에서 한 번 수집하고 서버별 설정에 따라 나누어 알린다.
- 조회 명령은 가능하면 마지막으로 저장한 캐시를 사용한다.
- 실시간성이 중요하지 않다면 정시 또는 일정 주기로 일괄 갱신한다.
- 검색어 하나로 여러 항목을 받을 수 있으면 묶어서 조회한다.
- 사용자가 요청할 때마다 API를 호출하는 기능은 별도의 호출 제한을 둔다.
- 실패한 회차는 불완전한 데이터로 덮어쓰지 않는다.
- API가 중단돼도 다른 기능은 계속 동작해야 한다.

외부 API를 쓰는 기획에는 다음 내용을 반드시 기록한다.

- 한 번 갱신할 때 필요한 호출 수
- 하루 예상 호출 수
- 길드 수 또는 사용자 수 증가에 따른 변화
- 캐시 유지 시간
- API 실패 시 행동
- 데이터가 오래되었음을 표시하는 방법
- 기능을 중단했을 때 영향을 받는 범위

## 7. 데이터 설계 원칙

- 원본 게임 정보는 Google Sheets에서 관리한다.
- 사용자 설정과 이력은 데이터베이스에 저장한다.
- 외부 API 응답을 시트의 원본 데이터처럼 취급하지 않는다.
- 이름만으로 연결하지 말고 가능한 경우 고정 ID를 사용한다.
- 표시 문구와 실제 계산 데이터를 구분한다.
- 새로운 클래스나 아이템을 추가할 때 코드 수정이 최소화되도록 한다.
- 여러 콘텐츠에서 사용할 수 있는 효과는 공통 효과 유형으로 정의한다.
- 특정 콘텐츠 하나만을 위한 예외 처리를 계속 늘리지 않는다.
- 시트 데이터가 잘못되면 부분적으로 실행하지 않고 마지막 정상 데이터를 유지한다.

## 8. 피해야 할 콘텐츠

### 8.1 인게임 정보 단순 복사

게임에서 몇 번만 누르면 볼 수 있는 내용을 그대로 출력하는 기능은 우선순위가 낮다. 여러 화면의 정보를 합치거나, 검색을 크게 단축하거나, 과거 기록·알림과 결합할 때 검토한다.

### 8.2 호출량이 사용자 수에 그대로 비례하는 기능

길드마다 동일한 아이템을 따로 검색하거나 명령을 실행할 때마다 외부 API를 호출하는 방식은 피한다.

### 8.3 긴 성장형 Discord 게임

별도의 레벨, 장비, 재화, 출석 숙제를 쌓아 몰리 안에 또 하나의 게임을 만드는 방향은 지양한다. 몰리의 놀이는 마비노기 모바일 이용자가 잠깐 즐기는 보조 콘텐츠여야 한다.

다만 하루 한 번의 짧은 상호작용으로 지급하고 즉시 가벼운 놀이에 사용할 수 있는 서버별 참여 재화는 허용한다. 이 경우에도 연속 출석·개근·일일 과제·성장 스탯·유료 교환을 붙여 의무감이나 장기 격차를 만들지 않는다. 현재 승인된 예외는 출석으로 지급하여 배틀 승부 예측에 사용하는 `마물 퇴치 증표`다.

### 8.4 설명이 먼저 필요한 놀이

시작 전에 긴 규칙을 읽어야 한다면 범위를 줄인다. 결과를 보면서 규칙을 자연스럽게 이해할 수 있어야 한다.

### 8.5 유지보수에 비해 사용 빈도가 낮은 기능

특정 기간이나 아이템 하나만을 위해 별도 수집기와 명령을 만들기보다 공통 검색·알림 구조로 흡수한다.

## 9. 기능 기획서 공통 양식

GPT, Codex, Claude가 새로운 콘텐츠를 제안하거나 구현 범위를 정할 때는 다음 형식을 사용한다.

### 기능명

사용자가 이해할 수 있는 이름을 먼저 정한다.

### 분류

- 편의
- 놀이
- 편의와 놀이의 결합

### 해결하려는 문제

사용자가 어떤 불편을 겪거나 어떤 순간에 심심함을 느끼는지 설명한다.

### Discord에서 제공하는 이점

인게임에서 하는 것보다 나은 이유를 한 문장으로 적는다.

### 핵심 사용자 흐름

명령 실행부터 결과 확인까지 3~7단계로 정리한다.

### 사용하는 기존 데이터

필요한 시트, 저장소 기능, DB 데이터를 명시한다.

### 새로 필요한 데이터

기존 데이터로 해결할 수 없는 항목만 적는다.

### API 사용량

갱신당 호출 수, 하루 호출 수, 길드·사용자 증가 영향, 캐시 정책을 계산한다.

### 최소 구현 범위

가장 작은 형태로 실제 사용 가치를 검증할 방법을 적는다.

### 제외 범위

초기 구현에 포함하지 않을 기능을 명시한다.

### 성공 기준

- 등록 후 실제 알림을 유지하는 서버 수
- 명령 재사용률
- 놀이 한 판의 완료율
- 한 기능의 주간 사용 횟수
- API 호출당 실제 사용자 도달 수
- 오류 또는 데이터 누락 비율

## 10. AI 역할 기준

### GPT: 기획과 검토

- 현재 저장소와 시트에서 재사용할 수 있는 자산 확인
- 사용자의 불편 또는 놀이 상황 정의
- Discord에서 제공할 이유 검증
- 기능 범위와 제외 범위 결정
- API 호출량과 운영 비용 계산
- 시트 데이터 구조 설계
- 사용자 흐름과 메시지 예시 작성
- 구현 결과와 기획 의도 비교
- 발견된 문제를 재현 가능한 검토 Issue로 작성

구현 방법부터 결정하지 않고 먼저 사용자 가치를 설명한다.

### Codex·Claude: 구현과 기술 검증

- 기획서와 현재 코드 구조를 기준으로 구현
- 기존 서비스·저장소·캐시 구조 재사용
- 기능별 하드코딩을 줄이고 공통 구조로 설계
- API 호출 제한과 실패 처리 구현
- DB 마이그레이션과 기존 데이터 보존
- 자동 테스트 및 수동 테스트 절차 작성
- README와 운영 문서 갱신
- 기획 범위를 넘어서는 변경이 필요하면 구현 전에 이유와 선택지를 보고

모호한 부분을 임의로 큰 기능으로 확장하지 않는다. 기획서에 없는 사용자 경험이 필요하면 먼저 선택지와 영향을 정리한다.

### 공통 원칙

- Google Sheets를 게임 원본 정보의 기준으로 삼는다.
- 저장소 구현을 실제 동작의 기준으로 삼는다.
- 기획과 구현이 충돌하면 어느 한쪽을 조용히 맞추지 말고 차이를 기록한다.
- 구현 완료는 빌드 성공만을 의미하지 않는다.
- 실제 데이터, 캐시, 알림, 실패 상황까지 검증해야 완료로 본다.

## 11. 완료 조건

- 사용자가 왜 이 기능을 써야 하는지 한 문장으로 설명할 수 있다.
- 명령어와 옵션이 도움말에 반영되어 있다.
- 정상 흐름과 주요 실패 흐름이 구현되어 있다.
- 외부 API를 사용한다면 호출량과 캐시 정책이 문서화되어 있다.
- 봇 재시작 후에도 필요한 설정과 기록이 유지된다.
- 같은 데이터를 서버마다 중복 수집하지 않는다.
- 데이터가 없거나 오래되었을 때 이를 사용자에게 숨기지 않는다.
- 시트의 실제 데이터와 구현 결과를 비교해 검증했다.
- 외부 서비스 장애가 다른 기능으로 전파되지 않는다.
- 최소한의 자동 테스트 또는 재현 가능한 수동 검증 절차가 있다.
